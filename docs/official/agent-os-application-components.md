# AgentCPM候选业务组件列表

> 文档定位：Agent OS 应用组件整体规划。此文件为飞书原文抄录快照，保留原文内容、顺序、编号、引用链接与历史说明，仅将标题层级、提示块和 5 张内嵌表格转换为 Markdown；表格单元格中的换行使用 `<br>` 表示。
>

## 一、整体框架：通用能力、业务任务与运行反馈

> 数据与知识进入  
> → 形成业务对象和事实  
> → 分析、规则、预测、仿真、优化  
> → 形成行动或制品  
> → 执行并记录结果  
> → 根据反馈修订知识、规则、代码或策略。

这里需要分清三种东西：

<!-- source-sheet: Uy9L8J; spreadsheet: X22vsXLdqhzpDwtfxuQcHIFqnEr; revision: 98; range: A1:C4 -->

| 层次 | 回答的问题 | 例子 |
| --- | --- | --- |
| 通用技术能力 | 需要哪些机制，能在哪些业务中复用？ | 数据修复、规则执行、约束求解、多智能体协作 |
| 业务任务 | 谁要完成什么工作，最终交付什么？ | 报销审核、采购风险处置、生产重排、软件迁移 |
| 组织与部署方式 | 这些工作以什么形态运行？ | 数字员工、主管与执行者、平级协作、私有化、端侧、离线 |

“数字员工”“多智能体”“私有化”可以贯穿很多业务，因此更适合作为组织或交付方式。讨论具体方向时，仍要落到明确任务上。

不同方向采用不同拆分维度：数据方向按生命周期拆，预测和优化按计算任务拆，多智能体按协作关系拆，业务方向按使用者和交付对象拆。

复用可以分四层讨论：通用基础组件、某类任务的专用计算组件、业务规则与语义包、客户现场适配。专用算法、对象模型、时效要求和执行接口也可能变化。

## 二、数据与决策：10 个方向、60 个二级能力

下面每个方向包含六个二级项，编号可按出现顺序使用，例如 D03-04 表示“数据质量”下的“修复方案生成”。

### D01｜数据资产发现与目录

解决“数据在哪里、归谁、是否适用”，用于企业接入盘点、审计找数和跨系统分析。

1. 元数据普查：扫描库表、文件和接口，形成可搜索的资产目录。
2. 业务资产匹配：把业务名称、字段样例和数据说明关联起来，寻找所需数据。
3. 责任与使用条件登记：记录维护者、更新承诺和使用条件，减少交付中的反复找人。
4. 可用性画像：评估覆盖时间、粒度、完整性和延迟，区分“存在”与“适合本任务”。
5. 运行血缘与出处：连接输入、处理任务、运行实例和输出，追溯某次结果怎样产生。
6. 变更影响传播：字段或数据源改变后，定位受影响的指标、规则、报告和业务任务。

目录、处理任务与实际运行记录值得分别建模。OpenLineage 的 Dataset、Job、Run 区分，为这一拆法提供了技术参照。

[OpenLineage 对象模型](https://openlineage.io/docs/spec/object-model/)

### D02｜连接适配与持续接入

解决数据怎样持续、准确地送达，覆盖数据库、文档、事件流与现场设备。

1. 结构化连接器：统一数据库、文件和 API 的读取、分页、游标与错误处理。
2. 文档结构化映射：从票据、合同、档案抽取字段，同时保存原文位置与映射版本。
3. 多模态时间对齐：对齐图像、声音、传感器和设备标识，形成可关联的事件。
4. 增量与事件接入：处理变更捕获、事件顺序、迟到数据和补采。
5. 接口与结构漂移适配：发现字段、接口或编码变化，生成兼容判断与映射修订。
6. 离线同步与冲突交接：现场断网时保留数据，恢复连接后同步并呈现冲突。

这里负责持续提供数据；一次业务操作是否执行成功，归后面的 R02。

### D03｜数据质量、修复与复核

把 DataAgent 从“发现脏数据”扩展到“提出修复、写回、确认修复有效”。

1. 结构与取值契约：检查缺列、类型、唯一性、允许范围等明确约束。
2. 跨表对账与勾稽：核对总分、余额、关联关系，处理局部正确但整体不一致的问题。
3. 异常与缺失定位：发现突变、分布异常和缺失模式，同时保留“异常未必是错误”的区别。
4. 修复方案生成：提出标准化、去重、补齐等修改候选，保留原值、理由和影响范围。
5. 复核反馈沉淀：把接受、驳回和修订原因转成可复用修复规则。
6. 质量事故定位与恢复：沿血缘定位已经受影响的结果，提出重算和恢复范围。

其中，修复建议由本方向产生，实际写回与回执核对复用 R02，人工复核复用 R07。

### D04｜语义层、实体与本体

解决“同一个业务概念到底是什么意思”，支撑跨部门报表、业务关系分析与历史复盘。

1. 指标定义与组合：明确聚合、过滤、分母和派生关系，让指标能被实际计算。
2. 粒度、时间与单位语义：处理订单与明细、日与月、币种与计量单位之间的差异。
3. 实体消歧与主数据对齐：识别同一供应商的多个编号，保留合并依据及拆分能力。
4. 对象关系与状态模型：描述订单、设备、组织等对象的关系和状态变化。
5. 术语解释与歧义解析：识别业务问题中的多种口径，定位真正需要澄清的含义。
6. 语义变更与历史重现：保存定义版本与生效时间，按指定口径重算历史结果。

更准确的目标是：在相同定义版本、过滤条件和数据快照下得到一致结果；条件不同造成的差异能够解释。dbt 的语义模型也将实体、维度和计算语义作为明确结构，而不只是术语说明。

[dbt 语义模型](https://docs.getdbt.com/docs/build/semantic-models)

### D05｜知识加工、索引与证据检索

解决“针对这个问题，哪些资料足够、适用、可引用”。

1. 结构切分与引用锚点：保留章节、表格、附件关系，避免切分后丢失上下文。
2. 混合召回与重排：组合关键词、语义等检索方式，再按任务相关性排序。
3. 图关系与路径检索：沿实体关系查找证据，用于供应商穿透、案例关联等任务。
4. 时效与版本检索：根据查询时点选择适用制度，支持历史复盘。
5. 权限感知证据集：按照调用身份控制检索和输出范围。
6. 缺证与冲突发现：识别资料不足、结论矛盾或来源互相依赖，形成待补证据清单。

D04 定义业务含义，D05 找依据，R05 管理当前任务使用这些材料的方式，三者分工不同。

### D06｜深度分析与问题诊断

解决“发生了什么、差异在哪里、哪些解释值得继续调查”。

1. 问题到分析计划：将问题拆成假设、取数和检验步骤，随新证据调整。
2. 可复现计算：运行 SQL、统计或代码，保存参数与中间结果。
3. 指标分解与差异诊断：按结构、维度和贡献拆解变化，用于成本、收入和质量分析。
4. 关系网络分析：分析多主体、多跳关系中的聚集、路径和结构异常。
5. 因果问题与验证设计：明确干预、对照和混杂因素，区分相关性与因果结论。
6. 持续问题调查：告警后自动展开进一步分析，持续积累调查记录。

其中，“业务计算程序怎样生成和修复”复用 R01；本方向负责选择分析方法、解释结果。

### D07｜预测与提前预警

估计未来状态及不确定性，用于需求准备、设备维护和风险预警。

1. 需求与负荷预测：估计订单、客流、能源用量等未来变化。
2. 故障与事件发生预测：估计事件概率或剩余时间，提供提前处置窗口。
3. 多层级预测协调：协调门店、区域和总量预测，避免各层互相矛盾。
4. 冷启动与迁移预测：为新品、新设备借用相似对象和先验知识。
5. 不确定性与预警分级：呈现区间、尾部情形和不同告警的代价。
6. 漂移监测与校准：对照预测和实绩，定位环境变化及误差来源。

预测回答未来可能怎样；给定行动后的后果交给 D08，行动选择交给 D09。

### D08｜仿真与可计算实验

给定假设、动作和环境，比较可能后果。

1. 业务账算情景：基于明确公式与约束，比较调价、扩产、预算等方案。
2. 离散事件仿真：模拟队列、拥塞和有限资源，适用于产线、仓储、服务窗口。
3. 多主体行为仿真：表达客户、车辆或组织的行为及相互影响。
4. 机理与数据模型耦合：连接已有物理、工艺和统计模型，处理行业专门问题。
5. 参数敏感性与随机实验：改变参数或采样情形，找出结果最敏感的因素。
6. 历史复盘与模型校准：按历史条件重演，定位模型与现场的偏差。

注：

这次补齐了旧稿未取得的 Palantir 官方资料：Ontology scenarios 当前标为 Beta，可比较隔离情景，但官方明确它不是历史快照工具。因此，场景副本、固定回测数据和专业模拟器需要分别考虑。

[Palantir Scenarios](https://www.palantir.com/docs/foundry/ontology/overview-ontology-scenario)

仿真内部也要继续区分机制。例如 SimPy 面向离散事件和共享资源，不能据此概括所有连续物理过程的仿真能力。

[SimPy 官方说明](https://simpy.readthedocs.io/en/stable/)

### D09｜约束优化与资源调度

在明确目标和约束下，选择可执行行动。

1. 约束建模与冲突解释：表达硬约束、软约束，并解释为什么没有可行方案。
2. 配额与资源分配：分配预算、人员、设备或算力。
3. 工序与时间排程：处理前后工序、机器占用和交期冲突。
4. 网络、库存与路径优化：联动运输、补货、容量和服务要求。
5. 多目标方案比较：展示成本、质量、交付之间的权衡，避免隐藏价值取舍。
6. 多方资源协商：协调部门或工厂之间的资源竞争，交换候选方案。

OR-Tools 的 Job Shop 示例明确建模工序先后、机器互斥和完工时间目标。由此可以借鉴“自然语言表达需求、求解器处理约束、Agent 解释方案”的分工；真实工厂仍需自己的领域模型。

[OR-Tools 排产示例](https://developers.google.com/optimization/scheduling/job_shop)

### D10｜外部变量与情景决策

解决“外部变化怎样影响自己、何时应该重新决策”。

1. 外部信号接入与可信度：登记天气、价格、政策等来源、时效和修订情况。
2. 业务暴露映射：把外部事件关联到设施、地区、供应商、产品和合同。
3. 事件与规则变化结构化：提取生效时间、适用对象、条件和待确认项。
4. 情景组合与假设管理：构造多因素联动情景，记录假设及概率依据。
5. 跨情景稳健选择：比较不同情景下的损失、后悔值和约束违例。
6. 触发重规划与结果跟踪：环境变化后重算方案，记录实际执行和结果。

D08 提供“怎么算后果”，D09 提供“怎样选行动”，D10 决定“哪些外部变化需要纳入、何时重新算”。

## 三、执行与协作：10 个方向、60 个二级能力

### R01｜规则、代码与可执行制品

把要求转成可运行、可检查、可修改的产物，是规则引擎与 Coding Agent 的共同主线。

1. 制度转规则：生成带出处、例外和生效时间的规则候选。
2. 业务计算转代码：把分析要求转成 SQL、Python 或表格公式。
3. 存量程序维护：理解已有行为、定位问题、修改代码并检查影响。
4. 批量迁移与重构：形成可复用转换规则、迁移脚本和兼容适配。
5. 测试与判例生成：从需求、历史缺陷和边界条件生成正反例。
6. 执行驱动修复：根据真实运行错误和差异，迭代修改代码或规则。

软件迁移可以积累可组合的变换规则。OpenRewrite 的 recipe 机制提供了这类技术参照，适合研究“Agent 形成候选变换—工具执行—独立检查”的组合。

[OpenRewrite Recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes)

### R02｜工具与动作执行

让分析结果进入真实系统，并确认操作是否完成。

1. 工具发现与契约适配：识别 API、MCP、CLI 的参数和返回结构。
2. 工具选择与参数装配：根据任务、对象和环境选择正确操作。
3. 执行环境管理：准备代码、浏览器、桌面操作所需的依赖和环境。
4. 批量动作与部分成功处理：拆批、限速、记录逐项结果。
5. 可靠写出与状态核对：通过请求标识、回执、查询、重试与对账确认结果。
6. 补偿与撤回：处理撤销、冲正和人工修复，区分不同动作的可逆程度。

“两层写回”本身不保证不丢不重。Palantir 明确说明，其 Action 的原子性不延伸到 webhook、通知和外部调用；这正是回执、幂等、对账与补偿需要独立考虑的原因。

[Palantir 事务与隔离](https://www.palantir.com/docs/foundry/action-types/consistency-guarantees)

### R03｜任务与流程控制

把一项工作持续推进到完成，区分计划、运行状态和触发条件。

1. 目标分解与依赖计划：形成有输入、产物和完成条件的任务图。
2. 确定性业务流程：表达顺序、分支、截止时间与退出条件。
3. 自主探索与重规划：根据新证据调整后续任务和工具路径。
4. 长流程暂停与续跑：跨进程、跨天等待材料、人审或外部回调。
5. 事件与定时驱动：按消息、数据变化、时间或阈值启动工作。
6. 工作优先级与队列：处理插单、取消、超期和任务间依赖。

这里调度业务工作；底层计算资源和调用预算由 R09 管理。

### R04｜多智能体组织

按责任、信息和交付关系选择协作方式。

1. 层级委派：负责人分解任务、子团队执行、逐级验收。
2. 平级并行分析：不同专业独立分析，再合并结论或保留分歧。
3. 共享工作区协作：围绕共同问题状态与制品持续增量工作。
4. 动态专家交接：按问题变化转交角色，明确接手条件与交接内容。
5. 群体讨论与裁决：支持提案、反证、辩论及明确结束条件。
6. 制品驱动团队：需求、设计、开发、测试等角色围绕代码、规则或报告交接。

组织拓扑和状态共享方式应分别配置。

### R05｜上下文与记忆

决定当前这一步需要知道什么，以及哪些经验需要跨任务保留。

1. 按任务装配上下文：按阶段选取制度、事实和历史产物。
2. 长上下文压缩：保留约束、证据位置和未解决问题，压缩重复过程。
3. 会话工作状态：保存计划、分支、工具结果和待办事项。
4. 个人与岗位记忆：积累偏好、职责、协作关系和长期知识。
5. 经验提取与复用：从任务中提炼带适用条件的案例和做法。
6. 记忆校正与失效管理：处理冲突、版本更新和过期事实。

长期岗位可以由 R03 的持续任务、R05 的记忆与 R07 的交互组合形成，不必另造一种底层组织架构。

### R06｜多模态与现场交互

重点是理解变化中的现场并与之互动；离线材料接入复用 D02。

1. 现场视觉与状态变化理解：识别作业过程、对象变化与异常事件。
2. 空间定位与测量：关联区域、位置、距离和尺寸，给出可复核证据。
3. 音视频事件理解：对齐讲话、画面和事件时间线，用于课堂、会议、作业复盘。
4. 实时语音协作：处理轮次、打断、确认与现场问答。
5. 屏幕与桌面操作：依据界面状态执行步骤，并确认操作结果。
6. 传感器与设备协同：将信号、设备状态、任务和指令关联起来。

### R07｜人在环与业务交付

让产物被理解、处理，并形成下一步行动。

1. 需求澄清与任务协商：定位真正影响结果的缺失信息。
2. 证据化报告与制品：交付有出处、计算方法和待核实项的报告、表格或图表。
3. 异常复核工作台：把问题、依据、建议和修改入口放在一起。
4. 按动作分级授权：根据对象、影响范围和可撤回性决定执行方式。
5. 协作工单与责任交接：把结论变成有负责人、期限和依赖的工作项。
6. 多入口与主动服务：聊天、嵌入页、API、移动端共享任务状态。

### R08｜评测、反馈与持续改进

把真实运行结果转成下一轮改进依据。

1. 业务判据建模：分别定义准确性、漏检、成本、时效和业务结果。
2. 离线回放与回归：在固定历史样本上比较候选版本。
3. 轨迹诊断与错误归因：区分数据、检索、计划、模型、工具和环境错误。
4. 人工反馈转样本：结构化保存复核、修改、申诉及业务结果。
5. 制品与策略优化：修改提示词、示例、规则、代码或路由，明确变化对象。
6. 影子评估、线上比较与漂移监测：观察候选版本影响，区分版本改善和环境变化。

历史回放与实际决策上的影子评估应保留为不同能力。Aera 的官方资料支持政策转规则、启用前观察影响以及记录决策结果，但不能据此承诺任意业务都会自动持续改善。

[Aera Decision Governance](https://www.aeratechnology.com/technology/decision-governance/)

### R09｜运行时与资源调度

支撑长期、多任务及云边环境中的运行。

1. 会话与执行循环：管理开始、运行、等待、取消和完成状态。
2. 模型与算法路由：在语言模型、视觉模型、规则和求解器之间选择。
3. 并发、预算与服务质量：管理调用量、耗时和计算资源分配。
4. 故障恢复与隔离：保存恢复点、限制故障传播、选择降级路径。
5. 云边协同与离线运行：在端侧与云侧分配工作，断网时保留必要能力。
6. 身份与执行边界：把调用者、数据范围和动作权限传递到执行端。

### R10｜组件装配与交付运维

将一次项目中的能力沉淀为可复用产品组件。

1. 能力包与依赖管理：封装工具、技能、规则、模型和示例。
2. 可视化与代码双入口：兼顾业务配置和开发者扩展。
3. 配置、版本与环境迁移：追踪不同客户、环境运行的组件与参数。
4. 可观测与任务回放：关联任务、调用、结果、成本与制品，定位卡点。
5. 部署与运维自动化：支持私有化、边缘部署、健康检查和升级。
6. 使用运营与复用分析：记录任务需求、采纳、失败和实际组件复用。

这十条链路共享一个核心：

生成代码、规则或计划，在真实数据或环境中运行，观察结果，再修改明确的对象。

“自进化”因此可以具体化为：改知识、改映射、改规则、改代码、改流程或改模型路由。每一种改动都有不同输入、反馈和适用条件。

## 六、本轮最值得继续展开的六条主线
