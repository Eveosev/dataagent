# 附录 B：通用能力契约 —— 与 IFace 的接口对齐（2026-10-29 修订）

> 本文是 RSI Toolkit 对 IFace 的“通用能力契约”需求清单，供与 Mint / kernel 开发者沟通。
> **2026-10-29 已对照 kernel master（`d950766`）与 cpmrt 0.1.14 全部复核**：C1–C7 的需求定义不变，
> 但“上游已有什么、还缺什么”一律以本文为准，替代 2026-10-28 初稿中的过时判断。
> 原始草案与复核证据在仓库 `docs/dev/rsi_toolkit/iface-review/`（附录 B、附录 F）。

## 0. 一页结论

| 契约 | 判定 | 上游现在有什么 | 一句话缺口 |
| --- | --- | --- | --- |
| C1 blob | 不满足 | 无内容寻址存储；最近的只有打包层 sha256 / dirhash 与 hub 的 blob | 运行时没有“按 digest 存取任意内容”的契约 |
| C2 index | 部分满足 | `mint-api` 的 `MemoryProvider`（store / recall / consolidate）+ WIT `memory.wit` + cpmrt 内置 `file-jsonl` | 没有不可变快照与 `bank_hash`，库是可改写的“活记忆” |
| C3 evaluation | 不满足 | 无任何评测 / 打分契约 | 从零开始；但 `Unknown` 语义有先例可引 |
| C4 evidence | 部分满足 | `ModelUsage`（input / output / total）+ `ModelResponse.model` 的“不得伪造”规则 + `Secret` 打码 | 没有 seal / verify / redact，没有观测方指纹，没有 cached / cost |
| C5 asset | 不满足 | `ExtensionContract` 的装配状态机；`mint.lock` 的包账本 | 没有“版本 + 当前激活集合 + 期望版本 + 一次性授权” |
| C6 workspace-staging | 不满足 | `FsBackend` 4 方法 + 4 个粗能力位；`ToolStaging` 证明窄契约可行 | 没有 mkdir / 原子替换 / 按名拒绝 / 细粒度能力声明 |
| C7 runtime-executor | 部分满足（语义有、接口无） | `RequestState`（含 `Unknown`）、`operation.*` 作业视图、`idempotency_key` 强制、五类终止 | 没有 task 级、调用方给 id 的 submit / status / result |

三条要点：

1. **七个契约没有一条被上游完整满足。**
2. **C2、C4 是“接口像、语义差”；C7 是“语义有、入口不对”**——所以 C7 的沟通成本比原判断低，但结论仍是缺口。
3. **上游不存在 `runtime-executor`，也不存在 `execution_id`**；hub 上的 `agentcpm/iface-*@0.1.0` 发布于 2026-10-27T15:37Z，已落后 master（缺 D93 模型流式、D96 模型会话）。

## 1. 契约分层与治理

| 类别 | 例子 | 治理归属 |
| --- | --- | --- |
| Kernel 机制契约 | session、loop、tool、model、store、policy、context、extension、env、handoff、lease、audit、trace | 由 kernel 维护；本项目的策略是**尽量消费、不重复定义** |
| 通用能力契约 | 下文 C1–C7 | 先在 RSI 仓库起草并发布，出现第二个消费者后再向 kernel 提议晋升 |
| RSI 领域数据契约 | `rsi-trace.data`、`rsi-experience.data`、`rsi-evaluator.data`、`rsi-recall.data`、`rsi-component.data` | 始终放在自有命名空间，遵守与 IFace 相同的规则 |

### 1.1 权威来源（2026-10-29 修正）

原口径“以线上 `agentcpm/iface-*@0.1.0` 的 bundle 制品 + 固定 digest 为准”**已失效**。原因是事实变了：

- hub 上 10 个包全部在 **2026-10-27T15:37Z** 发布，此后未再更新；
- 而 kernel master 在此之后还有多轮提交动了 iface，包含 **D93 模型流式**与 **D96 模型会话**两个新契约。

修正后的口径：

- 以 **kernel repo 的 release tag + commit** 为唯一权威来源；
- hub 制品必须由该 tag 重新生成，并同时记录 **commit 与 digest** 两个坐标；
- 两者不一致时以 commit 为准，并提 issue；
- 本地快照（`packages/kernel-iface/`）只作消费方参考，不作为基线。

### 1.2 本地基线已同步（2026-10-29）

`packages/kernel-iface/` 已按 master `d950766` 逐字节同步：**22 个 trait / 44 个 `.rs` / 6292 行**（同步前是 10 个 trait / 27 个文件 / 2853 行）。

同步带来的两个变化需要注意：

- `kind` 从 `iface` 改为上游实际使用的 **`bundle`**（mint 没有 `iface` 这个 kind；`bundle` 要求 `skills/` 等形态字段之一，故每包附 `SKILL.md`）；
- 新增 `handoff`、`lease`、`view`、`trace`、`audit`、`event_io`、`loop_payload`、`interrupt`、`version`、`model_session`、`model_stream` 等模块。

**本地已新于线上**：在 hub 重发之前，线上 `0.1.0` 与本目录内容不等价。

### 1.3 治理规则

- 只有一份权威源码；
- 包按 SemVer 发版，`schema_version` 独立演进；
- 明确哪些变更算破坏性变更；
- 变更要经过评审；
- 提供 conformance fixture；
- 有弃用流程。

### 1.4 落地方式

- 每个契约在 RSI 仓库的 `contracts/proposed/<name>.v1.json` 放草案，另附 `CONTRACT.md`；
- 代码里用同形的 Python Protocol 实现，并在 `iface.toml` 记为 `proposes`；
- 被上游采纳后，只需改名或加别名；
- 若上游已有近似接口（C2、C6），先在 `consumes` 里声明消费，再决定是否 `proposes`。

### 1.5 写法约定

伪签名沿用 kernel-iface 的写法：返回 `BoxFuture<Result<_, Error>>`，错误类型为 `Error { category, code, message }`。
状态与结论**复用 `iface-types` 已有的 `RequestState` 和 `Verdict`（两者都含 `Unknown`）**，不另造名字。

## 2. 七个通用能力契约

### C1 `blob/v1`：内容寻址存储

**作用**：按 digest 存取不可变内容（原始轨迹、候选 Skill、索引文件、证据附件）。同样内容只存一份，可随时校验是否损坏。

**RSI 之外的消费者**：任何需要保存制品或附件的应用，比如会话附件、文档快照。

**需求要点**

- 同样的内容得到同样的 digest，`put` 天然幂等；
- 契约里不定义删除，垃圾回收是单独的维护操作；
- 跨进程传输时，二进制的编码方式必须写清楚；
- **canonical JSON 必须写死算法**：现实现是 Python `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)`，不是 RFC 8785。契约要逐条写明浮点数格式化、禁止 NaN 与 Infinity、Unicode 不转义；
- **digest 命名空间与 mint 分开**：本契约只用 `sha256:`，不占 mint 打包层的 `h1:`（dirhash），并明确不参与 mint 的包完整性校验。

**上游现状（2026-10-29 核实）**：没有任何“按 digest 存内容”的契约。相关但不解决的三处：`StoreContract.verify_checkpoint` 的 digest（只校验会话日志）、`mint-pack` 的 sha256 / dirhash（打包完整性）、hub 的 blob（平台内部）。

**判定**：**不满足**，自有 `rsi_foundation.content` 成立，优先级最低。

```rust
trait BlobContract {
    fn put(&self, bytes: Vec<u8>, media_type: Option<String>) -> BoxFuture<Result<Digest, Error>>;
    fn get(&self, digest: &Digest) -> BoxFuture<Result<Vec<u8>, Error>>;   // 不存在时返回 NotFound
    fn has(&self, digest: &Digest) -> BoxFuture<Result<bool, Error>>;
    fn verify(&self, digest: &Digest) -> BoxFuture<Result<bool, Error>>;
}
```

### C2 `index/v1`：不可变检索索引

**作用**：从固定版本的条目集合（bank）构建不可变索引，再按作用域与预算查询。同一快照、同一查询必须结果一致，召回才可复现。

**RSI 之外的消费者**：记忆召回、知识库。

**需求要点**

- 构建原子，失败的构建对外不可见；
- 结果带 `bank_hash` 与 `index_hash`；
- 作用域（project / target / task_family）严格过滤，不跨作用域泄漏；
- 每条命中带条目 revision hash；
- 不管“选哪些条目、怎么渲染进提示词”——那属于 RSI 领域逻辑（recall-selection）。

**上游现状（2026-10-29 核实）**：接口已经有了，但不是这个语义。

- `mint-api` 的 `MemoryProvider`：`store` / `recall` / `consolidate`，配 `MemoryQuery{text, scopes, k, kinds, exclude_session}`、`MemoryHit{score, item}`、`MemoryCaps{index, curate}`；
- 同名 WIT 接口 `memory.wit`（store / recall / consolidate / forget），说明它是可替换 provider；
- cpmrt 内置 `file-jsonl`，挂在 `before_model`（召回）、`turn_end`（写入）、`session_end`（整理）。

差距不在“有没有”，在**保不保真**：没有不可变快照与 `bank_hash`；`consolidate` 会在后台合并删除条目；没有 `budget{max_chars}`；没有 lexical / vector 的显式分型。

**判定**：**部分满足**。C2 存在的唯一理由是**可复现**，而这正是它没有的。

**落地策略**

- 沟通口径从“请给我一个新契约”改为“`MemoryProvider` 能否加一个只读快照维度：先 `snapshot(bank_rev)`，命中带条目 revision”；
- 若上游只要“活记忆”，保留自有 `index/v1`，并在 `iface.toml` 里把 `consumes`（memory provider）与 `proposes`（index/v1）分开写；
- **硬约束**：评测路径禁止直连可整理的 memory provider，必须走冻结快照，否则 baseline / candidate 对比会被后台 consolidate 污染。

```rust
trait IndexContract {
    fn build(&self, bank: BankRef /* id + revision_hash */, spec: IndexSpec /* lexical|vector + params */) -> BoxFuture<Result<IndexBuild, Error>>;
    fn snapshot(&self, build: &IndexBuildId) -> BoxFuture<Result<SnapshotRef, Error>>;
    fn query(&self, snap: &SnapshotRef, q: Query /* terms, scope, filters, budget{k,max_chars} */) -> BoxFuture<Result<QueryResult /* hits + snapshot hash */, Error>>;
}
```

### C3 `evaluation/v1`：评测器

**作用**：对“用例 + 输出 + 轨迹”打分，同时给出评测器身份与资格。baseline 与 candidate 的比较完全建立在它之上。

**RSI 之外的消费者**：benchmark、回归测试、A/B 实验、质检。

**需求要点**

- **`unscored` 与 `score = 0` 严格区分**：超时、缺数据、judge 失败都记 `unscored` 并写明原因，不得伪造分数；
- **指纹由显式稳定 ID 构成**：评测器 ID、版本、实现 digest、配置，以及 `capabilities` 标签；不能依赖语言层面的模块路径；
- 请求带 `data_use`（evaluation / calibration / audit），标为 forbidden 的数据直接拒绝；
- 用模型做 judge 时通过注入的 `iface-model` 端口调用，并支持取消。

**上游现状（2026-10-29 核实）**：`kernel/iface` 里 eval / score / benchmark / qualify 零命中。最接近的是 `PolicyContract.review` 的 `ReviewVerdict`（审核判决，不是分数）与 `AuditSink`（审计，不是评测）。

**判定**：**不满足**，自有 `rsi-evaluation` 成立。可引两条先例：`StepOutcome::Unknown` / `SessionState::Unknown` 证明了“显式未知”不是特例；`ContractDescriptor{name, version, capabilities}` 是“显式 ID + 版本 + 能力标签”的现成形状。

```rust
trait EvaluationContract {
    fn describe(&self) -> EvaluatorDescriptor;   // id, version, fingerprint, output_schema, uses_model
    fn evaluate(&self, req: EvalRequest /* case, output, trace_ref?, data_use */) -> BoxFuture<Result<EvalResult /* scored|unscored + reason */, Error>>;
    fn qualify(&self, calib: CalibrationSet) -> BoxFuture<Result<Qualification, Error>>;
}
```

### C4 `evidence/v1`：测量证据封装

**作用**：统一回答“这个数字是谁、在什么条件下、用什么测出来的”。内容包括观测方指纹、模型与端点（只含非敏感部分）、观测值、用途、原始引用与完整性哈希。审计、复现、发布审批都依赖它。

**RSI 之外的消费者**：用量与计费统计、合规审计、任何对外报告实验结果的应用。

**需求要点**

- 以数据契约为主，操作只有 `seal`、`verify`、`redact` 三个；
- **usage 与上游同构**：上游是 `{input_tokens, output_tokens, total_tokens}`，三个都是 Option，没有 `cached_tokens` / `cost`。我们照抄前三个字段名与可空性，`cached_tokens` / `cost` 标为 opt-in 扩展；`cost` 不进 v1 核心（价格表是外部事实）；
- **供应商未披露的模型变化标“无法检测”**：上游 `ModelResponse.model` 已有同一条规则（`None` = 不暴露，不得伪造），我们的字段对齐为 `observed_model`；
- 脱敏操作要同时返回脱敏报告。

**上游现状（2026-10-29 核实）**：`ModelUsage` 挂在 `ModelCompletion.usage`；`ModelResponse.model` 明确“服务端可能改写、实现不暴露时为 None、不得伪造”；脱敏只有 `Secret`（Debug / Display 打码），没有策略化 redact 与报告。

**判定**：**部分满足**。观测值与模型身份有承载，证据封装与脱敏没有。

```rust
trait EvidenceContract {
    fn seal(&self, ev: Evidence) -> BoxFuture<Result<Digest, Error>>;
    fn verify(&self, ev: &Evidence) -> BoxFuture<Result<bool, Error>>;
    fn redact(&self, payload: Value, policy: RedactPolicy) -> BoxFuture<Result<(Value, RedactionReport), Error>>;
}
```

### C5 `asset/v1`：版本化资产账本

**作用**：管理 Skill、Policy、Index、Bank 等资产的不可变版本，以及“当前激活的集合”。一组资产可一次性激活、整体回滚，所有变更绑定“期望的当前版本”与授权引用。它解决的是评审中指出的“`release_set` 不驱动召回”问题。

**RSI 之外的消费者**：任何需要管理提示词、技能或配置版本并发布的应用。

**需求要点**

- 发布分两步：`prepare` 提交意图，`commit` 原子切换指针；
- expected-current 的比较与写入在**同一事务**内，不能先查后写；
- `authorization_ref` 只能使用一次、有 TTL，并绑定 target、版本与哈希；
- 本契约不授予权限，授权来自 `iface-policy`；
- “宿主已加载”的回执与“账本已切换”的记录分开保存。

**上游现状（2026-10-29 核实）**

- `ExtensionContract`：`AssemblyIntent → AssemblyHandle → AssemblyState{Pending, Ready, Failed, RolledBack}` → `deactivate`，是“一次装配”的生命周期，**没有版本、没有激活集合、没有期望当前版本**；
- `mint.lock`：`LockPackage{name, version, source, integrity(h1:), cksum, deps, trust}`，是包管理器账本，只记“装了什么”，不记“哪套在生效”，且不属于 iface；
- `LeaseStore` 有租约与代次，但语义是“谁持有”，不是“哪套资产在激活”；
- `request_approval(ApprovalRequest{session, call, summary, timeout_ms})`：有超时，**没有一次性消费 / nonce 语义**。

**判定**：**不满足**。但两阶段的形状可借上游讲：`intent → handle → status`，且 `RolledBack` 这个状态名已经存在。
沟通时要把“一次性消费”与“等待超时”分开问，否则会被答“我们已经有 timeout 了”；`expected_current` 的原子比较可类比上游的 epoch fence。

```rust
trait AssetContract {
    fn put_version(&self, asset: AssetId, kind: String, content: Digest, schema_ref: String) -> BoxFuture<Result<VersionId, Error>>;
    fn read(&self, asset: &AssetId, at: VersionSel /* version | active */) -> BoxFuture<Result<AssetVersion, Error>>;
    fn prepare_release(&self, intent: ReleaseIntent /* set, expected_current, authorization_ref */) -> BoxFuture<Result<IntentId, Error>>;
    fn commit(&self, intent: &IntentId) -> BoxFuture<Result<ReleaseReceipt, Error>>;
    fn rollback(&self, to: SetId, expected_current: SetId, authorization_ref: String) -> BoxFuture<Result<ReleaseReceipt, Error>>;
    fn active(&self) -> BoxFuture<Result<SetSnapshot, Error>>;
}
```

### C6 `workspace-staging/v1`：工作区暂存

**作用**：执行前把冻结的资产安全写进一个全新的工作区，需要支持：创建目录；同目录内原子替换；路径围栏（禁止 `..`、绝对路径、symlink 逃逸）；按名称拒绝（如 `.git`、`.mint`）；声明自身具备哪些能力。

**RSI 之外的消费者**：任何需要把文件送进沙箱或远端环境执行的应用。

**需求要点**

- 先查能力，能力不足直接拒绝，不用多次 `write_file` 模拟原子替换；
- 暂存完成返回回执，列出每个条目的 digest，事后可校验。

**上游现状（2026-10-29 核实）**

- `FsBackend` 仍是 4 个方法：`read_file` / `write_file` / `list_dir` / `stat`；没有 mkdir、没有 rename / 原子替换、没有按名拒绝；
- `EnvironmentCapabilities` 仍是 4 个粗开关：`fs` / `exec` / `signals` / `streams`；
- **词法围栏已经有了**：`PathUri` 拒绝 `..`、控制字符、反斜杠，并做 `/` 折叠；实现层 `LocalFsBackend` 还用 `canonicalize` 逐级回溯祖先做 symlink 逃逸检查——但它不是原子替换。

**判定**：**不满足**，但形态要改：**不是新契约，是 `iface-env` 的增补**。三条支撑：

1. 上游已证明窄能力契约可接受：`ToolStaging` 只有 3 个同步方法，注释写明“只有装配器需要它，不该污染主契约”；
2. 上游有通用能力协商：`ContractDescriptor.capabilities` + `require_capabilities`（fail-closed），所以不要自定义 `StagingCaps`，改成能力标签 `env.fs.mkdir` / `env.fs.atomic-replace` / `env.fs.nofollow`；
3. 措辞要对准事实：应说“**词法围栏已有，缺的是 fs 层的 symlink nofollow 与原子替换契约化**”，否则会被答“已经有 PathUri 了”。

```rust
trait WorkspaceStaging {
    fn capabilities(&self) -> StagingCaps;   // atomic_replace, nofollow, mkdir, max_file_size
    fn create(&self, spec: WorkspaceSpec /* fresh = true */) -> BoxFuture<Result<WorkspaceRef, Error>>;
    fn stage(&self, ws: &WorkspaceRef, entries: Vec<Entry>, policy: StagePolicy) -> BoxFuture<Result<StageReceipt, Error>>;
    fn dispose(&self, ws: WorkspaceRef) -> BoxFuture<Result<(), Error>>;
}
```

### C7 `runtime-executor/v1`：隔离执行一次完整任务

**作用**：给定目标 Agent、工作区、冻结资产、模型与预算，完整跑一次任务，拿回结果与原始事件。RSI 的每一次 baseline / candidate 执行都走这里。当前实现是 MintHost 调 `mint run --json`；以后换 cpmrt，也只是替换这个契约的实现。

**RSI 之外的消费者**：评测平台、批量任务执行、Agent 回归测试。

**需求要点**

- `execution_id` 由调用方生成并作为幂等键：重复提交返回同一次执行，结果中的 id 必须与请求一致；
- **不做隐式重放**：提交后失联、又无法确认是否已终止的执行，返回 `Unknown`；
- `Completed` 只表示宿主执行结束，不等于业务成功；
- 取消必须有明确应答：已取消、本来就已结束、或未知；
- 原始事件存进 blob，结果里只放 digest 与事件数。

**上游现状（2026-10-29 核实）**

**上游没有 `runtime-executor`，也没有 `execution_id` 字段。** 检索范围：kernel 全仓工作区 grep、`git log --all -S`（跨全部分支）、`mint/` 全目录、cpmrt 0.1.14 二进制、hub `mint/core` 版本列表（最新仍是 0.1.14）——全部零命中；唯一命中是我们自己 `contracts/proposed/` 里的草案。

现在实际能用的三条执行面：

| 面 | 入口 | 有调用方 id | 取消应答 |
| --- | --- | --- | --- |
| headless run | `cpmrt run [--json] [--session]` | 没有，session id 由运行时生成 | 没有，只能杀进程 |
| ACP over stdio | `cpmrt acp`：`session/new` → `prompt` → `update` → `cancel` | 没有，session/new 服务端分配 | 只有 null 或 `-32602 会话不存在`，没有 already-terminal / unknown |
| Kernel L-C | `agentcpm-kernel`（不是 cpmrt） | 部分：`session.deliver` 必填 `idempotency_key` | 部分：`operation.cancel` 只支持 `kind="tool"`，其余返回 `-32085` |

最接近“执行身份”的两处先例，作用域都不对：

- `LoopContract` 的 `ExecutionIdentity{run_id, operation_id, idempotency_key, deadline_ms}`——作用域是**一次 step**；
- `ModelSession.InputEnvelope.client_message_id`——**调用方生成 id**，作用域是**一条模型输入**（幂等域 = 主体 + 会话 + 方法）。

**判定**：**部分满足（语义有、接口无）**。`RequestState`（含 `Unknown`）、`Unknown` 不重放、`operation.get` 统一作业视图、`idempotency_key` 强制、五类终止——这些语义件上游都有；只差“task 级 + 调用方给 id”这一层壳。

**两条落地路线**

- **路线 A（现在可用，不阻塞 M4）**：RSI 自带执行账本。我们生成 `execution_id` 并持久化到 `(进程, session_id, 起止时间)`；调 `cpmrt run --json` 或 ACP，把 id 写进自己的记录与事件；取消 = 终止子进程 + 状态标 `unknown`。代价是幂等只在本表级别，跨进程崩溃靠对账（正好对应 `Unknown` 语义）。
- **路线 B（M6，向上游提）**：① `--execution-id`（或 ACP `_meta.execution_id`）并在事件与结果中回显；② 取消三态 `cancelled / already-terminal / unknown`（对应 `InterruptOutcome` 加一个 `Unknown` 变体）；③ `run --json` 的 `EventRecord.v` 进 ABI 文档并给出版本兼容规则。

```rust
trait RuntimeExecutor {
    fn submit(&self, req: ExecRequest /* execution_id, target, workspace, assets, model, budget, approval_mode */) -> BoxFuture<Result<RequestState, Error>>;
    fn status(&self, id: &ExecutionId) -> BoxFuture<Result<RequestState, Error>>;
    fn cancel(&self, id: &ExecutionId) -> BoxFuture<Result<CancelAck, Error>>;
    fn result(&self, id: &ExecutionId) -> BoxFuture<Result<ExecResult /* same id, Verdict, events digest, usage, isolation */, Error>>;
}
```

## 3. 不做成契约的部分

- **storage-sqlite 的工作单元（UoW）**：同进程内的机制，不跨包暴露 SQL 连接；
- **schema loader**：只是工具函数；
- **model-client**：直接消费 `iface-model`，不另立契约；
- **recall-selection、经验账本**：属于 RSI 领域的调用契约，留在 RSI 命名空间。
