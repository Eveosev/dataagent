# 代码落地质检 rubric

## 1. 与 quality-audit v3.4 的关系

本卡是 `agentcpm/quality-audit-dev@0.5.0`（RUBRIC v3.4）的**二值加权改编版**，用于 Mint 能力包与 DataAgent 三层。三处沿用，两处偏离，都写明。

**沿用**

| 机制 | 做法 |
|-|-|
| 轴级事实 | 12 个代码轴（A1–A12，A7 为信息轴）+ 6 个落地轴（L1–L6），规则只判 0/1，附依据等级 |
| 硬规则非补偿 | 7 条硬规则只出 `green/red/unknown/na`，不参与加权；红了封顶 59 |
| 依据分级 | 每条规则标 A/B/C/D；D 级只作判断，必须在报告里可见 |
| unknown 不判绿 | 未测量记 `unknown`，按 0 计并封顶 89，不得 A |
| 可复现 | 输出带 `rubric_sha256`、`facts_ref` 与源码快照；改口径升版本、旧结论不重算 |

**偏离**

| 偏离 | 理由 |
|-|-|
| 给加权总分（reference 明确不给） | 本卡的总分**只用于同版本内排序与版本趋势**，不用于准入；准入只看 §5 的闸门与验收线。reference 的「不给总分」是为避免把加权分当合格线，本卡保留该禁令 |
| 增加 L1–L6 | reference 假设“包已存在且能编译”，不覆盖“能力语义是否成立”；DataAgent 的主要失效恰在这一层 |
| 增加缺陷与清单闸门 | 二值规则对“1 条 MUST 未做”和“全部未做”给同分；按版本验收需要逐条清单与按严重级封顶 |
| A4 用模块/函数规模代理 LCOM4 | Python 无字段级 LCOM4 的直接对应；降为 C 级依据 |
| A12 从 iface trait 改为契约包/vendored 副本 | DataAgent 不实现 Rust iface；契约旁路表现为三份 bundle 各复制一份 contracts/runtime |

## 2. 判定规则

1. **二值**：每条计分规则只取 `1`（通过）或 `0`（不通过）；部分满足记 `0`。
2. **依据分级**：A=标准原文；B=有实证的方向/数值；C=默认值或约定；D=纯判断。判定为 1 也要写依据等级，便于复核时知道这条有多硬。
3. **证据优先**：每条判定附 `file:line`、命令输出或探针输入/期望/实际；只引用文档自述不算证据。
4. **失败关闭**：未取证、未跑、未读到 = `0` 或 `unknown`，永不默认通过。
5. **粒度**：以包或层为单位逐包出分，不跨包平均；跨层规则同样按包判。
6. **预注册**：权重、阈值、门禁在评测前冻结；评测后改任一项必须升 `version` 并记录，旧结论不重算。
7. **无证据即未测量**：`score` 为 0/1 但 `evidence` 为空，按未测量计；硬规则灯无证据按 `unknown` 计。
8. **一致性**：硬规则与镜像规则矛盾、未关闭的 P0/P1 缺陷所关联的规则判 1、清单未完成而 L2.1 判 1，结果整体无效（评分脚本退出码 2，不出分）。

## 3. 评分

```
dim_score = 100 * Σ(weight × r) / Σ(weight)        # 维度内；weight=0 的 A7 只报事实
raw       = 100 * Σ(all weight × r) / Σ(all weight)
total     = min(raw, 所有触发的 gate.cap)
```

| 等级 | 分数 | 含义 |
|-|-|-|
| A | ≥90 | 可交付 |
| B | 80–89 | 可验收，附已知缺口 |
| C | 70–79 | 可演示 |
| D | 60–69 | 仅内部联调 |
| E | <60 | 不合格 |

验收条件：`total ≥ 80`，且无任何闸门触发（§5）。

## 5. 硬规则与封顶

硬规则只出灯，不参与加权；`unknown` 和 `na` 都不等于绿。

| ID | 规则 | 依据 | 失败 | 镜像规则 |
|-|-|-|-|-|
| R01 | 强制面不依赖实现包 | A | red | A2.1（red ⇒ 0） |
| R03 | 包级依赖图无环 | A | red | A2.2（等价） |
| D1 | 重复率 ≤3.0%（包内 + 同级包） | A | red | A1.1（等价） |
| V1 | 版本单一事实源 | A | red | A11.1（等价） |
| E1 | 错误码 registry 一致（无 registry 记 na） | A | red | A10.2（等价） |
| R13 | 破坏性变更升 major（无基线记 unknown） | A | unknown | — |
| R14 | 契约不被影子复制，vendored 必须有同步门禁 | A | red | A12.1 + A12.2（等价） |

| Gate | 触发 | 封顶 | 理由 |
|-|-|-|-|
| GATE-RED | 任一硬规则 red | 59 | 存在结构性违规，不得进入可验收区间 |
| GATE-P0 | 存在 open/partial 的 P0 缺陷 | 59 | 静默错误或门禁可绕过；P0 不可豁免 |
| GATE-P1 | 存在 open/partial 的 P1 缺陷（未有效豁免） | 79 | MUST 未满足 |
| GATE-CHECKLIST | 清单有 partial / not_done / 未判定条目 | 79 | 本版本方案未落地完 |
| GATE-UNKNOWN | 任一硬规则 unknown | 89 | 未测量不得给 A |
| GATE-UNMEASURED | 规则为 null、0/1 无证据、或 na 不在 profile 内 | 89 | 没有证据就不算通过 |
| GATE-NO-CHECKLIST | `checklist` 为 null | 89 | 未逐条核对方案 |
| GATE-NO-DEFECTS | `defects` 为 null | 89 | 未做缺陷核查；`[]` 表示已核查且无缺陷 |

封顶值只在 JSON 的 `gates` 中定义。`--self-test` 断言：red/P0 封顶 < D 级下限，P1/清单封顶 < 验收线，各类 unknown 封顶 < A 级下限；放宽任一封顶都会使自测变红。

### 5.1 缺陷

| 级 | 定义 |
|-|-|
| P0 | 错误结果以成功状态交付、落库或外发（静默错误）；安全/治理门禁可被调用方绕过；数据丢失或损坏；主链路不可用 |
| P1 | 方案 MUST 未满足但失败可见；需特定条件触发的并发/资源/超时缺陷；合法客户端按契约调用会失败 |
| P2 | 健壮性、可维护性、文档与代码不一致；不影响结果正确性与安全 |

每条缺陷必填 `id, severity, status, title, location(file:line), repro{input, expected, actual}`，可选 `rules`（关联规则）。状态：`open`；`partial`（按未修复计）；`fixed`（须有 `fix_evidence`，即复跑原复现的结果）；`waived`（须有 `waiver{by, date, reason}`，P0 不可豁免）。缺陷 id 跨轮固定。

### 5.2 方案清单

清单由 `plan_checklist.py` 从方案抽取，条目 id 为 `<章节号>#<文本哈希>`，跨轮稳定。每条判 `done`（须有证据）/ `partial` / `not_done` / `na`（非需求条目，须写理由）/ `waived`（须有 waiver）。未判定、或 done 无证据的条目按未完成计。

### 5.3 Profile

| Profile | 适用 | may_na |
|-|-|-|
| contracts | 契约/类型/schema 库，无 operation 入口 | A10.2、L1.*、L2.3、L2.5、L3.*、L4.*、L5.3 |
| runtime | 共享运行时，无业务 operation | A10.2、L1.*、L2.5、L3.5、L4.1 |
| capability | 暴露 operation 的能力包 | A10.2、L2.3、L2.5、L3.*、L4.* |
| service | 独立部署的服务 | 同 capability |

R13 在没有已发布基线的仓库里恒为 `unknown`，因此所有包最高只能到 B。这是有意的：**“可交付”需要证据链完整，缺基线就不是可交付状态**。

## 6. 取证与抽样

| 对象 | 要求 |
|-|-|
| 能力面（L1） | 全量，不抽样 |
| 重复率/复杂度（A1/A5） | 全仓扫描，报原始量 |
| 对抗形状（L2.2/L2.3） | 按 `skills/code-landing-quality/references/probes.md` 的类别，每层 ≥8 类，其中 ≥2 类本轮新构造 |
| 上一轮缺陷 | 全部重跑原复现；上一轮已修复的 P0/P1 全部重跑以查回归 |
| 路径/外发（L3.1/L3.3） | 每入口类型一次；外发三态各一次 |
| 资源/并发（L4） | 每层各一次压测 |
| 真实样本（L5.3） | 每条主链路 ≥1 个 |
| 文档（L6.2） | 随机 5 条可验证声称 |

判 `0` 要写“为什么不是 1”；判 `1` 要能给出复跑命令。判 `unknown` 要写“缺什么才能测”。

## 7. 示例

`example-governance.score.json` 是按 2.0 填写的治理层部分判定（证据来自 [三层评估](research/dataagent-2026-11-03/10-layer-assessment-2026-11-05.md)），按 §9 原样保留、不重算。用当前版本读取时需显式声明，结果只作展示，不能作为验收结论：

```console
$ python3 docs/standards/score_landing.py --result docs/standards/example-governance.score.json --partial --allow-version-mismatch
总分: 48.4 / 100    等级: E 不合格    结论: 不可验收    证据覆盖: 65.3%

| 闸门 | 封顶 | 触发项 |
|-|-|-|
| GATE-RED | 59 | R14 |
| GATE-NO-DEFECTS | 89 | defects=null |
| GATE-NO-CHECKLIST | 89 | checklist=null |
| GATE-UNKNOWN | 89 | D1, V1, R13 |
```

不带 `--allow-version-mismatch` 时，脚本以退出码 2 拒绝该结果。

自测与模板：

```bash
python3 docs/standards/score_landing.py --self-test       # 23 条断言：封顶不变量、各闸门、证据、矛盾、na、版本
python3 docs/standards/score_landing.py --template > /tmp/score.json
python3 docs/standards/score_landing.py --result /tmp/score.json --fail-under 80
```

填写、测量与验收流程见 `skills/code-landing-quality/`（`SKILL.md`、`references/tester.md`）。改脚本或改 rubric 后先跑自测。

## 9. 复现与版本

- 每份结果带 `rubric_sha256` 与 `facts_ref`；引用结论时两者都要带，否则不可复核。
- 本卡 `version` 变更规则：改任一权重、阈值、门禁、unknown 语义 → 升 minor；改维度集合或计分公式 → 升 major；旧结果原样保留，不重算。
- rubric 的 JSON 是唯一事实源，Markdown 是它的说明；两者不一致时以 JSON 为准并立即修 Markdown。
- `skills/code-landing-quality/references/rubric.json` 与 `scripts/score_landing.py` 是本目录两个文件的逐字节副本；`quality_run.py` 报告漂移，skill 测试在漂移时失败。改动时两处同步。
- 结果文件声明 `rubric_version`；与当前 rubric 不一致时评分脚本拒绝出分。
- 自测（`--self-test`）是对“验收被放松”的机械检查：如果把封顶改大、把 missing 改成不扣分、让无证据判定计分，自测必须变红。

## 10. 已知限制

- 权重是判断（D 级），不是实证；跨版本不可比。
- A5 的 CC 阈值来自 SIG 的 Java/C 标定，移植到 Python 属 B 级；A4 的模块规模阈值是 C 级。
- L2 的“规格逐条落地”依赖设计文档本身可执行；文档含糊时只能判 unknown。
- 硬规则的 `unknown` 封顶 89 会让缺基线的仓库长期停在 B；这是刻意保守，不是缺陷。
- A1.1/D1 为全量口径（含存量重复），5 行窗口、忽略空行/注释/纯标点行；仓库无 git 基线，无法区分新旧代码。
- radon 未安装时，A5 用 `quality_run.py` 的 AST 实现，计数规则与 radon 一致（2026-11-05 在五个 dataagent 包 670 个函数上与 radon 6.0.1 逐个一致）。
- 严重级的判定仍是人工判断；拿不准时就高登记，并写明降级条件。
- 本卡不替代人工复核：工具通过 ≠ 语义正确 ≠ 允许发布。
