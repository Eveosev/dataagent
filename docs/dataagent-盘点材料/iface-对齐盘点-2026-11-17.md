## 1 结论摘要

1. **工具效果分级（PR-1 / B1）是 P1 唯一会卡验收的契约缺口，应先问方向。** iface 已有三级副作用词表 `EffectLevel`（只读 / 推进 / 副作用，`IF/session/effect.rs:193`），但它按 op 类别给值，`tool.execute` 一律是副作用（`IF/session/effect.rs:256`），`ToolSpec` 仍只有名字、描述、参数（`IF/tool.rs:35-39`）。问李鹏越、李奕杉：PR-1 能否直接复用 `EffectLevel`，作为 `ToolSpec` 的可选字段；不另造新枚举。
2. **新出现的 `scheduler_protocol`（Kernel 内建调度器的 7 个契约）是 B3 后台长任务最接近的现成形状，要尽早对齐，不要自建另一套。** 它有执行状态机（含 `NeedsHuman`、`Unknown`）、等人介入 `Wait`、取消控制、带期望修订的状态读写、幂等键、截止时间，还有带主体的 `InputOrigin`（`IF/scheduler_protocol/model.rs:31`、`:139`、`:234`、`:287`；`record.rs:75`；`contract.rs:50`）。但它绑定在会话上，会话关闭就取消执行树（`kernel/docs/scheduler.md:34`），也没有定时触发，满足不了 P5「关闭会话后任务继续」。问 pengyue.li：P5 的持续接入是挂在 Scheduler 上，还是另起后台任务契约。
3. **主体与租户（B7 / PR-8）的契约字段其实已经有了，只是停在会话层。** `SessionIdentity` 带 `principal`、`tenant_id`（`IF/session/identity.rs:37`、`:41`），Scheduler 的 `CallContext` 也带主体和安全引用（`IF/scheduler_protocol/model.rs:356-366`）。01 §6 B7 说的「`CallMeta` 加主体、租户」可以改问：能否把会话身份投影给 MCP 组件，而不是改 `CallMeta`（`IF/types/mod.rs:7-11`，没有 `#[non_exhaustive]`，加字段属破坏性变更）。
4. **调用元数据（PR-2 / A1）契约不变，DataAgent 这边先把读取形状对齐。** iface 规定 `CallMeta{session_id, call_id, turn}`；DataAgent 的 MCP 服务读的是 `_meta.context` 或 `request_id/scope_ref/authorization_ref`（`DA/dataagent-runtime/src/dataagent_runtime/interfaces/mcp_server.py:79-85`），工作台的 MCP 服务完全不读 `_meta`。R1 的 `resolve_context()` 应按 iface 字段名读，否则宿主开放后还要再改一次。
5. **凭据（PR-3 / B2）的契约面没有变化，要问的是「进程级注入」放在哪一层。** `SecretPurpose` 只有出网认证、状态加密两个用途域（`IF/policy/secret.rs:137-158`），值不出宿主；01 的 Q1 已拍「拉起 MCP 进程时注入明文」，这与 `SecretBrokerContract` 的「值不出宿主」相反（`IF/policy/secret.rs:161`）。问李鹏越：是新增第三个用途域（如「组件进程环境」），还是只在 Mint 实现层做、不进契约。
6. **基线漂移小，但 R0 要钉的版本已变。** 33075118 → ae6c3d5 契约轴 0.1.9 → 0.1.11，身份包 `iface/session` 0.1.14 → 0.1.15、`iface/store` 0.1.3 → 0.1.4、`iface/model` 0.1.4 → 0.1.5；01、03、07 的 iface 行号都仍成立（变动文件不在被引用之列）。
7. **该找的人比分工表集中。** iface 近期提交几乎都来自 pengyue.li（`lipengyue@modelbest.cn`，即李鹏越，122 次）和 luyaxi（49 次，对应谁待确认）；分工表上的 tool 负责人李奕杉（推测是 Kaguya-19 / `liyishanthu`）只有 1 次提交。建议按分工表找负责人拍方向，同时拉 pengyue.li 或 luyaxi 评审契约形状。

## 7. 补充核实（2026-11-17，agent-kernel@ae6c3d5）

### 7.1 Scheduler 能否让 MCP / Python 组件注册成后台服务

结论：**现在不能**。MCP 组件没有接入方式；Python 只在满足条件时可行，而且生产环境的接线本身是断的。

1. **生产接线断开。** 装配入口链是 `--components-config` → `startup/scheduler::install` → `Server::install_components`。模块头注明「生产组合根接线当前断线」，代码按 `dead_code` 留档，只有测试在用（`kernel/host/src/transport/scheduler.rs:4-8`，`kernel/host/src/startup/scheduler.rs:12-13`）。
2. **只支持 native 一种实现。** 装配文件的组件实现只有 `native { program, args, sha256 }`（`kernel/host/src/transport/scheduler.rs:50-51`）。程序路径必须是绝对路径，按 sha256 校验；协议是 stdio NDJSON 的 `agentcpm-scheduler/1`，双向，不是 MCP 的 JSON-RPC。装配在 Kernel 启动时冻结，运行中不能增加绑定。
3. **Python 的限制：**
   - 只能把 venv 里的 python 解释器当作 `program`，sha256 校验的是解释器而不是脚本；
   - 子进程启动时 `env_clear()`（`kernel/core/src/scheduler/adapters/native.rs:60`），环境变量全被清掉，PYTHONPATH 和凭据都不会传进去；
   - 协议的 SDK 只有 Rust 版，Python 要自己实现 NDJSON 帧格式和反向调用。
4. **Mint 包声明不了。** Mint 包的 `provides` 只有 api、interfaces、loops、mcp_servers、protocols、tools、uia，没有 scheduler 服务（从 mint 0.1.31 二进制的字符串核实）。
5. **关会话就取消。** 即使能注册，会话一关闭，执行树就被取消（`kernel/docs/scheduler.md:34`），满足不了 P5 的「关会话后继续」。

建议：

- P1 维持工作台自己的任务队列加分段续跑，任务状态按 Scheduler 的状态机命名（见第 5 节）。
- 向 Kernel 提的需求（P3 前）：
  1. 恢复生产接线；
  2. 增加 `mcp` 或 `command` 实现，能把 MCP 工具或已有命令通道桥接成 Capability 或 Service；
  3. Mint 清单增加 `provides.scheduler_bindings`；
  4. 环境变量白名单，以及对脚本本身的校验；
  5. 不跟随会话生命周期的执行，以及定时触发。

### 7.2 后台任务的结果能否用「系统通知」推回会话

结论：**契约里有通知类别，但组件没有可用的推送通道**。

1. 收件箱契约有 `InboxKind::SystemNote`，注释是「内核/工具写入，按 turn 交付」（`kernel/iface/src/session/inbox.rs:51-60`）。但契约边界明确说「注入真实模型输入、hook/MCP 入口」不在范围内（同文件头注释）。
2. 宿主有 `session.deliver`（`kernel/host/src/transport/session_deliver.rs:4-23`）：带幂等键的跨 loop 投递，进入收件箱时算普通消息或插话，并自动派一个 loop 作业，也就是会触发一次模型回合。打包版 GUI 的内核配置允许这个方法（`allow_ops`）。但它要求调用方持有 Kernel 连接并通过会话授权；DataAgent 的 MCP 组件只响应工具调用，拿不到这条连接。
3. 待确认：MCP 的服务端通知（如 `notifications/message`）会不会被 cpmrt 转成会话消息。
