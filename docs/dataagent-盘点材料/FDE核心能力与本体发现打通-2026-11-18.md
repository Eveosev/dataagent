## 1 第一性原理：FDE 在做什么

FDE（前置部署工程师）到一个新客户，要把**客户散落、异构的数据和没写下来的业务知识**，变成一个**可信、可用、可维护的业务模型**，让人和 Agent 能在上面查询、核对、执行，而且**不为每个客户写定制代码**。

拆开看只有一个闭环，六个环节，缺一个就不能独立交付：

| # | 环节 | 要回答的问题 | 不可替代的原因 |
|---|---|---|---|
| C1 | 接入与观察 | 客户有哪些数据、长什么样、能不能安全地读 | 没有观察就没有证据；只读、有界、带覆盖与缺口 |
| C2 | **建模（本体发现）** | 客户的业务里有哪些对象、怎么识别同一个对象、有哪些属性、关系和规则 | **通用性的来源**：本体写死，换一个领域就要开发者手写，无法推广 |
| C3 | 映射与对齐 | 每个来源的字段对应模型的什么、怎么换算、多来源同一对象怎么合并 | 模型和数据之间的桥；冲突不能静默 |
| C4 | 人机校验 | 每个值从哪来、错了怎么改、改动作用到哪个范围、脏数据怎么处置 | 客户只信能追溯、能纠正、能审计的结果 |
| C5 | 使用 | 建好的模型怎么被查询、被规则检查、交给下游 | **价值的出口**：没有使用，前面全是成本 |
| C6 | 维护与复用 | 下周同样的数据能不能直接用、结构变了怎么办、模型怎么演进 | 决定是一次性项目还是可持续交付 |

贯穿六个环节的三个约束：**安全**（凭据、出网、最小权限、审批、审计）、**成本与时延**（每轮步数、token、单次调用时限）、**可度量**（每个环节有评测，09-benchmark）。

关键判断：

1. **C2 是通用性的枢纽**。C1、C3、C4 都是领域无关的机制；只有本体决定「这是采购单还是报销规则」。本体只能手写，产品就只能做一个领域。
2. **C5 是闭环的出口**。没有按本体查询或按规则核对，用户看不到为什么要建模。
3. 准确率可以后补，**链路必须先通**：发现 → 审核 → 发布 → 映射 → 校验 → 使用，在一个非采购的新领域上走通一次。

## 3 打通本体发现的最小链路（D 线）

目标场景（验收）：一份合成的「差旅报销标准」docx（含条款段落和标准表）+ 一份「差旅报销明细」xlsx，**不预置任何本体**：

1. Agent 探查两份材料，产出发现证据；
2. Agent 提出本体草案（如「费用标准」：城市等级、职级、费用类型、限额、币种、条款引用；「报销明细」：单号、日期、城市、费用类型、金额），带证据；
3. 用户在工作台确认草案 → **发布为新本体 `expense-policy@1`**；
4. 两份材料映射到新本体，生成实例，每个值可追溯；
5. 用户能按本体查询（如「列出一线城市住宿标准」「列出金额超过标准的报销行」的前一半：按条件列实例）；
6. 再用 3 份令才真实制度原件跑一遍发现→发布→映射，只看能不能走通、覆盖与缺口，不判对错。

| 卡 | 内容 | 主要文件 | 依赖 |
|---|---|---|---|

## 6 codex 审后修订（2026-11-18，review-20261118-154410-sroa）

### 6.1 闭环补充

1. C0 入口：先明确客户目标、可访问范围和验收标准，再进入 C1。
2. C5 拆成两层：M1 交付「只读查询」；环境动作发现、受控执行与回执属于 operations 主线（`design/14-ontology-workbench-plan.md:338`），不在 D 线。

### 6.2 契约决策：一个领域本体包含多个概念（派工方裁定）

依据第一性原理：同一领域的对象之间有关系（如「报销明细」引用「费用标准」），关系的两端必须在同一个模型里，所以选「一个领域本体 = 多个概念」，不选「多个单实体定义拼一组」。这也是 06 PRD G2.1（多概念本体）的方向。

1. `OntologyRevision` 增加 `concepts`（每个概念：实体类型、属性及值类型、必需性、身份字段）与 `relations`（端点概念、方向、角色）；只有 `entity_type` 的旧定义视为单概念，读取兼容。
2. 映射目标从「全局定义」改为 `(ontology_id, revision, concept)`，固定在任务（session）上；一个映射提案把一个来源绑定到一个概念；`materialize` 按概念生成实例。去掉 `intake_service.py:534/850/970`、`tool_schema.py` 等处对全局 `wb.definition` 的依赖。
3. 实例之间的关系：M1 只在定义层登记关系，实例级关系事实留到 P2（G2.4）。
4. 顺带：问题（issue）带 `source_id` 与 `entity_id`，供网页准确跳转（F7 遗留）。
