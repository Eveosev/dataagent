# 最小 MVP 推进计划（2026-11-18，已按 codex 审核修订）

payne 11-18：进度要更快，按最小 MVP 推进。dsh、zcode 写代码，codex 审，Claude Code 监督与规划；MVP 完成后由一个 FDE 角色的子 agent 用截图和本地服务挑使用与功能问题，改到问题最小。

## 1. 最小 MVP 的定义

用户在 Mint（TUI 为主）里装好 preset-intake 后，能：

1. 接入 8 类本地文件（含扫描 PDF，用本机 OCR）、SQLite、带 token 的 REST；
2. 跨源对齐同一对象，冲突不静默覆盖；
3. 在工作台网页上看对象、纠正值或映射，回到对话保存；
4. 单次工具调用不超过宿主 60 秒，长探查分段续跑；同结构二次接入复用映射；
5. 凭据只按逻辑名注入，不进对话、日志、结果；doctor 能指出缺什么。

验收证据：安装产物上的 verify_local（files、sources）、verify_browser e2e、一份 TUI 证据包（T50），再加 FDE 子 agent 审核报告。

## 1.1 真实数据（payne 11-18 补充）

令才线上导出 `$LINGCAI_POLICY_DATA`（只读，不进仓库，报告只写聚合数）：18 份制度原件（14 份 docx、4 份 pdf）、45 个解析目录（规则、QL 规则、前置条件、条款、待澄清问题的 JSON）、15 个规则库版本。没有真值，也不含审核报文。

用法：

1. 真实输入冒烟：用 18 份原件和解析 JSON 走一遍 MVP 接入流程，只看能不能接、覆盖率、缺口、单次耗时，不判对错。脚本放 `$PRIVATE_DIR`，不进仓库。
2. FDE 子 agent 审核用它当真实场景。
3. 同一原件的多个解析版本可以做「无真值的跨版本对齐」观察，补 B16 的业务数据缺口时再用。

发现的缺口：原件大多是 Word（docx），8 类文件里没有 docx。新增 T26（Word 文本接入）进 M1。

## 1.2 边界与风险（codex 审后补）

1. M1 是单独里程碑，不等于原 P1 验收完成；T54 只记「M1 合入」，原 P1 退出条件（G1.10、G1.12、G1.13、G1.15 等）照旧待补。
2. M1 只验采购场景：工作台仍固定加载采购本体（`bootstrap.py:35`），T16 暂缓意味着不支持通用领域加载。
3. 已知风险（T24 暂缓）：没有白名单时，推断请求会带样本值和 PDF 摘录（`inference_requests.py:8-24`）。用令才真实数据冒烟时要知道这一点。
4. 暂缓的还有 T11b（R1 其余调用点）；GUI（T51）结论取决于 T02，不能只用 provider_unsupported 概括。
