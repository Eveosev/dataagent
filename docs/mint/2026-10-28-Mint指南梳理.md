# Mint 指南梳理（2026-10-28，core 0.1.14）

> 对象：<https://mint.ea.modelbest.co/guide.html>
> 对照仓库：`/Users/payne/Vibe/AgentOS/packages/agent-kernel`（HEAD `5035bfe`，2026-10-28）
> 对照线上：MintHub `https://mint-hub.ea.modelbest.co`（2026-10-28 19:20 实测）

## 0. 先给结论

1. **架构口径是对的，版本口径全部过期。** 指南的分层（AgentOS / cpmrt / AgentCPM kernel / Mint）与九节点图现在仍然成立，但它自称"截至 2026-10-26"，写的是 core 0.1.9、CLI 0.1.10、GUI 0.1.6、Agent 0.1.6；线上已经是 **core 0.1.14、CLI 0.1.11、GUI 0.1.9、Agent 0.1.8**。仓库里 0.1.12 之后还有一整套能力（多会话、steer、语义压缩、记忆、子 Agent 权限、no step cap），指南一个字没写。
2. **线上站点就是仓库里那几个字节，但要靠重发镜像才生效。** `curl` 下来的 `guide.html` 与 `mint/site/guide.html` md5 完全一致（`290ccc40…`），首页同理（`5e4fa3fc…`）——站点不是另建的 CMS。但 `mint/hub/server/src/site.rs` 是用 `rust-embed` 把 `mint/site/` 编进 `mint-hub` 二进制的，所以改文案后必须**重建 hub 镜像并发布**；它也不随 core/GUI 的 release 自动更新。这就是文档为什么总慢一拍的机制原因（不是有人忘了，而是它有自己的发布节奏）。
3. **运行时拆出来了，但"批次"没有。** `cpmrt` 已经是规范二进制名（双 `[[bin]]`，同一份 `entry()`），Phase 1–3 已落地；Phase 4（`agentos.lock` 发行批次）没开始。结果是：`mint/core` 已 stable 0.1.14，而官方成品 `mint/agent-gui` 还停在 0.1.8、冻结的是 core 0.1.12。**你装到哪一个 core，取决于你走的是"组件路径"还是"成品路径"**——这就是"首页已经有新 runtime，但指南还写 0.1.9"的根因。

## 1. 指南在讲什么

正文只有五段加一张图，信息密度不高但边界写得很克制（大量"不宣称""不达标"），值得逐段读。

### 1.1 定位段（第 1 自然段）

> 运行时 cpmrt（旧名 mint-core）在本机跑 Agent。MintHub 保存版本制品；CLI 负责验签、安装与组装，GUI/TUI 通过 stdio ACP 连接 cpmrt。模型、工具、权限、工作区与会话由 cpmrt 管理，JS 插件在独立 V8 Host 执行。

一句话把四个角色分完了：

| 角色 | 干什么 | 不干什么 |
|---|---|---|
| MintHub | 存版本制品、索引、签名 | 不执行 |
| CLI（`mint`） | 验签、安装、组装（解析 + 锁） | 不做 loop、不持会话 |
| GUI / TUI | ACP 客户端，只通过协议说话 | 不直接碰文件/模型 |
| cpmrt | 会话、loop、模型、工具、审批、工作区 | 不知道自己怎么被装上 |
| V8 Host（`mint-host`） | 只执行 JS，副作用回 cpmrt | 不能靠自报声明提权 |

第二句"bootstrap 清单在 MintHub，不是产品站的 self 路径"是个容易被忽略的运维细节：首页那条 `curl install.sh` 只是脚本，真正的版本清单在 `https://mint-hub.ea.modelbest.co/self/bootstrap-stable.toml`。实测该文件现在写 `version = "0.1.11"`、`gui_version = "0.1.8"`。

### 1.4 更新与修复段

讲了三件容易踩坑的事，都值得保留：

- **升级 = 重跑安装**，不需要卸载、不需要清理；先退出 App。
- **`--repair` 只在元数据/锁漂移时用**，必须先验证 App、收据、工作区身份三者匹配，只重建受管理元数据，不动用户文件、模型配置、会话。不能与 `--locked` / `--frozen` 组合。
- **`--yes` 的语义边界**：只同意替换 CLI/入口/收据，**不透传**给 GUI 的能力或信任确认。

这三点在代码里都有对应实现（`mint/bins/mint/src/cmd/app_install/upgrade_workspace.rs` 的 `repair` 分支、`mint/install.sh:697` 的"Never pass bootstrap --yes to the CLI"）。

### 1.5 限制段——最诚实的一段，也是最需要重算的一段

原文：std 压缩制品约 25 MB，strip 后 Host 约 54 MB、未压缩 runtime 约 65 MB，仍超 50 MB 预算；没有原生 TS、code mode 或通用 JS 文件/exec/tool.execute；只保证 macOS M 系列。

- 体积：原文的"约 25 MB"对应 `0.1.9` 实测 24,900,003 B；`0.1.12` 25.1 MB；**`0.1.14` 是 30,053,210 B（≈28.7 MiB）**；0.1.13 未 strip 是 34.2 MB。数字必须重算。
- "strip 后 Host 约 54 MB、未压缩 runtime 约 65 MB"：仓库里**找不到这两个量测**。`xtask` 的 size-budget 只量 `core < 6 MiB` / `tui < 8 MiB`（`mint/tools/xtask/src/main.rs:9`），"std < 50 MB 含 mint-host"的预算写在 `mint/docs/eng/E1-Rust内核与扩展-b.md:152`。所以这句话属于"当时手工量的、没有留证"。
- 能力边界（无原生 TS / 无 code mode / 无 tool.execute）目前仍成立：`capabilities.rs:246-251` 有显式的 `code_mode_not_implemented`。
- 平台：仍只有 `aarch64-apple-darwin` 一个 target。

## 4. 主线：cpmrt 是怎么从包管理器里拆出来的

这条线是理解整个仓库的钥匙，指南只有一句话（"旧名 mint-core，只在历史兼容语境出现"），实际过程记录在 `mint/docs/prd/2026-10-27-cpmrt-runtime-prd.md` 与 `mint/docs/roadmap/2026-10-27-feedback-and-agentcpm-runtime.md`。

### 4.1 问题：五条用户反馈里有三条是同一个病

原文的三条硬证据：

1. `mint/bins/mint/src/cmd/start.rs:17-19` 把官方组件白名单写死在启动路径（`RELEASED = ["mint/core","mint/tui","mint/gui","mint/agent-gui"]`）——组件一改名，启动就坏。`core`→`std` 档位改名那次故障（请求 `core-aarch64` 制品 404）就是它。
2. `mint-core` 不依赖任何 `agentcpm-*` 包，kernel 侧的 loop 宿主（`kernel/host/src/transport/loop_runner.rs`）从来没被交付的运行时用过。
3. `provides.loops = ["graph"]` 被解析后落进 `Provides.other`，无校验、不显示、无消费。

**判据**：包提供 `next()`，运行时提供 `while`。loop / tool / skill 可以无限包化，但总得有一个不被包化的 `while`——否则包 A 由包 B 拉起、B 由 C 拉起，谁给第一个进程发工具调用、谁批准第一个 `rm -rf`？

七件不可外包的不变量（今天都在 `mint-core` 里）：装载谁、会话/上下文/预算、判停、工具执行与审批、插件进程监管、对外协议（ACP）、状态与恢复。

### 4.2 命名：为什么是 `cpmrt`

- 过渡名 `mintrt` 从未对外发布，2026-10-28 全仓替换为 `cpmrt`，不留兼容名。
- 否决 `agentcpm`：这名字已被 `kernel/cli` 的安装器二进制占用，且是模型/机制品牌。
- 否决"mint 让给运行时"：要改全部命令、`mint.toml`/`mint.lock`/`~/.mint`、官方 scope、域名证书，而信任记录按绝对路径记账（`config.rs:605-607`），换目录会集体失效。
- 使用规则：品牌层做减法（用户只记 AgentOS + Mint），边界层做加法（mint / cpmrt / kernel 各司其职）。**cpmrt 不是用户敲的名字**，就像没人手敲 `containerd`。

### 4.3 落地：Phase 1–3 已完成，Phase 4 未开始

| Phase 1 | 产出 `cpmrt` 二进制（同一 `entry()`，双 `[[bin]]`） | ✅ | `mint/bins/mint-core/Cargo.toml:11-17`、`src/lib.rs:26` `RUNTIME_BIN_NAMES = ["cpmrt","mint-core"]` |

| Phase 3 | mint 瘦身：`start/chat/gui/serve` 的实现迁到 cpmrt，`mint start` 退化为"缺就装、有就 exec"的转发壳；打包只打 `bin/cpmrt` | ✅ | `mint-manifest/src/layout.rs` 的 `CORE_BINS` 同时接受旧名 |

注意 Phase 3 的一个**残留**：`mint/bins/mint/src/cmd/start.rs` 里 `RELEASED` 白名单还在。也就是说"包管理器不该知道怎么跑 Agent"这条原则只走了一半——改名炸启动的根因还在，只是现在被"按实际发布档位选"的解析逻辑兜住了。

### 4.4 三档同一运行时

`core` / `lite` / `std` 只差 JS 宿主，同一份源码按 feature 构建：

```toml
default = ["flavor-core"]
flavor-core = ["mcp"]
flavor-std  = ["flavor-core", "js-host", "computer-use"]
```

`mint-core` 版本史在制品上能直接看出来：0.1.0–0.1.6 打的是 `core-aarch64`（约 5 MB），0.1.7 起改打 `std-aarch64`（约 25 MB）。**首页"现在发行 core 档，std 档在 V1、lite 在 V2"这句话已经过期**——现在发行的就是 std 档，`core` 只是 feature 名与历史档位名。

## 5. mint 与 iface 的仓库边界

一个仓库两条线，2026-10-26 的 `7acca7a refactor: split kernel/ from mint/` 把它们从代码上分开，但仍在同一个 workspace。

```
packages/agent-kernel/
├── mint/                     ← 装与发（用户敲的那一半）
│   ├── bins/mint              CLI 二进制 `mint`
│   ├── bins/mint-core         运行时二进制 `cpmrt`（+ 兼容名 `mint-core`）
│   ├── bins/mint-host         V8 Host，只执行 JS
│   ├── crates/                mint-manifest（清单/布局）、mint-pack（打包）、
│   │                          mint-api、mint-protocol（ACP/错误码/dirs）、
│   │                          mint-core（引擎本体）、mint-acp-client、
│   │                          mint-provider-local、mint-wasm-host、mint-tck、mint-i18n
│   ├── hub/server             MintHub 服务端，一个二进制 `mint-hub serve`（SQLite + 本地盘）
│   ├── hub/web                控制台 SPA
│   ├── site/                  产品站源码（index.html / guide.html / diagrams / tests）
│   ├── packages/              官方包：core、preset-*、skill-*、plugin-*、theme-*、provider-*

│   └── docs/                  PRD / roadmap / eng / 规范 / 品牌

│   ├── cli/                   `agentcpm` 安装器（装/升级/回滚/体检，别和运行时混）
```

**依赖方向是单向的**：`mint` 不依赖任何 `agentcpm-*`，`kernel` 不依赖 `mint`（workspace 里 kernel 13 个成员 + mint 21 个成员 = 34 个，`Cargo.toml:3-43`）。这条边界由这些门禁守着：

| 保障 | 文件 | 实测（本次只读跑过） |
|---|---|---|
| L-A API 冻结 | `ci/check-iface-api.sh` + `kernel/iface/api-baseline.txt` | strict；破坏性变更 exit 1；实测 `fail=0 warn=179` |
| 契约源唯一 + iface 零反向依赖 | `ci/check-contract-source.sh --strict` | R2 直接断言 `iface/Cargo.toml` 的 `[dependencies]` 为空；五项全 `[ok]` |
| 可替换性（换实现不改调用方） | `ci/check-replaceability.sh --strict` + `replaceability-allowlist.toml` | 豁免已清零到 0 条；实测 `fail=0 warn=0 info=5` |
| 分发件不分叉 | `scripts/sync-iface-packages.sh --check` | 逐字节比对 + 覆盖完整性；实测 `total=53 mapped=44 allowlist=9 uncovered=0` |
| 错误码单一分配 | `kernel/error-registry.toml` + `ci/check-error-codes.sh` | 禁段 / 登记 / 全局唯一 |
| 规范阈值 | `ci/check-conventions.sh` | 文件 >800 行 FAIL、`lib.rs` >300 行 FAIL |
| 单一入口 | `ci/check.sh` | fmt → clippy → test → xtask → kernel 门禁 → GUI，无 warn-only 步骤 |

`kernel/CONTRACT-MAP.md` 是这套东西的索引：42 条机制（M01–M42）× 7 族，每族写清"判决点落在哪个 iface、实现落在哪个包、当前状态"。它明确写了两件事——**"Mint 的 approval 是产品内规则"**（不算 kernel 授权面）、**"现有资产都不是 kernel 本体"**（Mint 包管理器、Mint Agent Core、参考实现都在这一栏）。

### 5.1 iface 是怎么"进到" Mint 里的

这是"mint 与 iface 同仓"最容易被误解的一点。**iface 不是 Mint 的一部分，而是被 Mint 当作包分发出去的契约**：

| 环节 | 事实 | 证据 |
|---|---|---|
| 权威源 | 契约只在 `kernel/iface/src/` 定义 | `kernel/CONTRACT-MAP.md` §2 |
| 分发形态 | `packages/iface-*/src/` 是 `kernel/iface/src/` 的 **verbatim 复制**，无 `Cargo.toml`、无 `lib.rs`、无测试，**也不是 workspace 成员** | 各包 README"分发形态：Mint 扁平分发" |
| 同步方式 | `scripts/sync-iface-packages.sh` 逐字拷贝，`--check` 只管"有没有分叉"，不管"契约好不好" | `scripts/publish-iface-mint-hub.sh` 负责发布 |
| 包形态 | Hub 上是 `agentcpm/iface-{types,session,loop,tool,policy,model,store,env,context,extension}`，`kind = bundle`（Hub 还没有 `kind=iface`，见 D-I2），带 `schema.json` | `packages/iface-*/mint.toml:3` |
| 消费者 | `mint iface list|show|verify` 只读本地单元库，校验清单 / schema / src 一致，失败退出码 `VERIFY_FAILED`；`--remote` 在 MVP 里明确拒绝 | `mint/bins/mint/src/cmd/iface_cmd.rs` |

十个契约包各自的形状与**真实消费方**：

| 包 | 定义什么 | 被谁真正用 |
|---|---|---|
| `iface-types` | 共享类型：SessionId/TurnId/Cursor/Error/Handshake/KernelRequest/Interrupt* 三元组/版本协商（1786 行，其余九包的基座） | 其余 9 包 + `host/src/startup/{contract_check,kernel}.rs` + cli + core |
| `iface-session` | 创建/推进/恢复/归档 + 推进权与围栏（lease）+ 跨 loop 交接（handoff，1571 行） | host(3)、runtime(4) |
| `iface-model` | ModelRequest/Response + `ModelProbe` + `ModelStreamContract` + `model_session`(D96)（934 行） | runtime(12)、host(6) |
| `iface-policy` | 委派 / 出网 / 审批 / 审核位置 / 审计（808 行）；**方法名是 `check`/`check_egress`/`check_delegation`**，不是 README 里写的 `authorize*` | core(4)、runtime(12)、host(14) |
| `iface-store` | `StoreContract`(async) + `EventIo`(sync)，只追加事实源 | runtime(9)、host(11)、core(8)、三个投影/压缩包 |
| `iface-tool` | ToolSpec / ToolCall / ToolResult（74 行，最小的一个） | runtime(6)、host(4)、wasm-host(2) |
| `iface-env` | `FsBackend` + `ExecBackend`：Environment / PathUri / ExecRequest / Signal | runtime(3/3)、host(2/6) |
| `iface-context` | `ContextContract` + `TraceSink`（先写后执行）+ ContextSnapshot | runtime(4)、context-assembly(3)、host(4) |
| `iface-extension` | `ExtensionContract` + AssemblyIntent/AssemblyState | runtime(4)、host(2) |
| `iface-loop` | `LoopContract` / `LoopDescriptor` / `StepOutcome`（5 值，无 Idle） | **内核 0 引用**（见下） |

### 5.2 三个必须知道的"契约真相"

1. **`iface-loop` 目前是死契约。** grep 全仓，`LoopContract` 只在 iface 自身出现；**内核里没有任何实现或调用**。真正跑的 loop 在 `mint/crates/mint-core/src/loop_host.rs`，它跟 kernel 只是"语义对齐"，并不 link。所以"包提供 next()、运行时提供 while"这个 PRD 主张，**在 cpmrt 里是靠自家 `loop_host` 兑现的，不是靠 iface-loop**。这条记在 `mint/docs/contract/2026-10-28-cpmrt-iface-defects.md` 的 D-I1。
2. **`cpmrt` 对 iface 零依赖。** 契约包是"发出去给未来替换用的"，今天的运行时并不消费它们；`mint-protocol` 里甚至用 `ContractDomain` 枚举（`:20-45`）复刻了十个域名——同一份语义存在两套类型宇宙（D-C12 自认）。理解这一点，才能理解为什么"契约冻结"和"运行时能跑"现在是两件事。
3. **门禁能拦破坏性变更，拦不住加法漂移。** `kernel/iface/src/lib.rs:9` 还写着"19 个公开 trait"，实测 **22 个**；`api-baseline.txt` 只登记 20 个 / 737 行；门禁跑出 `warn=179` 但 `fail=0`。也就是说：删改签名会被拦，新增接口只会告警——**契约在"只增不改"的方向上是在缓慢漂移的**。

另外三个诚实的缺口（都在文档里，不是猜测）：

- **"kernel 不得依赖 mint"没有自动门禁。** 只有 `Cargo.toml:2` 的注释与 code review；`xtask check-deps` 只管 mint 侧分层。
- **`ci/README.md:43-44` 说"仓库内不存在任何 CI 配置文件"**，但 `.github/workflows/e2e.yml` 存在（2026-10-26 引入），它只跑 mint e2e 与 hub 集成测试，**不跑 `ci/check.sh`、不跑 kernel 门禁**——所以"远端已阻断 L-A 回归"目前不成立。
- **`[requires]` 表达不了 interface 级依赖**（D-I3/D-I4），跨包依赖写在 `schema.json` 的 `contract_deps` 且没有门禁；10 个 `schema.json` 也都不是真 JSON Schema（D-I7）。

一句话概括三者的关系：**kernel 定义"话怎么说"，cpmrt 决定"话在哪说、谁批准"，mint 只管"把话术包送到位"——而今天这三件事是靠三个互不 link 的实现各自兑现的。**
