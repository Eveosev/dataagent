# cpmrt 拆分后的文档口径审计（2026-10-28）

> 触发：本地升级到 core 0.1.14 后，发现「Mint 运行时」这一层在文档里仍然被写成 Mint 的一部分，
> 而代码已经拆成四层。本文回答：**到底哪些文档写错了、错在哪一层、该按什么策略改。**

## 0 结论

1. **错的主要不是句子，是分层模型。** 旧 PRD 把「L1 内核 Agent Core」当成 Mint 六层结构里的一层
   （`mint/docs/00-总览-a.md:88`），把包管理器放在「横切」。cpmrt 拆分后这是反的：
   运行时是独立产品层，Mint 只剩解析/验签/锁/安装/发布。
2. **「在 Mint CLI 跑」这条要求本身没错，错的是它的含义。** 作为**验收入口**它至今成立
   （`mint start`/`run`/`chat` 都只是转发 + exec）；作为**架构归属**它已经不成立
   （`mint/bins/mint/Cargo.toml:12`：「mint 不依赖 mint-core / mint-api」，源码 `use mint_core` 零命中）。
3. **最该修的不是 67 份历史 PRD，而是 9 份「半迁移」文档和 6 处用户可见文案。**
   半迁移（同文件里既有 `cpmrt` 又有 `Mint 内核`）比纯旧口径更危险：读者无法判断哪句是现行事实。

## 1 两套模型对照

| | 旧模型（PRD 00–15） | 现在的模型（代码事实） |
|---|---|---|
| 顶层 | Mint = Agent 组装系统 | **AgentOS** = 发布批次 |
| 运行时 | Mint 六层里的 L1「内核 Agent Core」 | **cpmrt** 独立产品层，`mint/bins/mint-core` 产出 |
| 契约 | `mint-api` / `mint-protocol` 属于内核 | **AgentCPM kernel**（`kernel/iface`）独立一层 |
| 包管理 | 六层里的「横切」 | **Mint / MintHub** 自身就是一层（解析/验签/锁/装/发布） |
| 谁跑 Agent | 隐含是 Mint 的一部分 | **只有 cpmrt**；mint 只 exec |

判据只有一条：**谁持有 loop、会话、工具执行、审批。** 答案永远是 cpmrt，不是 mint，不是 CLI，也不是 kernel。

### 3.4 替换时必须区分的三种「旧名出现」

改文档最容易误伤的地方——`mint-core` 在仓库里有三种用法，只有第二种该改：

| 用法 | 例子 | 处置 |
|---|---|---|
| **真实路径/标识** | `mint/crates/mint-core/src/engine.rs:148`、`mint/bins/mint-core`、Hub 上的包名 `mint/core` | **不改**，目录和包名没有跟着二进制改名 |
| **概念称谓** | 「Mint 内核」「Agent Core」「mint-core 是 Mint 的一部分」 | 改成 `cpmrt`（运行时） |
| **历史说明** | 「旧名 `mint-core`」「运行时 cpmrt（旧名 mint-core）」 | **保留**，这是兼容语境，站点已有断言保护 |

`kernel/docs/notes/` 下的 8 份是**带日期的调研快照**（如 `kernel-entity-grounding.md:149`
「不能将 Mint Agent Core 直接认作目标 Kernel」——这条判断今天依然正确），只需加 banner，
不要按新名词机械替换，否则会把「当时的核实结论」改造成「伪造的当下事实」。

## 5 机制：把口径变成闸门

站点已经有术语断言（`mint/site/tests/site.test.cjs:343` 禁止 `Agent Core 本体|三档同一内核`），但文档侧没有任何检查，所以才会出现「commit 说全量同步、实际只同步一半」。建议：

1. `ci/check-docs-terms.sh`：对 `mint/docs/*.md`、`kernel/docs/*.md`、`mint/book/*.md` 里**非 banner 文档**禁止出现 `Agent Core`、`Mint 内核`、`mint-core`（作为「旧名」出现的例外需同行带 `旧名` 字样）。
2. `mint/docs/README.md` 顶部加一节「当前分层（唯一事实源）」，四行：AgentOS / cpmrt / kernel / Mint。
3. 发布脚本把「`<bin> info` 的编译档位必须等于 `--flavor`」也纳入校验——同一个 commit 里既有「文档全量同步」的宣称，也有「std 制品按 core 编译」的事实，说明这条链缺的正是断言而不是人。

## 6 一句话

**旧文档没有写错「怎么用」，只是写错了「谁在做」。** 把它当成一次产品分层变更的迁移债务：
用户可见文案（T1）本周清完，历史文档（T3）加 banner 冻结，中间那 9 份半迁移（T4）优先收口。
