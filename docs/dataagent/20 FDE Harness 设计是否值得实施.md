# 20 FDE Harness 设计是否值得实施

**建议只投入一轮对照试点。当前证据不足以支持按整份 PRD 排期。** 多源接入一直是 FDE Harness 的验收目标。已有 DataAgent 可以处理多源冲突、保留缺口、复用已核映射，还能在部分外部操作丢失回执后恢复。新设计最值得验证的价值，是让经办人在熟悉的宿主里看见正确的证据、只回答会改变结果的问题，并在换人或中断后接得下去。试点要允许得出“现有 Skill 加已有工具就够了”的结论。

[第 19 篇](19-DataAgent现状与FDE-Harness选路.md)讨论项目归属。本篇判断新增软件是否值得做。团队即使决定单列项目，以下接口和收益仍需验证。

## 2. 对照真实接口后的判断

以下 DataAgent 路径相对 `packages/capabilities/`，基线为 `e75b086a`。新提案指宿主 `projects/fdeharness/` 的本地工作稿，PRD 与架构的 SHA-256 前缀分别为 `9348ecf88d41`、`f861bb61df29`。

| 新设计 | 历史接口与实质差异 | 实施判断 |
|---|---|---|
| 四类材料导入、能力发现 | PRD 第 84、117 行仅导入 HAR（网络请求记录）、Playwright 浏览器轨迹、DDL（数据库结构）和 API 文档。**HAR 是多源输入支持的文件格式之一。** 请求与响应元数据可用于了解系统操作，已保留的响应正文也可能直接提供业务记录。现有 `SourceSelection` 可指定实际业务来源，`SourceProfile` 还能区分全量、抽样、部分和未知，保留来源修订、未读分区及定位。见 `dataagent-contracts/src/dataagent_contracts/intake.py:21`、同文件第 47 行。 | **应补齐从现场问题到业务数据的路径。** 指导经办人取得缺失的观测材料也是 Harness 的职责。草案写明了导入、遮罩与分析，仍需用样例验明：已有 HAR 能提取哪些记录，其范围是否足以交付，以及何时需要补采或连接在线接口。 |
| 单一 Skill、证据摘要和业务／工程两种视图 | 旧 `WorkSpec` 已含目标、验收条件与授权引用。Workbench 已有精简摘要和按来源取明细。新方案补充了面向经办人的展示、问题样例，以及回答后继续原任务的要求。见 `dataagent-contracts/src/dataagent_contracts/intake.py:11`、`dataagent-workbench/src/dataagent_workbench/service_tools.py:234`。 | **值得验证。** 在同一个冲突样例上，尝试让经办人从结果查到原文，仅修正受影响记录。若旧工具缺少准确定位，先修原工具。若仍反复问同一问题，再验证跨轮保存是否有增益。 |
| 通用工作流与受控执行 | 新架构第 262 行用显式边、风险和批准描述业务图。现有 `WorkflowSpec` 执行按类型区分的步骤，有独立的等待、转换、核验语义。`ActionRecord` 单独记录业务键、参数摘要及派发状态。见 `dataagent-contracts/src/dataagent_contracts/workflow.py:55`、同文件第 84、152 行。 | **保留业务图作为候选表示，推迟冻结第二套执行契约。** 先拿一条含等待、回读、部分生效的流程验证转换。未知结果和未完成的步骤必须能回到原运行号，旧网关继续持有派发和回执。 |
| 决定、批准、目标回读 | 新方案把业务确认、执行批准和实际生效分开，这对跨宿主有价值。现有 Operations 已用业务键回读，新宿主仍需证明可把当前人的决定与具体动作和对象绑定。`agent-kernel@2fcc72f55d786d6ac0d13892a02a3b47c2005f11` 已有 `kernel/iface/src/policy/human.rs:174` 的人工决定通道，`policy/receipt.rs:6` 区分事后回执和事前凭据。DataAgent 的业务后态检查见 `dataagent-operations/src/dataagent_operations/reconciliation.py:33`。 | **保留三种事实各自的来源。** 验证首个宿主能否提供可信的动作级确认，同时用目标系统证明业务结果。Kernel 有契约不代表该宿主已经接通。缺可信确认时，首轮仍可完成只读接入与人工交付。 |
| 资产库、召回、漂移与运维 | 旧 `VersionedRepository` 已提供按修订取值、条件写入及按摘要查找。新 `AssetStore` 增加环境过滤、停用后抑制旧版召回、全文检索、迁移和退役，覆盖跨任务、跨现场的问题。见 `dataagent-runtime/src/dataagent_runtime/ports/versioned.py:9`、新架构第 399、414 行。 | **按交接需求增设。** 同会话首单先复用原有引用。有明确换人复办需要时，先验证新材料与旧规则的适用范围，再决定是否建设通用检索和迁移。对真实材料的访问和保留要求随试点范围生效。 |
| 静态页面 A、本地工作台 B | A 允许离线批量核对，回答经文件导入。B 将判断结果直接写回，需要引入临时本地服务并修订 D02。旧 Workbench 已有针对数据映射的逐项核对。 | **按经办成本选入口。** 少量冲突先在会话里处理，多项冲突先与既有 Workbench 对照。只有当数据显示打开、导入或反复切换造成实际漏项和返工，才值得为相应场景加入 A 或 B。 |

**以分页为例。** 经办人要上月的订单，手里已有一份脱敏 HAR。若归档保留了查询响应正文，可以从中提取订单，逐条关联到对应请求，并核对日期、页数、总数与重复记录。经核对覆盖整月，就能用这份文件完成委托。若只有两页，就交代已取得的记录和缺少的范围，再按需要补页或走获准的在线接口。若正文缺失，请求参数仍可能说明分页方式，此时业务记录的数量和内容应标为未知。现场还没有 HAR 且确实需要时，Skill 再指导经办人查询、翻页并导出。自动录制的投入另按采集频次、失败和成本判断。

还有两个接口细节影响可行性。第一，旧 Operations 的工具回包会携带运行状态、续办引用和恢复条件，新 HostPort 的必填响应表列出结果状态，缺少同等明确的续办字段。适配时应规定这些字段如何传回，避免一次“待核验”变成新建一笔工作。第二，主线由 Python 模型生成 JSON Schema，新方案把 JSON Schema 设为权威源。两条生成链应约定每类对象由谁维护，并用同一份调用样例验证升级兼容。见 `dataagent-operations/src/dataagent_operations/mcp.py:121`、`dataagent-contracts/scripts/generate_schema.py:81`、新架构第 326、405–414 行。

## 4. 怎样决定继续还是停止

1. **对照要给旧方案同样的工具。** A 组用现有宿主、FDE Skill 和 DataAgent 工具。B 组用相同宿主、模型、权限和输入，只增加候选的证据展示、冲突澄清与续办。分别开新会话，固定样本和预期结果，交错运行顺序，记录工具调用、重复询问、人工纠错和经办人实际用时。给两组相同的脱敏 HAR 样例，分别核对正文完整、只含部分页和正文缺失时的提取结果及覆盖说明。另设一个两组开场都没有 HAR 的分页任务，比较能否用已有信息解决、确需采集时能否一次取得足够材料，以及最后读到的记录是否一致。两组都可用同一浏览器导出。当前尚无这些比较数据。
2. **先用多源接入检验基本价值。** 用既有文件、SQLite、分页 REST 样例，包含 4 个冲突对象。两组均须保留来源及缺键记录，按经办人的选择保存 6 个无问题对象，并在再次接入时复用已确认的映射。漏掉冲突、错存对象或无法回溯来源，直接判该路径失败。若两组结果相同且 B 在新样例上没有可重复的收益，保留原工具与 Skill，停止新增通用层。
3. **按实际委托验证交接与写回。** 对“以后替我办”，换经办人、输入版本和新会话，观察旧做法能否在规则变化时停下。对确有写回的委托，在可重置沙箱模拟回执丢失，以目标端业务键、记录数和状态判定。原通道已能恢复时，新层要证明改善了经办人定位或接管，而不能把既有恢复测试计为自己的收益。
4. **扩围以证据为条件。** 首个场景的结果至少达到原验收要求，并在未见样例重复观察到少返工、少等待或更可靠的交接，再投入第二个不同业务场景。完整资产库、双轨 ERP、第二宿主和工作台各自对应实际需求与成本。现有材料支持做这次比较，对全量实施的净收益仍无法估算。
