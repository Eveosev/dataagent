# 21 FDE Harness 多源输入与工作记录设计

**工作记录在逻辑上独立于宿主 Agent 的会话 Store，底层存储可以共用。** 宿主负责对话和推理。Harness 约定一次委托怎样留下目标、证据、决定和未决问题。经办人隔天打开新会话，凭工作编号和自己的权限，就应能看出哪些结论已有依据、哪些仍需核实。

多源接入仍按同一目标验收。一份材料能支撑什么结论，取决于它实际包含什么，以及经办人要完成什么。[现状与项目归属](19-DataAgent现状与FDE-Harness选路.md) · [历史接口评审与试点条件](<20 FDE Harness 设计是否值得实施.md>)

## 1. 谁判断输入属于哪一层

| 判断 | 负责人 | 订单接入示例 |
|---|---|---|
| 材料怎样形成，能直接读到什么 | 格式适配器解析内容，返回来源、范围、可定位的观测及读取限制 | 一次 HTTP 交换是一条观测。HAR（HTTP Archive，网络请求归档）可以汇集多条交换。若其中一条响应保留了订单正文，该条目也可以是业务数据来源。 |
| 对当前目标意味着什么，还缺什么 | 宿主 Agent 对照目标提出解释，写明所依赖的证据和待核之处 | 用户要上月全部订单。分页响应能证明读到过这一页。报表是否齐全，还需核对日期窗口、分页和总数。 |
| 哪些结论可采信 | 工具核验可重复检查的事实，业务负责人确认只有现场能定义的口径 | 数据库查询日志显示此次访问用到的字段。表定义、类型和约束应从有权限的目录或 DDL（数据定义语言）导出核对。仅凭样本推测的关联仍标为候选。 |

一份材料可以同时含单次观测、汇集记录和结构声明。适配器按可定位的片段报告，工作记录允许一个来源承担多种用途。用户已经有 HAR 就直接接入；缺少请求样本时，Harness 可指导其在授权范围内导出所需操作窗口的脱敏 HAR。若缺的是全量订单，应优先请求能核对覆盖范围的导出或数据接口。

## 2. 一项工作怎样留记录

跨会话继续、需要交接或要回查交付依据时，为这次委托分配稳定的 `work_id`。同一项工作可跨多个会话，一个会话也可处理多项工作。一次性问答可留在会话里。发生外部动作时，执行器始终按自身约定保存回执。

| 记录项 | 写入内容 |
|---|---|
| 标识与目标 | `work_id`、记录修订号 `revision`、委托目标和可观察的验收条件。项目与租户范围由宿主可信身份取得。 |
| 证据与解释 | 为条目分配稳定 ID，保存原件引用、来源版本或采集时间、条目位置、实际观测及覆盖限制。推断单列，引用支持它的证据 ID。 |
| 决定 | 记录决定内容、决定人、可复核的确认来源和适用范围。口径被修订时保留前后关系，据此找出受影响的结论。 |
| 未决问题 | 记下缺口、影响的验收项和可选的核实办法。宿主在恢复时依据最新材料选择下一步。 |
| 关联产物和动作 | 只存必要的固定版本、运行号、动作号或回执引用。受控原件、工具结果和执行记录由各自的来源维护。 |

例如 `orders-nov` 的目标是交付上月订单明细。证据 E1 指到脱敏 HAR 的第 4 个请求，记录“此响应返回 20 行，后续页未知”。决定 D1 指到业务负责人确认的“按支付时间归月”。未决问题 Q1 是“是否覆盖全部已支付订单”。这三条允许接手人保留已确认口径，并对照 Q1 找缺失数据。

## 3. 何时写，怎样恢复

1. **写入。** 出现新证据、确认或修订口径、识别影响验收的缺口、取得动作回执引用时，宿主提出有来源的变更。Harness 校验权限、结构、引用和修订号，保存后返回新修订。会话消息由宿主管理。
2. **恢复。** 经授权的宿主调用 `load(work_id)`，读取目标、验收项、证据、决定和未决问题。宿主检查本次要用的引用与权限。原件无法访问时标明待核，必要时向有权限的经办人补取材料。
3. **补采或换源。** 经办人改传 CSV 时，将它作为新来源 E2。用 E2 核对日期与分页缺口，保留仍适用的 D1。若新文件只含创建时间，支付时间口径仍有效，该文件能否满足口径则重新列为未决。已确认且与换源无关的事项无需再问。
4. **处理副作用。** 若记录指向某次提交，但结果未知，按原运行号和动作号向执行器查回执，必要时回读目标系统。只有本次权限与执行前提满足，才能发起后续动作。交接摘要不能充当批准。

界面可从工作记录展示“探查中”“待确认”等进度。每个动作检查自己的前提，宿主据此决定先读材料、先提问还是直接交付。受控写入的派发、未知结果回查等局部状态继续由执行器维护。

## 4. 两个读写接口，三处责任边界

| 接口 | 契约 |
|---|---|
| `load(work_id)` | 在调用者获准的范围内返回该项工作最新的完整记录及修订号。会话销毁后仍能按编号读取已持久化的工作。 |
| `save(work_id, expected_revision, changes)` | 首次保存须原子地验证记录尚不存在。更新时校验读到的修订号，同一修订上的两次并发更新只能有一次成功。落盘后返回新修订号。冲突方重读并核对本次变更是否仍成立；结果未知时先查本次条目及来源，再决定是否补写。 |

- **宿主 Store** 保存消息、会话上下文与工具交互。只有在能跨会话按工作编号寻址、持久保留、落实项目权限并提供原子条件写入时，才可作为工作记录的后端。记录中的原件引用仍按原系统权限读取。
- **Harness 工作记录** 拥有一次委托的数据结构和读写语义。每项工作选择一个权威后端。可选的 `Checkpoint` 从指定修订生成供展示或恢复的摘要。缓存损坏时从工作记录重建。
- **资产库与执行器** 分别维护经验证可供其他任务复用的资产，以及动作派发、核验和回执。工作记录按 ID 和版本引用。跨任务复用时另行判断适用范围。

## 5. 积木选择

| 已有积木 | 拟采用方式与缺口 |
|---|---|
| DataAgent `VersionedRepository`，代码基线 `f1c9b01b` | 优先试用 `current/get/save` 和 SQLite 的条件更新。工作记录适配层负责范围授权、应用变更、首次创建的原子保护。现有 SQLite 在 `expected_revision=None` 时跳过比较，直接传空值无法保证只创建一次。见 `packages/capabilities/dataagent-runtime/src/dataagent_runtime/ports/versioned.py:9`、`adapters/sqlite.py:99`、`adapters/sqlite.py:125`（后二者相对同一包的 `src/dataagent_runtime/`）。 |
| 宿主 `iface/store` 0.1.5、`agentcpm/store` 0.1.1（MintHub 候选） | Store 契约按会话和游标读写。若选宿主后端，须为每项工作提供独立可寻址的记录流，核验授权、保留期及所有写入者的原子追加能力。普通会话的游标同时包含聊天消息，不能直接当作工作修订号。契约默认关闭原子追加能力，内存后端仅存活于当前实例。基线 `agent-kernel@2fcc72f55d786d6ac0d13892a02a3b47c2005f11`，`kernel/iface/src/store.rs:127`、第 134、144、177 行。 |
| DataAgent Operations，代码基线 `f1c9b01b` | 沿用现有运行与动作台账，按原键关联并查回执。见 `packages/capabilities/dataagent-operations/src/dataagent_operations/store.py:127`、同文件第 139、169 行。 |

## 6. 试点验收

| 场景 | 可观察的通过条件 |
|---|---|
| 换会话、换经办人 | 关闭原会话。另一位获授权经办人仅凭工作编号，可说清目标、已确认口径和待补证据，并能回到获准访问的证据位置。未获授权的身份不能读取该项工作。 |
| 换来源 | 先导入只有一页响应的 HAR，再补 CSV。记录保留两个来源，能指出哪些结论得到补证、哪些仍有缺口，并保留适用的原决定。 |
| 并发与重试 | 两个会话从相同修订写入，后提交者收到冲突。重读并合并后两条有效变更都在。两个客户端并发首次建同一编号只会有一个创建成功。 |
| 动作结果未知 | 在外部操作已发出、工作记录尚未更新时中断。接手者用原动作号回查，核验后补记结果引用，执行器中只有一次原动作。 |
| 一次性问答 | 只解释一份材料且无需交接时，宿主可直接答复。回答不依赖建立持久工作记录。 |

以上为方案的试点判据。实施投入仍按第 20 篇与现有 Skill、工具进行同案对照。
