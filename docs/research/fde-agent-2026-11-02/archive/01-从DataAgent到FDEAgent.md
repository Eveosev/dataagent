# 从 DataAgent 到 FDE Agent：概念校准与差距分析

> 前置阅读：[00-FDE调研.md](00-FDE调研.md)、飞书《Pluggable DataAgent》（快照见 [sources/00-feishu-dataagent-modules.md](sources/00-feishu-dataagent-modules.md)）
> 本文只做两件事：**把概念对齐**，**把差距量化**。模块清单见 [02-新增模块清单.md](02-新增模块清单.md)

---

## 1. 概念校准：三种智能体的真实关系

现在的表述里混了三个不同层次的东西，先拆开：

| 概念 | 工作对象 | 动作空间 | 交付单位 | 结束条件 |
|---|---|---|---|---|
| **狭义 DataAgent** | 给定的库 + 语义 | 只读查询/计算 | 一次问答 | 答案给出 |
| **广义 DataAgent（现文档的 General DataAgent）** | 来源数据（无库） | 只读 + 建库写入 | 一套可复用的数据/语义资产 | 资产发布并可持续运行 |
| **FDE Agent** | 客户的整个工作环境 | 读 + 提议 + 受控执行 | 一个可验收的业务结果 + 客户能运营的系统 | 客户接管（交接完成） |

**关系不是替代，是包含：**

```
FDE Agent
├── 广义 DataAgent（环境中的"数据子空间"：建库、建语义、持续运行）
│   └── 狭义 DataAgent（环境中的"一次问数"：问题 → 答案）
└── 非数据域（OS / SaaS 写操作 / 工单流转 / 审批 / 交付物）
```

所以用户的直觉是对的，但需要补一句更准确的话：

> **广义 DataAgent 不是「更像」FDE Agent，而是 FDE Agent 在「只读 + 数据语义」子空间上的一个特化投影。**
> 反过来说：只要一个系统的工作对象不限于数据、动作不限于只读、交付不限于报告，它就是 FDE Agent。

这个判断有一个直接后果：**DA 的 14 个模块里，大部分不是「被替换」，而是「被泛化」**——它们的边界定义需要重写，内核可以保留。第 6 节给映射表。

## 2. 「类数据库资源」到底"类"在哪

用户的核心洞察是：OS、文档目录、SaaS、代码仓……都可以是输入数据。这句话要能用，必须说清楚「类」的是什么。我把它拆成 9 条性质——**一条资源只要满足前 6 条，就可以当数据源用；满足全部 9 条，才可以当 FDE 的工作对象。**

| # | 性质 | 含义 | DataAgent 是否已覆盖 |
|---|---|---|---|
| R1 | **可寻址** | 有稳定标识（路径、URI、主键、对象 ID） | 部分（表/文件） |
| R2 | **可枚举** | 能列出集合与容量 | 部分 |
| R3 | **有结构** | 有 schema / 目录树 / 字段表 / 键 | 部分（不含 OS、Web） |
| R4 | **有语义** | 名字背后有业务含义，需要映射 | ✅ 已覆盖（DA03） |
| R5 | **有权限** | 谁能读、在什么条件下写 | 弱（只有访问控制） |
| R6 | **有时效** | 随时间变化，有新鲜度承诺 | ✅ 已覆盖（DA01.6.3 / DA14.2） |
| R7 | **有动作面** | 除读之外，可写、可执行、可触发 | ❌ **缺失** |
| R8 | **有副作用与可逆性** | 动作的影响范围、能否回滚 | ❌ **缺失** |
| R9 | **有证据与审计** | 动作留下可追溯记录 | ❌ **缺失** |

**结论：现有 DA 体系把 R1–R6 做得很细，但 R7–R9 是空白。** 这正好对应「数据源」与「工作环境」的差别，也正是 FDE Agent 需要新建的那一层。

### 2.1 资源类型矩阵（FA01 需要抽象的东西）

把「表 / schema / 记录 / 读 / 写」这五个概念投影到不同资源上，就能看出为什么不能只做「数据库连接器」：

| 资源类型 | 相当于「表」 | 相当于「schema」 | 相当于「记录」 | 读动作 | 写动作 |
|---|---|---|---|---|---|
| 关系库 | table / view | 列、类型、键 | row | SELECT | INSERT / UPDATE / DELETE |
| 数据仓库 | 主题表 | 星型模型 | 分区/行 | 查询 | 物化写入 |
| 文件目录 | 目录 | 命名规范、扩展名、模板 | file | list / read | create / move / rename / delete |
| OS | 进程、服务、包、配置单元 | unit 文件、参数、依赖 | instance | status / log / ps | start / stop / config / install |
| SaaS（Jira、Slack、CRM…） | 对象类型 | 字段、状态机 | record | GET | POST / PATCH / 状态流转 |
| Web / 浏览器 | 页面 | DOM、表单、导航图 | 页面元素 / 条目 | navigate / extract | fill / click / submit |
| 代码仓 | repo | 模块、接口、依赖 | commit / PR | grep / read / diff | commit / push / merge |
| 消息与工单 | 队列 / 频道 | 字段、标签、SLA | message / ticket | list / get | send / reply / close / assign |
| 设备 / 传感器 | 设备类型 | 点位表、量程 | 采样点 | 读值 / 状态 | 下发指令 |
| MCP Server | tool 集合 | inputSchema | tool call | tools/call（只读） | tools/call（有副作用） |

**这张表是 FA01 的设计输入。** 注意最后一行：MCP 把「读」和「写」混在同一个 `tools/call` 里，这正是第 3 节要说的问题。

## 3. 分水岭：动作面，以及「三档动作」

SQL 之所以让 DataAgent 变得可治理，是因为它同时给了四样东西：**声明式、有 schema、默认只读、可回滚（事务）**。

OS / SaaS / Web 没有这些。它们给了你一堆 `exec()` 或 `POST`，**能做什么和允许做什么被混在一起**。

所以从 DataAgent 到 FDE Agent，最关键的一次抽象不是「支持更多数据源」，而是**把动作分成三档，并给每档配上不同的治理强度**：

| 档位 | 语义 | 治理要求 | 失败代价 |
|---|---|---|---|
| **A0 读** | 观察，不改变世界 | 授权范围 + 脱敏 + 审计 | 信息泄露 |
| **A1 提议** | 生成结构化变更，但不落地 | 证据充分性 + 影响面预估 + 可回滚性检查 | 误导决策 |
| **A2 执行** | 真正写入 / 触发 / 通知 | 身份委托 + 策略校验 + 审批（或明确豁免）+ 后置校验 + 补偿计划 | 不可逆损害 |

**判断规则：任何不能被表达为 A0/A1/A2 之一的能力，都不应该进入能力目录。** 这条规则会强迫我们把「一个能 SSH 的 shell」拆成「读日志」「改配置（A1 提案）」「重启服务（A2）」三个动作——而这正是可治理性的来源。

配套要引入一个类比于 SQL 的核心资产：**动作契约（Action Contract）**。它至少包含：

```yaml
action: jira.issue.transition
tier: A2                      # A0 / A1 / A2
params:                       # 有 schema 的参数
  issue_key: {type: string, required: true}
  target_status: {type: enum, values: [Done, Blocked]}
preconditions:                # 执行前必须成立
  - issue.assignee == actor.delegate_of
  - current_status in allowed_from[target_status]
authority:                    # 谁有权执行
  requires: [delegation:project_lead, approval:if(pii)]
impact:                       # 影响面预估
  blast_radius: single_issue
  reversible: true
  inverse: jira.issue.transition   # 反向动作
postconditions:               # 执行后必须成立，否则视为失败
  - issue.status == target_status
evidence:                     # 必须留存的证据
  - policy_ref, approver_id, request_trace_id
```

这个结构不是凭空设计的——Palantir 的 Action Type 已经把这套东西产品化了（参数、提交条件、副作用、读写授权、撤销/回退、Action Log、分支动作），可以作为参考基线。

## 4. 六个维度的差异（这张表决定了哪些模块要重写）

| 维度 | 狭义 DataAgent | 广义 DataAgent | **FDE Agent** | 对模块的影响 |
|---|---|---|---|---|
| **工作对象** | 库 + 语义库 | 来源数据 | 环境（数据 + 系统 + 流程 + 人 + 制度） | DA01 要扩成资源/环境接入 |
| **动作空间** | 只读查询 | 只读 + 建库写 | 读 / 提议 / 执行 / 触发 | DA06/DA07 要重构成计划+网关 |
| **时间尺度** | 一次会话 | 数周运行 | 数周到数月驻场 + 持续运营 | 新增现场上下文与长程编排 |
| **交付单位** | 答案 | 数据/语义资产 | 受控业务结果 + 可运营系统 | DA10 要扩成交付与交接 |
| **成功判据** | 答案对不对 | 资产准不准、能不能复用 | 结果对不对 + 过程合不合规 + 成本可不可接受 + 客户能不能自己跑 | DA11 要双轨化 |
| **失败代价** | 答错 | 资产污染 | 不可逆的业务/合规/财务损害 | DA12 要升级为变更控制 |

## 5. 能力光谱：五个成熟度等级

给「我们做到哪一步了」一个可对齐的刻度：

| 等级 | 名称 | 能力特征 | 典型交付 | 判据 |
|---|---|---|---|---|
| **L0** | 问答 | 给定库，回答一次问题 | 答案 / SQL | 首答正确率 |
| **L1** | 分析交付 | 多步计算 + 图表 + 报告 | 报告 / 看板 | 结论可复核 |
| **L2** | 环境建模 | 无现成库，能勘查环境、建库、建本体 | 数据集 / 语义层 / 本体 | 资产被复用 |
| **L3** | 受控执行 | 能提议、审批、执行、校验、回滚 | 一个跑通的业务流程 | 无越权、可审计、可回滚 |
| **L4** | 持续运营 | 客户接管后仍持续运行，异常自愈，经验回流 | 客户可自运营的系统 | 客户自主运行率、单位结果成本下降 |

**当前 DA 体系大致覆盖 L0–L2（DA01–DA05、DA13），L3 只有零散件（DA07.4 写入、DA12.5 变更控制、DA11 评测），L4 只有监控雏形（DA14）。**

从 L2 到 L3 不是加功能，而是加**信任基础设施**。这是本文档后面所有模块设计的出发点。

## 6. DA → FA 映射：复用 / 升级 / 新建

### 6.1 可以直接复用（内核不变，只改输入类型）

| 现有模块 | 复用方式 |
|---|---|
| DA02 数据准备与探查 | 泛化为「环境探查」，画像/质量/血缘/结构变化适配的算法全部可用 |
| DA04 任务轨迹与记忆 | 泛化为「现场记忆」，轨迹/经验提炼/晋升机制直接复用 |
| DA05 召回检索 | 泛化为「资源与能力召回」，增加工具/动作/制度/人的检索 |
| DA09 预测仿真优化 | 原样保留，FDE 场景同样需要（排产、容量、风险） |
| DA10 表格可视化 | 复用，但交付物扩展（见 6.3） |
| DA13 数据建模与物化 | 复用，作为「环境建模」的一个子能力 |
| DA14 持续运行与监控 | 复用，但监控对象从「数据」扩展到「环境 + 动作」 |

### 6.2 需要升级（边界语义变了）

| 现有模块 | 升级点 | 新增/改写的能力 |
|---|---|---|
| DA01 数据接入 | → **环境与资源接入** | 系统/目录/SaaS/Web/代码仓适配器；**能力探测**（能做什么，而不只是有什么字段）；健康检查 |
| DA03 业务语义与关系 | → **工作本体** | 增加 Action / Authority / Evidence / Approval / Lifecycle 五类定义；语义与「可执行」绑定 |
| DA06 语义查询与计算计划 | → **动作计划** | 从「生成 SQL」到「生成动作序列」：含人工步骤、等待、审批点、分支、回滚路径 |
| DA07 计算执行 | → **执行网关** | 三档动作、幂等键、dry-run、影响面预估、后置校验、补偿动作 |
| DA08 分析 | 基本复用 | 增加「对动作结果的分析」与「异常归因」 |
| DA11 评测与验证 | → **双轨评测** | 结果正确性 + 过程合规性；轨迹级评测；影子运行门禁 |
| DA12 治理与资产维护 | → **变更与信任治理** | 爆炸半径评估、分级授权、审批策略、不可否认审计 |
| DA10 交付 | → **交付与交接** | runbook、客户自助界面、SLA、知识移交 |

### 6.3 必须新建（现在完全空白）

按优先级排序（详细定义见 [02](02-新增模块清单.md)）：

| 编号 | 模块 | 为什么必须新建 | 优先级 |
|---|---|---|---|
| FA05 | 现场上下文（Site Context） | 多任务/多 Agent 的口径一致性无解；对应「待商榷的点 1」 | **P0** |
| FA03 | 工作本体（Work Ontology） | DA03 只有「世界是什么」，没有「能对世界做什么」 | **P0** |
| FA06 | 动作面与工具契约 | 没有它，能力无法被治理地暴露 | **P0** |
| FA14 | 现场评测与影子运行 | 现场没有 ground truth，需要旁路比对才能验收 | **P0** |
| FA07 | 身份、委托与权限 | Agent 不能继承人的全量权限 | **P1** |
| FA08 | 人在环与审批 | 高风险动作必须有审批点与证据包 | **P1** |
| FA13 | 证据、审计与可回放 | 「查得到为什么」比「做得到」更难 | **P1** |
| FA10 | 长程编排 | 真实流程跨天、要等人、要等外部事件 | **P1** |
| FA12 | 交付与交接 | 决定规模化分母是「产品」还是「人头」 | **P1** |
| FA15 | 成本与预算 | 决策依据从 token 改为「每次受控结果成本」 | **P2** |
| FA11 | 环境漂移监控 | 系统升级/权限变更/流程改版是主要失效源 | **P2** |
| FA16 | 现场→平台回流 | 唯一防止退化成咨询的机制 | **P2** |
| FA01 | 环境与资源接入 | R1–R6 的适配器层（可先复用 DA01） | **P0**（最小版） |
| FA04 | 工作流契约 | 把业务目标编译成可治理契约 | **P0**（最小版） |
| FA02 | 现场勘查 | 把「流程、角色、例外」变成可计算对象 | P1 |
| FA09 | 执行网关与沙盒 | 受控执行 + 预演环境 | P1 |

## 7. 回到「待商榷的点」

原文档留了两个开放问题，FDE 视角下可以给出更具体的答案：

### 7.1 子 Agent 之间怎么保证口径一致

**不是靠传递，是靠「钉住」。**

DA04.5 的任务上下文在 FDE 场景下不够用，因为它只有「一次任务」的生命周期。FDE 需要的是 **Site Context（现场上下文）**：一个现场一份，跨任务、跨周存在，内容是**一组版本引用**而不是内容本身——

```
SiteContext {
  data_snapshot:   rev@...
  ontology:        rev@...        # 实体、动作、权限、证据
  contracts:       [wf@rev, ...]  # 工作流契约
  authority:       policy.rev@... # 委托与审批策略
  evals:           suite.rev@...  # 验收与回归用例
  budget:          ...
}
```

子 Agent 收到的是这份引用的「裁剪视图 + 摘要」，**不能各自改写**。任何口径变更必须走一次显式的修订（记版本、失效旧结果、通知受影响方）。这同时解决了「改了口径但旧结果还在用」的问题。

### 7.2 业务 SKILL 的交付形式

原文档的判断是「DA08–DA10 一般不会直接交付给业务」。FDE 视角下，**SKILL 应该被重新定义为四元组**：

```
SKILL = 工作流契约 + 动作集（含权限）+ 评测集 + Runbook
```

- 只交付契约 → 业务看得懂但跑不起来；
- 只交付动作集 → 工程能跑但业务不知道边界；
- 只交付评测集 → 能验收但无法运营；
- 四件齐备 → 业务可以自己跑，Agent 可以退到「监护」角色。

这也回答了一个隐含问题：**SKILL 应该由 Agent 即时生成还是预置？** 答案是——契约与评测集应该由 Agent 生成草案、由人确认（因为它们是责任载体）；动作集必须来自受治理的能力目录（不能即时生成）；Runbook 可以由 Agent 生成并由现场验证。

---

## 8. 一句话总结

> 从 DataAgent 到 FDE Agent，**不是把「数据」换成「更多数据」，而是把「答案」换成「受控结果」**。
> 代价是必须补上三样现在完全没有的东西：**动作的语义（本体）、动作的边界（身份与审批）、动作的证据（审计与评测）**。
