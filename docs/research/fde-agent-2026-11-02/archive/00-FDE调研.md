# FDE 调研：从「驻场工程师」到「驻场智能体」

> 调研时间：2026-11-02　｜　范围：FDE（Forward Deployed Engineer）的角色史、工作内容、市场信号、产品化路径与失败模式
> 目的：为「DataAgent → FDE Agent」的延展提供事实基础和判断依据

---

## 0. 一句话结论

**FDE 不是一个岗位名词，而是一种交付范式：把工程能力放进客户现场，用「可验收的业务结果」而不是「软件功能」来结算。**

它之所以在 2025–2026 年突然变热，不是因为 Palantir 的故事被重讲了一遍，而是因为三件事同时成立：

1. **模型能力越过了「演示可用」线**，但企业内部的权限、口径、审批、审计没有跟着变——差距从「模型不够强」转移到了「系统接不住」；
2. **驻场的边际成本结构被改写**。过去一个 FDE 年薪 50–80 万美元，现在「1 个资深 FDE + N 个 Agent」可以覆盖同样面积的流程；
3. **控制面开始标准化**（Agent Identity / Gateway / Sandbox / Session / Eval 这一套被 hyperscaler 产品化），使得「驻场」不再等于「每个客户从零搭一套」。

这三条合起来，才让「FDE Agent」在 2026 年成为一个可讨论的产品问题，而不是一个比喻。

## 1. FDE 的由来：四段演化

| 阶段 | 时间 | 形态 | 关键特征 |
|---|---|---|---|
| 起源 | 2003–2010 | 工程师驻场 | Palantir 早期把工程师派到客户办公室，和业务人员坐在一起工作。身份介于工程师、解决方案架构师和客户员工之间 |
| 产品化 | 2010–2018 | 驻场经验 → 平台抽象 | Foundry / Gotham 把反复出现的现场工作沉淀为产品能力（本体、动作、权限、审计） |
| 模式验证 | 2018–2025 | FDE 成为组织范式 | a16z 2025 年称之为「startups 最热门的岗位」，并把它归因为 **services-led growth** 对 PLG 的反动 |
| Agent 化 | 2025–2026 | 派 Agent 驻场 | OpenAI 成立 Deployment Company；Firecrawl 提出 FDA 概念；Ramp 等把 FDE 写进 JD |

**要点：Palantir 模式真正稀缺的不是「离客户近」，而是那条反馈回路**——

> 现场摩擦 → 驻场工程发现 → 可运行交付 → 抽象为可复用能力 → 平台变强

没有最后两步，FDE 就是高级外包。这条回路是后面所有判断的基准线。
（[a16z, 2025-06](https://a16z.com/services-led-growth/)、[rmax-ai 分析](https://github.com/rmax-ai/rmax-ai.github.io/blob/main/processed/forward-deployed-engineer-enterprise-ai.md)）

## 2. FDE 实际在做什么

把公开材料里的 FDE 工作拆开，会发现它几乎不写「模型代码」，而是在做**五类约束的消解**：

| 约束 | 具体表现 | FDE 的动作 |
|---|---|---|
| **语义碎片化** | 「活跃客户」「重大合同变更」在不同部门定义不同 | 建一套可执行的业务本体，而不是写文档 |
| **身份与授权** | 企业权限是为「人 + 应用」设计的，不是为「会推理、会调工具、代表别人行动的系统」设计的 | 拆分读权限 / 提议权 / 审批权 / 执行权 |
| **行为不确定** | 输出质量取决于上下文、工具状态、模型版本、权限 | 用评测与轨迹把不确定性变成可度量 |
| **成本不可预测** | 推理只是成本的一部分，工具调用、重试、沙盒、人审、事故处理才是大头 | 用「每次受控结果的成本」而不是 token 计价 |
| **责任分散** | 平台、厂商、安全、合规、业务各管一层，没人管结果 | 设计审批点、证据链与回滚，把责任落到可指认的位置 |

（来源：rmax-ai 对 FDE 的五约束归纳，与 Kindo 的实践一致）

### 2.1 一个 FDE 的真实交付物

不是 prompt，也不是一个应用，而是**一份「工作流契约」**。典型形态：

> 给定用户对某条记录的修改请求，系统检索相关上下文与制度，生成带证据的结构化变更提案，判断是否需要审批，仅在委托范围内执行，校验执行后的真实状态，并留下可追溯的审计记录。

这句话里已经隐含了后面设计要用的全部要素：**发起者、被改对象、证据源、允许的推理、适用制度、审批边界、工具交互、不可逆动作、成功判据、回滚路径、审计要求**。

### 2.2 FDE 的六项核心工作

1. **定义契约**——把「让客服更快」翻译成可治理的执行契约；
2. **建语义层**——不是知识图谱表演，而是把「什么是对的」和「什么是被允许的」分开；
3. **做身份与委托**——用户身份 / Agent 身份 / 委托范围 / 工具身份 / 审批权 / 执行权，六者分离；
4. **设计人在环**——`读 → 分析 → 提议写 → 策略校验 → 请求审批 → 执行窄动作 → 校验结果 → 记录`；
5. **建评测与观测**——结果对不对之外，还要看合规、审批纪律、工具正确性、成本、人审负担；
6. **把现场变成平台**——这是唯一的护城河，也是唯一避免退化成咨询的机制。

## 3. 三种 FDE 形态，三种失败方式

| 形态 | 谁在做 | 优势 | 失败模式 |
|---|---|---|---|
| **Vendor FDE** | 模型/产品厂商（OpenAI、Anthropic、Cohere、Ramp、Kindo） | 深度适配 + 反馈回产品 | 客户定制无边界 → 变成「伪装成平台的服务的公司」 |
| **Consulting FDE** | 咨询/系统集成商（Bain、Capgemini、McKinsey 等） | 跨系统协调、组织推动 | 激励错位：延长转型项目比简化架构更赚钱 |
| **Internal FDE** | 企业内部的「嵌入型工程师」 | 沉淀为企业自身能力 | 变成没有边界的「AI 转型岗」，不拥有任何可验收结果 |

**判断：对做产品的团队（我们）来说，真正要建的是「让 Internal FDE 能规模化」的那层基础设施，而不是去抢 Consulting 的生意。** 因为 Internal FDE 是三种形态里唯一会长期采购「平台能力」的角色。

## 5. 为什么 AI 时代 FDE 反而更重要

一个反直觉但重要的判断：**Agent 越强，FDE 越重要，而不是越不重要。**

理由是 Agent 把「执行」变便宜了，于是瓶颈整体前移到「定义什么该被执行」：

1. **Agent 可以大规模行动，所以「允许做什么」必须先被定义。** 人类有判断力作为兜底，Agent 没有；权限设计从「够用就行」变成「必须先于执行存在」。
2. **Agent 的成本随流程而非调用增长。** 一个流程跑 1000 次，每次多 3 轮人审，成本结构就完全变了。这需要有人对「每次受控结果的成本」负责。
3. **Agent 的失败是系统性的。** 同一个错误会以相同方式复制一万次。评测、影子运行、金丝雀不是工程洁癖，是风险控制。
4. **企业真正缺的不是工具，是「把工具接进流程」的能力。** a16z 的原话是：企业买 AI 就像奶奶买 iPhone——她想用，但需要你帮她设置。

**所以 FDE Agent 的产品定位不是「更聪明的助手」，而是「能把一个流程从人工接管到可运营状态的系统」。**

## 6. 失败模式清单（设计时必须规避）

| 失败模式 | 表现 | 对应设计约束 |
|---|---|---|
| **咨询化** | 每个客户一套定制，平台不变强 | 必须有「回流」模块，且回流要可度量 |
| **技术债化** | 集成绕过统一网关，安全例外累积 | 动作必须走网关，例外必须登记 |
| **权限放大** | 「反正人本来就有这个权限」→ Agent 继承全量权限 | 强制读/提议/执行三档分离 |
| **以 token 计价** | 便宜的模型 + 大量返工，实际更贵 | 成本单位改为 cost per controlled outcome |
| **无头=无人** | 把「headless」误解为「无人参与」 | 高风险流程必须保留监督界面 |
| **演示即验收** | 10 个 curated demo 通过就上线 | 必须有轨迹级评测与影子运行门禁 |
| **抽象过早** | 现场还没跑通就急着做通用平台 | 先 1–2 个现场跑穿，再抽象 |

## 7. 对「DataAgent → FDE Agent」的直接启示

调研给出四条硬结论，直接决定后面的设计：

1. **分水岭是「动作面」，不是「数据面」。** 只读的 FDE Agent 和广义 DataAgent 没有本质区别；一旦要写、要触发、要代表某人行动，就必须引入身份、审批、回滚、审计——这是新的一层，不是旧模块的参数。
2. **控制面已经被商品化，不要再造。** Agent Identity / Gateway / Sandbox / Session / Memory 应复用 AgentOS 或云平台；我们该建的是**业务本体、工作流契约、动作语义、现场评测、交接**——这些是业务侧的、无法被通用平台替代的。
3. **「现场」必须是一等对象。** 一个客户现场有资源清单、本体、权限模型、契约、评测集、变更历史、预算。没有这个对象，多任务/多 Agent 的口径一致性无解。
4. **交付物必须是「客户能自己运营的系统」。** 否则规模化的分母永远是 FDE 人数，而不是产品。

## 8. 待验证 / 存疑

- 「FDE Agent」目前只有 Firecrawl 一类早期样本，**没有成熟的品类定义**；本报告的用法是「被部署到客户现场、对受控结果负责的智能体」，属于我们的工作定义，不是行业标准。
- DeployCo 的实际交付形态（服务公司 vs 产品）尚未公开细节，需持续跟踪。
- 「驻场」在中国 ToB 的付费习惯下是否成立，存在结构性疑问（中文圈已有「FDA 反人性 18 个月」的说法，属观点而非数据）。
- Palantir 模式不可简单复制：它的杠杆来自本体 + 动作 + 权限 + 审计的一体化平台，而不是「派人」这件事本身。
