# DataAgent 市场、实现与 MintHub 产品方向

调研日期：2026-10-30，Asia/Shanghai。状态：前期研究与建议，未实施 DataAgent、未运行 benchmark、未发布 MintHub 包。

## 1. 结论先行

**建议把 DataAgent 定义为：将陌生数据逐步转成可审核语义资产，并据此完成取数、分析和预测的 Agent 应用。** MintHub 提供模块分发与组合，DataAgent 维护数据任务、语义资产和结果证据的生命周期。

用户提出的三部分应连成一条可积累的链路：

```mermaid
flowchart LR
    F[Excel / JSON 等文件] --> D[探查与数据画像]
    E[数据库 / API / MCP] --> D
    D --> O[语义与关系候选]
    O --> R[验证 / 业务确认 / 发布版本]
    R --> S[实体 / 指标 / 表字段值召回]
    S --> Q[语义计划 / NL2SQL / 校验执行]
    Q --> A[BI / 表格 / 统计 / 预测]
    A --> V[答案 / 数据 / 图表 / 工作簿 / 证据]
    V --> C[反馈转变更提案与回归用例]
    C --> R
```

五项核心判断：

1. **竞争正在覆盖整个分析链路。** 商业产品已覆盖语义建模、值检索、多步取数、文件分析和 Python。单一聊天框或 NL2SQL 接口的产品区分度有限。[01 §2–3]
2. **ontology 应有可执行含义。** 至少表达实体、grain、指标、业务时间、单位、值映射、join 及证据；不能只保存表说明或 embedding。[02；04 §3–5]
3. **自动构建应输出可验证提案。** 元数据和统计可以发现候选关系；业务指标、时态关联和正式发布需要明确的确认规则。[01 §3.1–3.3；03 §6]
4. **跨行业依赖组合能力与领域资产。** 通用内核复用连接、探查、召回和执行；行业包提供术语、指标模板、方法和测试；企业完成物理映射和口径确认。这是建议路线，尚未证明其交付成本优势。
5. **当下先做闭环，未来再扩自治。** 首版应让多文件与一个企业数据库都能跑通“数据到有证据的答案”；将受控预测函数纳入验证，后续扩展语义互通、主动分析和带审批的业务动作。

## 3. 市场实现分别教会我们什么

| 路线 | 代表 | 已有能力与关键边界 | 对我们最有用的部分 |
| --- | --- | --- | --- |
| 数据平台原生 Agent | Snowflake Cortex、Databricks Genie、Fabric | catalog/权限/计算集成；仍依赖已定义语义、作者配置或审核 | 导入已有治理资产，避免另造重复指标；采样和值检索也做授权 |
| 语义引擎驱动 BI | Looker、ThoughtSpot、Quick BI、FineChatBI | 指标/字段到受约束查询；深分析能力与产品模式有关 | 让模型选择语义、让编译器控制关联和聚合；暴露歧义与口径 |
| Notebook 与文件分析 | Hex；Genie/Quick BI 的文件路径 | SQL/Python、单元结果、图表和产物；上下文治理不等于权限隔离 | 文件分析保留代码、数据来源和可复算产物，分析可迭代 |
| 业务 ontology 平台 | Palantir Ontology/AIP | objects/links/actions/functions、分支、权限；建设范围更广 | 长期把概念、关系、函数和业务动作组合，初版聚焦读分析 |
| 开源可组装体系 | WrenAI、Vanna、DB-GPT、SuperSonic 等 | 架构与代码可参考，版本/许可证/执行边界差别很大 | 按模块选型和替换，建立统一契约与评测 |

### 开源代码的具体取舍

| 实现 | 值得优先评估的代码或机制 | 不能直接假设的能力 |
| --- | --- | --- |
| WrenAI 当前主线 | MDL、语义 engine、hash 过滤的上下文、dry-plan 和查询 policy | 当前 SDK/CLI 与旧 ChatBI 界面不同；完整审批/编排需调用方提供，README 将完整用户/组及行列权限产品能力列为商业功能 |
| MetricFlow | 指标请求到 dataflow/SQL，按实体类型和有效期限制 fanout join | 自带企业探查、文件分析或业务身份审批 |
| SuperSonic | metrics/dimensions/entities/values 映射、语义翻译和中文纠偏机制 | 直接无条件内嵌；固定版本 LICENSE 有商业衍生附加条件 |
| DB-GPT | 表到字段的分级 schema 检索、连接器和分析工作流 | schema RAG 已等同完整 ontology 或值级召回 |
| Vanna | user-aware tools、数据可见性开关、SQL runner 边界 | 默认 RLS 自动生效；所读 registry 参数变换默认是 NoOp |
| DataHub/OpenMetadata | catalog、glossary、ownership、lineage 等资产接口 | 目录权限自动转为数据库行列权限，或目录本身执行指标；OpenMetadata 本轮仅核对 README/LICENSE |
| RD-Agent | 假设、代码、实验、评分、工件与反馈闭环 | 通用业务预测有效性、无泄漏，或实验确认等同强制审批 |

这些是静态代码核验后的候选，尚未在 Mint 集成或比较。基础计算优先采用 DuckDB/Arrow、SQLGlot 和成熟统计/预测库；避免在 Agent 层重写计算引擎。许可证按目标 commit、路径及依赖重新确认。[02 §2–5]

### 三个需要修正的直觉

**“竞品都要先人工建模”不准确。** Genie 文档已有元数据和历史 SQL 挖掘、知识建议；Snowflake 有关系类型推断和优化建议。但建议、审核接纳与业务语义正确仍是不同阶段。[01 §3.1–3.2]

**“文件分析只是读一个 CSV”不够。** Excel 有多 sheet、多个表块、合并表头、公式、格式和隐藏区域；文件与企业表混合还有身份、键和时间对齐问题。应根据能力声明区分“支持矩形数据表”和“支持任意工作簿任务”。[01 §3.9；03 §4]

**“接了 MCP 就接了千行百业”不成立。** MCP 连接工具，业务含义仍来自文档、目录、现有模型、数据证据和用户确认。API 不一定有全量 schema、任意过滤或 SQL；跨源检索也不等于跨库 join。[04 §6]

## 4. 三种产品路径

| 方案 | 起点与价值 | 主要代价 | 建议 |
| --- | --- | --- | --- |
| 连接器 + 通用 SQL/Python Agent | 起步快，适合分析师探索 | 口径易漂移，陌生源建模和正确性难验证 | 作为基线与受控探索能力 |
| 语义资产驱动的组合式 DataAgent | 文件与企业数据共享资产和分析链路，适合 MintHub 生态 | 需建设语义生命周期、关系验证和评测 | **推荐主线** |
| 完整企业 ontology / 决策平台 | 覆盖对象、动作、权限、业务应用与自动化 | 实施、治理、集成和产品面显著扩大 | 作为长期方向，逐个验证需求 |

推荐主线仍保留灵活探索。对已定义的指标走受约束语义查询，对未建模问题走受控 NL2SQL/Python；探索得到的口径经确认进入语义版本，避免系统只能回答预先列好的问题。

## 5. 双入口，共享一套中间资产

### 5.1 即席文件分析

建议流程：选择文件 -> 结构识别 -> 类型/单位/时间/缺失与重复画像 -> 关联候选 -> 任务级临时语义 -> 查询与分析 -> 数据/图表/工作簿 -> 按用户需求转成可复用领域资产。

初版支持 CSV、矩形 Excel、JSON/JSONL；对复杂表头、嵌套、公式缓存缺失和无法识别的表块明确提示，提供范围/字段确认。保留原文件 digest、sheet/范围和变换记录，清洗不能覆盖原件。读取公式值与计算公式是不同能力。

临时任务无需先完成全企业 ontology。只构建当前问题足够的字段、值、指标和关联，再随交互补充。发布为企业指标时补 owner、确认和回归，不能把单次分析结论自动作为全局事实。

### 5.2 企业数据问答

建议流程：可信身份连接 -> 导入 catalog/dbt/既有指标 -> 按域探查元数据 -> 预算内采样与 profile -> 搜集文档/SQL证据 -> 语义与关系提案 -> 确认发布 -> 授权范围内检索/规划/执行 -> schema drift 与语义更新。

探查采用渐进方式：先名称、类型、约束、注释和数据量，再处理选定业务域与高价值字段。禁止默认对全企业表做全扫描或把所有样本塞入模型。源无法提供统计或字段可见性时，保存能力缺失和不确定性。

### 5.3 共享中间资产

共享 `SourceProfile -> SemanticRevision -> QueryPlan -> ResultArtifact`。文件里的订单与数据库里的订单可以映射同一业务概念，但合并必须核验实体键、单位、时间和授权；共享概念不会自动证明两个源可以直接拼接。

## 6. Ontology 的建议边界

这里使用“ontology”统称业务概念、可执行分析语义及物理映射。它与 RDF/OWL、厂商对象平台有交集，初版不要求完整推理引擎或图数据库。

| 资产 | 必需内容 | 自动化与确认 |
| --- | --- | --- |
| 物理画像 | 源、表/文件范围、类型、分布、唯一性、采样与时间 | 可自动采集，区分全量和估算 |
| 概念与实体 | 名称/别名、稳定 ID、主键、实体粒度、物理映射 | 文档/目录辅助提案，关键身份需确认 |
| 关系 | 复合键、方向、cardinality、桥表、租户键、时态条件 | 约束和统计验证候选，复杂关系需确认 |
| 指标 | 公式、过滤、grain、聚合方式、分子分母、单位、币种、时间 | 从已有模型导入或建议，业务定义由 owner 确认 |
| 业务时间 | 事件/下单/支付/结算角色、时区、财务日历、as-of、有效期与迟到处理 | 可识别时间字段候选，默认业务时间和跨期规则需确认 |
| 值语义 | 编码/别名、单位与格式、值索引、覆盖与新鲜度 | 自动构建候选字典，敏感值受权限约束 |
| Policy | 主体/租户、元数据和值可见性、行列规则、外发和导出、独立策略版本 | 对接可信授权，Agent 不自行批准或扩大权限 |
| 质量与来源 | freshness、完整性/唯一性断言、采样范围、lineage、证据与异常 | 自动记录获准检查，权威来源和质量豁免需明确责任人 |
| 证据与版本 | 来源、规则/数据/代码版本、提案人、审核状态、生效范围 | 自动记录，发布与回滚有明确权限 |

### Join 发现是一个验证任务

先导入声明的 PK/FK、dbt 关系和历史 SQL，再用名称/类型筛候选，检查复合键唯一性、包含率、空值、租户、时间和重复膨胀。保存候选证据、采样范围、验证日期、反例和允许用途。

同名 `id`、较高值重合或历史上有人 join 过，都不足以证明关系正确。即使键可关联，一对多 join 也可能放大订单金额。涉及多事实表时，应在共同粒度聚合再组合；按历史状态匹配 Type 2 慢变维等情形需要有效期条件；多对多应明确桥接关系，涉及可加指标时定义去重、分摊或其他聚合语义。

推荐发布状态 `draft -> proposed -> validated -> reviewed -> published`，并能 deprecated/revoked。机器验证与业务审阅分别记录，不能只用一个“confidence=0.99”代替。初版关键指标和关系采用审阅发布；将来再按风险开放自动发布范围。

### 格式与版本

Ossie/OSI 是值得适配的开放语义交换方向；当前 Core `0.2.0.dev0` 明确是可变草案，查询编译与治理仍有路线图事项。建议内部契约稳定、外部格式适配，实际消费者决定交换版本，并测试转换损失。[04 §5]

代码包版本、语义版本、policy revision、schema 指纹、数据快照和索引版本分别管理。一份 `mint.lock` 不足以复现实时数据库的历史答案。

## 7. 智慧问数：召回、规划、验证

建议链路如下，具体预算由评测确定：

1. 识别问题中的实体、指标、维度、值、业务时间和所需产物，检测歧义。
2. 在当前授权范围内，混合术语/全文/向量检索召回领域、指标和表，按关系图补桥表。
3. 单独召回字段与值：先确定字段语境，再做编码、精确/模糊匹配；高基数和动态值按需查询。
4. 生成绑定到稳定语义 ID 的 QueryPlan，显示时间、单位、指标定义、join 和假设；关键歧义触发简短澄清。
5. 已治理指标优先编译语义计划；开放问题采用受控 NL2SQL，值用参数绑定。
6. 解析并校验 SQL，结合源侧只读权限、对象/函数限制、成本预算与超时；支持时做 EXPLAIN，但不假设 EXPLAIN 无成本。
7. 执行并检查空集、单位、重复膨胀、聚合守恒和可验证业务约束；有界修复，超预算明确失败。
8. 输出答案和可查看的口径、数据截至时间、SQL/计划、结果引用与限制；反馈进入变更提案和回归用例。

召回需保留可用替代路径，但每次继续检索应有缺失证据：缺字段、未知值、不可连接或计划校验失败。没有必要为每一问都让多个 Agent 并行写完整 SQL；并行更适用于独立候选探查、较难问题的受控候选与核验。

业务正确性的失败应分为：接错源、漏召回、值错配、口径/时间错、join 错、SQL 错、执行错、解释错。单看最终正确率无法决定该换模型还是修语义。

## 8. 分析、表格和预测如何扩展

### 8.1 函数注册应成为明确的模块边界

每个函数声明输入数据 schema、语义要求、输出产物、适用条件、参数、版本、资源预算、数据外发和副作用。Agent 负责选方法和解释结果，库负责计算；所有函数绑定上游查询、语义版本与数据截至时间。

| 类别 | 可先提供的函数 | 输出与验证 |
| --- | --- | --- |
| BI | 分组比较、同比环比、贡献度、漏斗、留存、cohort | 明确分母、时间、去重、缺失和单位 |
| 表格 | 清洗、合并、透视、公式、格式化导出 | 重算、目标区域、无关区域完整性与引用检查 |
| 统计 | 分布、异常、相关、回归、假设检验 | 样本量、效应、不确定性、多重检验与适用条件 |
| 预测 | naive/seasonal naive、ETS/ARIMA 或已有预测器 | 时间切分、baseline、回测误差、区间和数据不足判断 |

Python/SQL 生成保留为复杂探索工具，放在具有限制的工作环境。函数名称、模型文本承诺和 SQL AST 均不能替代数据权限与进程隔离。

### 8.2 预测的首版范围

先验证一类明确需求，例如“预测未来四周按周聚合的销量”。先确认目标、粒度、horizon、历史长度和外生变量是否未来可知，再调用算法。比较 seasonal naive 与统计/可用预训练模型，输出 rolling backtest、区间及限制。

预处理只在训练窗口 fit，选模使用验证窗口，最终测试窗口隔离；每个回测起点只能读取当时可得的信息。当下的预测样例同样需要防泄漏、baseline 与回测，近期再扩大任务和模型覆盖。

不能只生成未来数字和折线图。无法超过 baseline 时允许选 baseline；数据不足、结构变化或目标不可观测时允许拒绝预测。“销量下降的维度贡献”也不能直接写成因果结论。因果推断、干预模拟与优化决策需要不同的假设、数据和评测。

## 9. MintHub 的模块映射

下表都是建议职责，尚未创建或发布同名包。

| 层 | 建议模块 | 可以复用什么 | 需要新增什么 |
| --- | --- | --- | --- |
| Agent runtime | Mint/Kernel 会话、工具、模型与事件 | 当前已装配的运行能力 | DataAgent 配方与工作流 |
| 数据服务 | connector、file ingestion、profile、query jobs | 数据库驱动、DuckDB、MCP Toolbox 等候选 | 源能力契约、任务/授权和一致结果引用 |
| 语义资产 | ontology registry、import/export、validator | dbt/Cube/目录/开放标准适配 | 提案审阅、证据、版本、映射与影响分析 |
| 问数 | retriever、planner、SQL validator/executor | WrenAI/Vanna/DB-GPT 等架构/模块候选 | 统一表字段值召回、语义计划与端到端评测 |
| 分析 | BI functions、spreadsheet、forecast | 成熟计算库、固定模型与函数 | 语义输入约束、产物、适用条件与回测 |
| 领域 | retail/manufacturing 等包 | 公开业务知识与授权模板 | 企业映射、指标裁决与领域测试 |
| 产品与交付 | bundle + preset，按需 app | Mint 依赖、lock 与分发 | 数据选择/口径确认/结果界面和安装验收 |

当前核验的 stdio bundle 路径能承载本地服务；远程 HTTP MCP 与单次调用取消尚未接通。应通过本地连接器访问源，并由服务实现长任务和取消。工具调用未自动透传业务身份，企业共享部署必须补可信身份链。[04 §2–4]

公开 MintHub 分发代码、模板、契约和无客户数据的领域包。客户 ontology、值索引、凭据和数据保留在客户环境；受控私有分发是另一个需要验证的交付选项。

## 10. 跨行业的可扩展方式

建议分成三层资产：

| 层 | 包含什么 | 生命周期 |
| --- | --- | --- |
| 通用能力 | 连接、画像、检索、查询、分析函数、证据和评测 | 由平台维护，跨行业复用 |
| 行业领域包 | 实体和术语、候选指标、日历、方法、反例与示范映射 | 由领域维护者版本化发布 |
| 企业工作区 | 真实字段映射、指标口径、权限、数据、批准的关系与问题 | 由客户确认，跟随其业务演进 |

行业包中的“收入”“活跃”“良率”“及时率”都是待确认模板。客户的结算、退货、时间和组织维度可能不同，不能安装模板后直接变成认证指标。

建议先用两个结构差异大的业务域验证可复用性，例如零售经营与制造质量/交付。它们是研究试点候选，不是已确定客户。用新数据源首次回答时间、需要人工澄清数量、可复用资产比例和维护成本衡量泛化；只测 SQL 准确率不足以证明跨行业。

## 11. Benchmark 组合和内部验收

| 能力 | 公共参照 | 仍要自建的部分 |
| --- | --- | --- |
| 企业 SQL 工作流 | Spider 2.0、BEAVER | 私有 schema、源授权、业务口径、版本 |
| 值和规则 | BIRD、LiveSQLBench | 真实编码、权限过滤、规则时效与索引更新 |
| 多轮与恢复 | BIRD-Interact、BIRD-CRITIC | 企业澄清、结果指代、任务取消和失败处理 |
| 文件/工作簿 | DABench、DSBench、SpreadsheetBench | 企业文件结构、混合来源、原件保护与导出 |
| 深分析 | DataSciBench、DiscoveryBench | 行业假设、证据、结论有效性 |
| 预测 | GIFT-Eval、Monash | 取对序列、特征可知性、业务损失和端到端防泄漏 |

公开集的变体、hint、预算、scorer 和运行环境必须固定。原始 BIRD 评估器使用结果 set，忽略重复行；DABench 评估器存在漏答未计分母的路径。内部应保留完整分母、行关系与重复语义，不能照搬分数作为业务验收。[03 §3–4、§7]

建议分两步建设内部数据，均尚未构建/运行：

1. 最小核验集：两个业务域、8个固定数据包、约80个业务问题，另含权限矩阵与版本变更，先保证真值、环境和错误归因可靠。这是快速验证规模建议，不能证明普遍跨行业能力。
2. 扩展评估：采用专题建议的24包、360业务任务，加120权限用例与12组版本变化；数据包级拆开发/回归/盲测，避免同源近重复泄漏。[03 §8]

分别报告从原始数据冷启动、已审核 ontology 问答、提供 gold 表/字段/join 的诊断轨道。端到端任务需同时满足业务结果、权限、证据和产物约束。权限失败阻断交付；零观测泄漏也不等于已经证明零风险。

ontology/关系发布初期优先经过审阅；可以离线测“若自动发布”的 precision/recall，达到门槛再逐步开放。建议门槛应由真实试点成本和业务风险调整，不作为行业标准。

## 12. 当下、近期与未来

采用能力与证据门槛推进，当前没有团队规模和客户约束，暂不承诺日历排期。

| 阶段 | 应交付的结果 | 进入下一阶段的证据 |
| --- | --- | --- |
| 当下：技术与产品核验 | 两个入口共享画像/语义/结果契约；一条文件分析链路、一条企业只读链路；具备防泄漏、baseline 和回测的预测样例；小规模真值集 | 可重放任务、真实模型调用、明确错误归因；新源可重复接入 |
| 第一版：可信分析闭环 | 多文件/一个数据库、渐进探查、关系提案、语义审核版本、表字段值召回、SQL+BI、导出和结果证据 | 业务任务达到试点门槛，权限矩阵通过，升级可回归 |
| 近期：领域复用和深入分析 | 第二方言、既有语义导入、文件与库融合、领域包、函数生态、扩展预测覆盖与schema drift | 第二业务域无需重写内核；语义更新可发现影响并验证 |
| 中期：主动分析 | 周期分析、指标异常、可解释归因、任务订阅与分析资产更新 | 有意义告警比例、可追溯证据、成本收益与误报可接受 |
| 长期：决策与业务动作 | 情景模拟、因果分析、优化建议、经批准的操作与结果观察 | 专门的因果/优化验收、动作授权、回滚与业务收益证据 |

长期价值可能来自持续维护的企业语义和分析经验：每次澄清形成可审核规则，每次错误成为回归，每次 schema 变更定位影响，每个行业积累可移植模板。这个判断需要通过交付和使用数据验证。

## 13. 优先研究的下一组问题

1. 用真实或脱敏业务数据，对比“schema直接入上下文”“检索+NL2SQL”“受审核语义+结构化计划”三条基线，固定模型和预算。
2. 对 join 引入复合键、多事实表、跨租户相同 ID、慢变维和文件补数反例，测机器能否识别不确定性而非只测命中。
3. 对一个用户问题比较指标口径变更前后结果，验证版本、影响分析和索引失效。
4. 用同一 ResultArtifact 接 BI、工作簿和预测函数，核验输入语义是否足够，避免每个函数独立猜含义。
5. 以干净 Mint 工程验证 bundle/preset 的安装、工具发现、源授权、长任务/取消、产物和升级；再决定 app 形态。

以上是调研后的验证建议，不表示本次已经授权或完成产品实现。决定首批数据和使用场景后，应据此形成正式设计与可执行计划。
