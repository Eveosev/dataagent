# DataAgent 正确性、验证与评测模块

> 证据口径：本文所有数字均来自公开论文、官方文档或第三方复现页，**本次没有运行任何 benchmark、没有企业私有数据、没有模型凭据**。每条数字都附样本与条件；标注 `未核实` 的条目表示本次未能抓到一手页面，或公开材料不存在。文中的阈值均为**建议初始值**，需用自有基线校准，不构成行业标准。

## 0. 结论先行

1. **公开基准的 SOTA 仍停在 57%–60% 区间，而不是 90%+。** Spider 2.0-Lite 60.15%、Spider 2.0-Snow 60.51%（ProSPy，2026-06，Claude-4.5-Opus，无 majority voting）；DataAgentBench 57% pass@1（GPT-5.5，2026-10）。这意味着即便最好系统，**每 5 个企业问题仍有约 2 个答案是错的**。
2. **公开榜单本身不可作为验收真值。** 一项 2026-01 的专家复核发现 BIRD Mini-Dev 52.8%（263/498）、Spider 2.0-Snow 62.8%（76/121）的样本存在标注错误；修正 100 条子集后，16 个 agent 的 EX 相对变化 −7%～+31%，排名平均移动 5 位、最大 ±9 位（arXiv 2601.08778）。
3. **"受控语义"比"更强模型"更能提升正确率。** 410 道 BIRD-Interact 题、7 个 LLM 的同题对照中，语义层给每个模型加 20–31 个百分点（GPT-5：21.5%→50.5%），而换模型最多只移动 17.6 个百分点（AtScale，2026-10-28）。但该增益只覆盖"语义层能表达"的题，必须按覆盖率折算。
4. **答案级评分天然漏检，验证必须是独立模块。** BIRD 的 EX 用 `set(pred) == set(gt)`，忽略行序与重复行；Spider 2.0-Lite 只检查 gold 列是否出现、容差 1e-2、可配置 `condition_cols`；DAB 的验证脚本是字符串包含 + 容差 + Levenshtein，作者明确写明"无法发现答案里多出来的错误信息"。**这些口径都无法证明答案对，只能证明"看起来一样"。**
5. **LLM-as-judge 只能做分诊与部分评分，不能做唯一验收。** MT-Bench 报告 GPT-4 judge 与人类一致率 >80%，但同时存在位置、冗长、自我增强偏差；DAB 用 GPT-5 做失败归因 judge，与人工精确一致仅 67%，FM2–FM4 的跨 judge Cohen's κ 只有 0.42–0.46。

### 2.2 Spider 2.0：数字与"VERIFIER"核实结论

**任务形态**：来自真实企业数据应用，库常有 1,000+ 列，跨 BigQuery/Snowflake/SQLite；解题需检索元数据、方言文档乃至项目代码，常需多条 SQL、超过 100 行。`[一手：arXiv 2411.07763v2，2025-03-17；README 2026-11-01]`

**评分口径**（读 `spider2-lite/evaluation_suite/evaluate.py`，523 行）：
- `compare_pandas_table(pred, gold, condition_cols, ignore_order)`，`tolerance = 1e-2`；
- 只比较 `condition_cols` 指定的列；`ignore_order=True` 时对列向量排序后比较；
- 支持多 gold（`compare_multi_pandas_table`），任一 gold 命中即通过；
- 论文附录称 Lite/Snow 用 EX，Spider 2.0 用 SR（人写 evaluation scripts，按 string/table/database 三类输出判定）。

**成绩轨迹**：

| 时间 | 系统 | Lite | Snow | 条件 |
| --- | --- | --- | --- | --- |
| 2024-11（论文） | o1-preview + Spider-Agent | 23.40% | 23.77% | 论文 Tab.2；632 全量为 21.3% |
| 2024-11（论文） | 传统 text-to-SQL parser | **5.7%** | — | 论文 §3.2，说明"预置 schema 的一次生成"几乎不可用 |
| 2025-02 | ReFoRCE | 36.56% | 35.83% | 自蒸馏+多数投票；arXiv 2502.00675 |
| 2026-06 | ProSPy | **60.15%** | **60.51%** | Claude-4.5-Opus，**无 majority voting**；arXiv 2606.05836 |
| 2026-10 | LYNX | 最高 59.54% | — | 轻量到商用模型区间 10.66%–59.54%；arXiv 2610.14777 |

> 结论：两年内 Lite 从 23% 提到 60%，但**仍有三到四成失败**；且 ProSPy 的 60.15% 是单系统单配置，未给置信区间。

**关于 "Spider2-VERIFIER"**：本次在 arXiv API、DuckDuckGo、GitHub 仓库搜索、xlang-ai 组织 33 个公开仓库中均**未找到名为 Spider2-VERIFIER 的公开基准或组件** `[未核实]`。最接近的真实机制是：
- Spider 2.0 的 **per-task human-written evaluation scripts**（论文 Tab.11，按 string/table/database 三类输出写判定函数）；
- Lite/Snow 的 **execution-based focused evaluation**；
- 另有独立基准 **Spider2-V**（NeurIPS 2024，多模态数据科学 GUI 任务），与本议题不同。

因此报告中不应把 Spider2-VERIFIER 当作既有基准引用；可写成"Spider 2.0 采用逐题人写 verifier，而非通用 verifier"，这恰好支撑"验证是独立模块、需要工程化"的论点。

**已知缺陷**：
- **标注错误**：76/121（62.8%）Spider 2.0-Snow 样本存在 E1–E4 类错误（问题/SQL 不一致、join 未去重、领域知识错误、问题歧义）`[一手：2601.08778]`；
- **评分器变更**：2025-10-29 官方修复 evaluation-suite 并刷新榜单，历史分数不可直接比；
- **oracle tables**：2025-04 起提供 gold tables，使用即须标注，否则掩盖表召回问题；
- **数据/环境不稳定**：Snowflake 账号 2026-08-12 起 suspension；2025-11 因 MFA 政策导致登录方式变更；
- **Gold SQL 泄漏**：官方明示不推荐用 gold SQL 做 SFT，但文件已公开。

### 2.3 BIRD：EX 口径的三处结构性漏检

**口径**（读 `bird-bench/mini_dev/evaluation/evaluation_ex.py`）：
```python
if set(predicted_res) == set(ground_truth_res):
```
- **丢重复行**：`set` 去重，`1,1,2` 与 `1,2` 判等；财务明细、重复计费、Top-N 并列全部失真；
- **丢行序**：排序题（"按营收降序前 10"）只要集合相同即通过；
- **保留列序**：tuple 内列序敏感，`SELECT a,b` 与 `b,a` 判不等——列序成了一个"假难度"；
- **无部分分**：列缺失/多列一律 0 分，无法区分"接近"与"完全错"。

**成绩**：

| 口径 | 成绩 | 条件 |
| --- | --- | --- |
| 隐藏测试集 | 82.95 | 官方榜单（第三方页转述，2026-10-19 快照） |
| Dev 1,534 | 77.12 | Claude Opus 5.5，单次调用 + 检索，第三方自测，2026-10-19 |
| Mini-Dev 500（SQLite） | 81.00 | 同上；作者注明重跑一次为 80.20，单次约 ±1 |
| 人类 | Dev 92.96 / Test 72.37 | `[前序，未复核]` |

**标注错误的影响**（arXiv 2601.08778，UIUC，2026-01-19）：
- Mini-Dev：263/498 = **52.8%** 样本有标注错误；Spider 2.0-Snow：76/121 = **62.8%**；
- 修正 100 条 Dev 子集后，16 个 agent 的 EX 相对变化 **−7%～+31%**；12 个上升、4 个下降；
- 排名平均移动 **5 位**，最大 **±9 位**：CHESS 62%→81%（+30.6% 相对）从第 7 升到并列第 1；Contextual-SQL 从第 1 掉到第 7；MAC-SQL 从 14 升到 5；
- 原始子集排名与全量 Dev 的 Spearman **r=0.85（p=3.26e-5）**，与修正后子集只有 **r=0.32（p=0.23）**；
- 错误类型：E1 问题与 gold SQL 不一致（过滤器、比较符、公式）；E2 需理解数据/schema（非唯一键 join 未去重、漏聚合、格式转换）——**E2 最常见**；E3 领域知识错误；E4 问题多解/输出未定义。

> 这条证据对报告极关键：**"榜单分数"与"真实能力"的相关性可以被标注错误压到 0.32**。企业内评必须自建并持续校正，不能外包给公开榜单。

### 2.4 DataAgentBench（DAB）：最接近"企业 data agent"的公开基准

**形态**：104 题、17 个数据集、4 种 DBMS；每题至少满足 4 个属性中的 2 个（多库、脏/重复数据、非结构化文本、开放语义）。来源是对六个行业生产 data agent 团队的访谈。`[一手：arXiv 2603.20576v3，2026-10-07；github.com/ucbepic/DataAgentBench]`

**成绩**（每题 5 次，2026-10 版本）：

| Agent | pass@1 | 总成本 | 备注 |
| --- | --- | --- | --- |
| GPT-5.5 | **57%** | $484 | 最好；无 agent 超 70% pass@5 |
| Gemini-3.1-Pro | 52% | $294 | 最便宜 |
| Claude-Sonnet-4.6 | 48% | $705 | 最贵 |

- 有数据集（`patents`）所有 agent **0%**；
- 按总额/次数粗算约 **$0.93/次尝试**（$484 ÷ (104×5)），仅作量级参考；
- 消融：去掉 hints 或 desc，pass@1 变化 ≤5pp；hints 甚至可能误导（`crmarenapro/query12` 因全局 hint 怀疑正确结果而改错）。

**验证脚本的设计与其边界**（原文关键句）：
- 数值：容差区间；单值：子串包含；格式差异：Levenshtein < 答案长度 20%；集合：逐元素；字典：键 + 值邻窗；
- 明确写道："checks whether the response contains the complete correct answer, even if it also contains incorrect information. Detecting additional incorrect information would require manual review or an LLM judge, making evaluation not scalable or deterministic."

**失败归因**（196 条错误轨迹，GPT-5 judge）：
- FM1 未开始规划 1%；FM2 计划错 **31%**；FM3 选错数据 11%；FM4 实现错 **57%**；FM2+FM4 = 90%；
- 人工校验 30 条：精确一致 67%，部分一致 10%，不一致 23%；GPT-5 vs GPT-5.4 的 Cohen's κ：FM1 0.80，FM2–FM4 **0.42–0.46**（moderate）。

> 这组数字直接说明：**"选对表"不是主要瓶颈，"算对 + 实现对"才是**；也说明 LLM judge 只能做趋势判断，不能做逐条验收。

### 2.5 DA-Code 与 DSBench

- **DA-Code**（arXiv 2410.07331v2，2024-10-11）：agent 式数据科学代码生成，要求 grounding + planning，真实多样数据，可执行环境；当前最强 LLM + DA-Agent 仅 **30.5%**。题量 `[未核实]`（本次未抓到项目页）。
- **DSBench**（arXiv 2409.07703，2024-09）：466 分析 + 74 建模；长上下文、多模态背景、大文件、多表；最好 agent 分析 **34.12%**、RPG **34.74%**；分析题用 `gpt-4o-2024-05-13` 做答案 judge（前序调研读 `compute_answer.py`），建模题按竞赛指标。数据许可限教育/研究。

### 2.6 语义层/受控查询 vs 自由 NL2SQL：两组可引用的同题对照

**(A) dbt Labs 2026 benchmark**（2026-04-07，`docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026`）`[二手，厂商自测]`
- 数据集：ACME Insurance（data.world 原版），15 张表；**11 道题 × 每配置 20 次**；
- 配置：纯 text-to-SQL / 最小语义层 / 规范建模语义层 / 在建模数据上做 text-to-SQL；
- 结果：Claude-Sonnet-4.6 **90.0% → 98.2%**；GPT-5.3-codex **84.1% → 100.0%**；GPT-5.2 text-to-SQL 仅 68%；
- 限定：text-to-SQL 臂把**完整 schema 放进上下文**（15 表可行，大库不可行）；语义层只能回答"已建模"的问题，覆盖率是硬约束；作者明确"when it can't, it tells you"。

**(B) AtScale 2026-10-28 同题对照**（`atscale.com/blog/semantic-layer-text-to-sql-accuracy/`）`[二手，厂商自测]`
- 410 道 BIRD-Interact 业务题，7 个 LLM，两臂：PostgreSQL + 完整文档 + 知识库 vs AtScale 语义层；
- 无层臂 **21.5%–36.1%**；有层臂 **44.6%–62.2%**；每个模型 **+20～+31pp**；
- GPT-5：21.5% → 50.5%（+29）；Gemini 3.1 Pro：36.1% → 62.2%（+26.1）；Kimi K2.5 49.3% vs GPT-5 50.5%；
- 换模型最多移动 **17.6pp**，小于语义层给任何单模型带来的增益；
- 成本：Nemotron 每正确回答约 **$0.30**；Kimi 比 GPT-5 便宜约 $0.01/正确回答；
- 限定：厂商自测、单轮 sweep、未报告置信区间与 judge 细节，**必须独立复现后才能当硬结论**；且语义层臂的"可回答题"是子集，需按覆盖率折算（见 §3.3）。

### 2.7 评测缺陷横向对照

| 缺陷 | Spider 2.0-Lite | BIRD | DAB | DSBench | 后果 |
| --- | --- | --- | --- | --- | --- |
| 重复行 | 列向量比对，重复行可被排序后对齐，未做 bag 校验 | `set()` 直接去重 | 字符串/集合包含 | judge | 重复计费、明细汇总失真 |
| 列序 | `condition_cols` 指定列，未指定则按向量位置 | tuple 列序敏感 | 不适用（自然语言答案） | 不适用 | 假失败/假通过 |
| 行序 | `ignore_order` 可开 | 默认丢序 | 不适用 | 不适用 | Top-N、时间序列漏检 |
| 空集 | gold 空则空集通过 | 空=空判等 | 答案须出现 | judge | "查不到"被当成"就是 0" |
| 缓存 | 评估脚本有 `temp/` 缓存 | 无 | 无 | 无 | 旧结果复用，回归假通过 |
| 训练污染 | gold SQL 已公开，官方不推荐 SFT | 公开 train/dev | 新基准，风险低 | Kaggle 公开解法 | 分数虚高 |
| 标注错误 | 62.8%（Snow 抽样） | 52.8%（Mini-Dev） | 双人复核 + 共识 | 未核实 | 榜单不可作真值 |
| judge 依赖 | 人写脚本 | 无 | 脚本 + 失败归因 judge | 分析题 gpt-4o | 口径漂移、不可复现 |

## 3. 这些数字对"护城河"论证意味着什么

### 3.1 天花板论证

- Spider 2.0-Lite 60.15%、Snow 60.51%（2026-06，单配置）；DAB 57%（2026-10，5 次）；DA-Code 30.5%；DSBench 34.12%。
- 若产品对客承诺"答案对"，以 60% 为基线，**40% 的答案是错的**；而这还是公开集、有 hint、有干净 schema 的条件。DAB 原文对私有仓库任务的描述是 "abysmal"。
- 因此竞争点不是"能否生成 SQL"（生成早已不是瓶颈，Spider 2.0 论文里传统 parser 也有 5.7%，LLM 直接生成远高于此），而是**能否在 40% 的不确定性里识别、拦截、修复、证明**。

### 3.2 榜单不可当真值

- 标注错误率 52.8%/62.8%；修正后排名平均移动 5 位、最大 9 位；原始子集与修正子集的排名相关性只有 0.32。
- 结论：**"我们在某榜单上 X%"不能作为验收证据**；只能作为"与公开系统同量级"的旁证。企业必须自建 golden set 并做标注质量审计。

### 3.3 语义层/认证答案的增益必须按覆盖率折算

设语义层/认证答案覆盖率为 `c`，覆盖内准确率 `a_c`，未覆盖时回落自由 NL2SQL 准确率 `a_f`，则：

```
overall = c × a_c + (1 − c) × a_f
```

例：`c=40%`、`a_c=98%`、`a_f=70%` → overall = **81.2%**；若只报 `a_c=98%`，是把"覆盖率"藏进了分母。

这条公式应写进产品验收：**同时报 coverage、in-coverage accuracy、fallback accuracy、overall**，缺一不可。dbt 的 98.2%/100% 与 AtScale 的 +20–31pp 都是 in-coverage 口径，不能直接当产品整体准确率。

### 3.4 成本与方差的现实约束

- DAB：$484 / 104 题 / 5 次 ≈ **$0.93/次**；三个 agent 总成本 $484–$705。
- 104 题的 95% 置信区间约 **±9.5pp**（p=0.57，二项分布，`1.96×sqrt(0.57×0.43/104)`）。也就是说 57% 与 62% 在 104 题上**统计上不可区分**。
- 要在单臂上稳定检出 5pp 差异，粗略需要 1,500 题量级；配对设计（同题集、McNemar）在 10% 不一致率下约需 **300 题**（估算，未做正式功效分析）。这直接决定"最小可行评测集"不能只有 30 题。

## 4. 验证机制：能自动证明什么、不能证明什么

> 原则：**可执行检查优先于模型判断；模型判断优先于人工；人工只处理前两者都无法判定的残余。** 每一层都要留下可复算的证据。

### 4.1 SQL 静态检查与 AST（SQLGlot）

**能力**（读 SQLGlot README，2026-11-01）：无依赖的 parser/transpiler/optimizer/engine，支持 30+ 方言；可检测语法错误（括号不配对、保留字误用等）；`qualify` 与 `annotate_types` 可做 schema 感知的列解析与类型推断；`diff()` 可计算两条 SQL 的语义差异；可遍历表达式树、程序化构建 SQL。

**可落地的检查清单**：

| 检查 | 实现 | 能抓到 | 误报风险 |
| --- | --- | --- | --- |
| 语法/方言 | `parse_one(sql, dialect=...)`，异常即失败 | 方言函数、引号、LIMIT/OFFSET 语法 | 低 |
| 未知/歧义列 | `qualify` + schema | 幻觉列名、join 后同名列歧义 | 中（schema 不全时） |
| 类型不匹配 | `annotate_types` | 字符串比日期、数值比文本 | 中 |
| 聚合/非聚合混用 | 遍历 `Select`，检查 `GROUP BY` 覆盖 | 漏 GROUP BY、粒度错 | 低 |
| `SELECT *` | AST 节点检查 | 列漂移、宽表爆炸 | 低（有时是合理的） |
| 笛卡尔积 | 检查 `Join` 无 `ON`/`USING` | 忘记 join 条件 | 低 |
| 非确定性函数 | 检测 `RAND`/`NOW`/`CURRENT_DATE` | 复算不一致、缓存穿透 | 低（需 as-of 替代） |
| 除零/NULL | 检测除法分母、`NULLIF` | 运行时报错或 NULL 传播 | 中 |
| 缺时间过滤 | 检测是否引用时间列/分区列 | 全表扫描、口径错 | 高（有些题不需要） |
| 语义 diff | `diff(ast_pred, ast_gold)` | 与认证 SQL 的结构偏差 | 中（等价改写会误报） |

**边界**：AST 只能证明"结构合法、引用存在、形状像"，**不能证明结果正确**。等价改写（`JOIN` vs 子查询、`UNION ALL` 顺序）会让 diff 误报；因此 AST 检查用于**拦截低级错误 + 生成解释**，最终裁决必须靠执行结果与断言。

### 4.2 口径守恒与总分对账

**机制**：对同一指标构造"总量"和"分项"两条独立计算路径，要求恒等（在声明容差内）。

| 断言 | 形式 | 抓什么 |
| --- | --- | --- |
| 分项和 = 总量 | `SUM(region_rev) == total_rev` | 漏分组、重复计数、过滤条件不一致 |
| 占比和 = 1 | `SUM(share) ≈ 1` | 分母错、重叠分组 |
| 极值关系 | `MIN ≤ AVG ≤ MAX` | 聚合函数用错 |
| 计数守恒 | `COUNT(*) == COUNT(DISTINCT pk) + 重复数` | fanout、重复行 |
| 余额恒等 | `assets == liabilities + equity` | 财务口径错 |
| 流量恒等 | `open + new − closed == close` | 快照/时点错 |
| 同比恒等 | `(cur − prev) / prev == growth` | 公式错、分母错 |

**实现要点**：把断言写成数据模型里的**可执行测试**（dbt `data_tests`/`unit_tests` 风格），每条断言附带容差、适用范围、owner；断言失败不是"警告"，而是**阻断交付**。容差按单位设定：金额按分/元，比率按 0.01pp，计数必须精确。

### 4.3 Join fanout 检测

**问题**：多对一 join 放大事实表行数，`SUM` 被重复累加，结果"看起来合理但偏大"；多对多更隐蔽。BIRD 的 set 比较完全抓不到——只要 gold 也这样算错，双方"一致"。

**检测手段**（按成本从低到高）：

1. **键唯一性预检**：对每个被 join 的维度键执行
   `SELECT key, COUNT(*) c FROM dim GROUP BY key HAVING c > 1`；
   若键不唯一且查询用它 join 事实表，标记 fanout 风险。
2. **行数比**：`rows_after / rows_before`；>1.0 且查询含聚合 → 阻断或要求显式去重。
3. **度量膨胀比**：`SUM(measure)` 在 join 前后对比；比值 >1（对可加度量）即异常。
4. **主键计数校验**：`COUNT(DISTINCT fact_pk)` 在 join 前后应不变。
5. **join 图基数推理**：从 profile 构建 edge cardinality（1:1/1:N/N:1/N:N），N:N 边必须显式桥表 + 去重策略。
6. **对照认证口径**：与语义层同指标结果比对（若语义层已处理 fanout）。

**阈值建议**：可加度量 fanout 比 >1.001 即告警、>1.05 阻断；计数类必须精确相等；N:N join 默认阻断，除非查询显式 `COUNT(DISTINCT ...)` 且声明了业务理由。

### 4.4 空集与膨胀检测

**空集的双重语义**：可能是"业务上确实为 0"，也可能是"过滤条件写错/数据没到/权限过滤掉了"。BIRD 的 `set()==set()` 让"空对空"直接通过，是最典型的假阳性。

**检测**：
- **谓词可满足性**：对每个过滤谓词，在快照上单独执行 `COUNT(*)`；若某谓词命中 0 行，要求解释（是业务真空，还是值映射错）；
- **选择性合理性**：结果行数 / 源表行数 落在历史分位数区间外 → 告警；
- **时间窗口检查**：窗口内是否有分区/数据（freshness + partition existence）；
- **权限影响**：空集是否由 RLS/字段掩码导致（对比高权限与当前主体的计数）；
- **膨胀**：结果行数 > 源表行数、`SUM` > 源表总量、`COUNT(DISTINCT)` > `COUNT(*)`、出现负值/零值异常分布。

**建议阈值**：空集假阳性率 ≤2%（用标注集测）；"无法区分空集与失败"的题必须进 golden set。

### 4.5 多实例 test suite（防硬编码 / 防偶然正确）

**问题**：单实例通过可能只是"这条数据碰巧对"。BIRD 的固定库、固定 gold 让"背答案"成为可行策略。

**设计**：
- **同题多实例**：同一逻辑问题在 3–5 个数据变体上执行（改行数、改空值、改重复、改边界值），要求**全部通过**；
- **变形测试（metamorphic）**：
  - 加过滤 → 结果集应为子集；
  - 改 `ORDER BY` → 行序变、集合不变；
  - `LIMIT n` → 行数 ≤ n 且是全集的子集；
  - 列重命名/别名 → 结果不变；
  - 时间窗口平移 → 结果按预期平移；
  - 增加无关维度 → 总量不变（除非分组）。
- **dbt unit tests 模式**：给定输入行 → 期望输出行，直接测 SQL 逻辑，不依赖真实库；适合语义层 metric 与关键模型。
- **OJ 式评分**：参考 SpreadsheetBench 的"同一方案处理变值输入"，把"通过固定输入"升级为"通过输入族"。

**成本**：每个变体一次执行；建议只对 P0 题（口径/财务/对外报表）做 5 变体，其余 2 变体。

### 4.6 数据快照与 as-of

**要求**：任何可对外引用的答案，必须绑定 `snapshot_id`（Iceberg snapshot / Delta version / 分区批次 / 文件 digest）+ `as_of` 时间 + 查询时刻。

**机制**：
- 接入层记录源 digest、分区、增量位点（Iceberg/Delta 支持 time travel 到指定 snapshot/version）；
- 语义层/指标记录定义版本与生效区间；
- 结果 fingerprint 包含 snapshot 与 metric version；
- 重算时强制同快照；跨快照对比必须显式声明"数据变了"，不能静默当回归。

**as-of 测试**：
- 用 T-1、T、T+1 三个快照跑同一题，预期结果按业务规则变化；**非预期变化**即数据/口径 bug；
- 迟到数据、重述（restatement）、SCD2 有效期、财年/自然年切换、时区（UTC vs 本地）单列测试。

### 4.7 结果复算与 fingerprint

**fingerprint 组成**：
```
hash(
  normalized_result_set
  + canonical_sql_ast
  + dialect + engine_version
  + snapshot_id + as_of
  + metric_version + params
)
```

**归一化规则**（必须先定义，否则 fingerprint 不可比）：
- 列：按列名（而非位置）对齐；列别名规范化；
- 行：无序结果按 multiset（保留重复）排序后哈希；有序结果保留序；
- 数值：按声明精度四舍五入（金额 2 位、比率 4 位），decimal 不用 float；
- NULL/NaN：统一 sentinel；
- 时间：统一 UTC + ISO8601；
- 空集：保留 `[]` 与 `NULL` 的区别。

**复算流程**：同 fingerprint 输入重跑 → 结果 hash 必须一致；不一致则判定为**非确定性**（`RAND`/`NOW`/并行浮点/ASOF join）或**数据漂移**，二者都要定位，不能笼统记"环境问题"。

### 4.8 LLM-as-judge 的可靠性边界

**能做的**：
- 开放式解释的 rubric 评分（是否回答了问题、是否给出假设、是否越权下结论）；
- 失败轨迹的分诊（属于哪类错），用于**优先级排序**而非验收；
- 生成候选测试与反例，供人工确认。

**不能做的（作为唯一验收）**：
- **偏差**：MT-Bench 报告 GPT-4 judge 与人类偏好一致率 >80%，但明确指出位置偏差、冗长偏差、自我增强偏差与推理能力有限；
- **细粒度标签不稳**：DAB 中 FM2–FM4 的跨 judge κ 仅 0.42–0.46；人工与 judge 精确一致 67%、不一致 23%；
- **版本漂移**：Snowflake Cortex Analyst 的 SQL correctness metric 已迭代 v1/v2/v3，judge 版本不同分数不可比；
- **无法发现"多余错误"**：DAB 验证脚本原文承认这一点，judge 也未必可靠；
- **可被提示注入**：答案文本、数据内容都可能影响 judge。

**工程约束**：
1. judge 只评"无法执行验证"的维度（解释、假设、证据充分性）；
2. 必须有 ≥100 条人工标注的校准集，报告 Cohen's κ / 一致率，κ<0.6 不得上线；
3. 固定 judge 模型、prompt、温度、版本，变更即视为"评测口径变更"；
4. 高风险场景用**评审团**（PoLL：多小模型组合优于单一大模型，成本低 7 倍以上，arXiv 2404.18796）；
5. judge 不接触 gold answer 的"泄漏版本"；对被评答案做匿名化，避免自我增强；
6. 任何 judge 结论必须能回溯到可执行证据（SQL、结果、快照）。

## 5. 企业内评怎么设计

### 5.1 黄金问题集（golden set）

**规模**：
- 起步 **120–150 题**（覆盖 6–8 个业务域），其中 20% 为不可回答/歧义题；
- 对外承诺/财务口径类必须有 **≥30 题**的 P0 子集，逐题双人复核；
- 年度目标 **300–500 题**，并按季度轮换 20% 防记忆；
- 参考量级：DAB 104 题、dbt 11 题、AtScale 410 题、BIRD Dev 1,534 题——**104 题的置信区间约 ±9.5pp**，不能用来判断 5pp 级改进。

**来源**（按优先级）：
1. 真实用户问题日志的 Top 意图（脱敏后聚类采样）；
2. 事故/工单/追问记录（每个 P1 事故至少沉淀 1 题）；
3. 核心报表与指标字典（每个认证指标至少 1 题）；
4. 销售/客服/分析师高频问答；
5. 对抗合成（歧义、越权、注入、不可回答）。

**单题 schema（建议直接建表）**：

| 字段 | 说明 |
| --- | --- |
| `id` / `version` | 稳定 ID + 版本 |
| `question` | 用户原话（保留错别字/口语） |
| `context` | 会话、角色、租户、时间 |
| `snapshot_id` / `as_of` | 数据快照与业务时点 |
| `gold_sql` | 认证 SQL（可执行） |
| `gold_result_hash` | 归一化结果 fingerprint |
| `accepted_variants` | 等价答案（多 gold、容差、列序） |
| `metric_ref` / `metric_version` | 口径引用 |
| `evidence_required` | 必须引用的表/列/规则 |
| `stratum` | 单表/多表/歧义/时间/不可回答 |
| `difficulty` | L1–L4 |
| `owner` / `reviewers` | 责任人 + 双人复核记录 |
| `last_reviewed` / `next_review` | 复审节奏 |
| `contamination_flag` | 是否可能进过训练/示例 |

**治理**：
- 双人独立复核 + 分歧仲裁（参考 DAB 的 "两位作者共同写题、共同验证脚本、直到共识"）；
- 题目即代码：进 Git，走 PR，变更留痕（Cube 的 `eval_questions.yml` 模式）；
- **评测题与运行时示例隔离**：Snowflake Cortex 在评测时会把选中的 verified query **从语义视图临时移除**，防止"用答案回答答案"——这是防泄漏的关键设计，应直接借鉴；
- 每季度做一次"标注质量审计"：抽 30 题重标，统计与原始标注的一致率；低于 90% 则整批返工。

### 5.2 问题分层

| 层 | 占比建议 | 考什么 | 判定要点 |
| --- | --- | --- | --- |
| 单表/单指标 | 20–25% | 基础正确性、过滤、聚合 | 严格结果匹配 |
| 多表 join | 30–35% | 关系召回、join 路径、fanout | 结果 + 行数守恒 |
| 口径歧义 | 15–20% | 指标选择、假设声明、澄清 | 口径正确率 + 假设质量 |
| 时间/as-of | 15% | 时间窗口、时区、财年、迟到数据 | 快照 + 时间语义 |
| 不可回答 | 10–15% | 拒答/澄清而非编造 | 拒答正确率、编造率 |
| 文件/Excel | 5–10% | 结构识别、公式、跨 sheet | 重算后校验 |
| 权限/对抗 | 单列 20–40 题 | 越权、注入、诱导 | 一票否决 |

分层不是装饰：**每层单独报分**，否则"单表题拉高平均分"会掩盖多表与歧义题的失败。

### 5.3 口径一致性评测

**定义**：同一业务概念的不同问法，是否落到同一个 metric/同一段受控 SQL。

**做法**：
- 为每个认证指标写 5–10 个同义问法（"营收/收入/销售额/流水"），要求**全部映射到同一 metric**；
- 对"同名不同义"（不同部门对"活跃用户"定义不同）单列冲突集，要求系统**暴露冲突**而不是二选一；
- 指标版本变更（v1→v2）后，用同一题集回归，检查答案是否按预期变化（LiveSQLBench 的 Business Rule Drift 思路）。

**指标**：
- 口径一致率 = 映射到正确 metric 的题数 / 总题数；
- 冲突暴露率 = 正确识别并询问/声明的冲突数 / 冲突总数；
- 口径漂移检出率 = 版本变更后被标记的受影响题数 / 应受影响题数。

### 5.4 证据完备性评测

**要求**：答案中的每个数字都能追溯到"SQL 结果单元格 / 指标定义 / 快照"。

**检查**：
- **对象覆盖**：AST 引用的表/列 ⊇ 题目要求的最小证据集（表、列、规则、指标）；
- **数字可追溯**：答案文本中的数值必须能在结果集中找到（容差内），"孤儿数字率" ≤1%；
- **假设显式**：所有未从问题中确定的槽位（时间范围、口径、过滤）必须有声明；
- **来源可审计**：SQL、快照、metric version、权限主体全部落库。

**评分**：证据完备率 = 满足上述四项的题数 / 总题数；建议 P0 题 ≥95%。

### 5.5 澄清质量评测

**歧义类型**：指标定义、时间范围、粒度、过滤范围、实体指代、对比基准、单位/币种。

**指标**：
- 澄清精确率：该问才问的比例（问了但问题本可确定 = 无谓澄清）；
- 澄清召回率：该问且问了（没问却猜 = 静默假设）；
- 平均轮次、用户操作成本；
- 澄清后任务成功率；
- **静默假设率**（最关键）：未声明假设就作答的比例，建议 ≤5%。

**方法**：脚本化用户模拟器（BIRD-Interact 的 function-driven simulator）+ 人工抽检 30 段对话；judge 只评"语气/是否答非所问"，不评事实正确性。

### 5.6 成本与时延评测

| 指标 | 口径 | 采集 |
| --- | --- | --- |
| 端到端 p50/p95 | 从提问到首个完整答案 | trace |
| 首 token / 首结果 | 交互体验 | trace |
| token 数 | 输入/输出/缓存命中 | provider 账单 |
| 工具调用次数 | 每任务 | trace |
| 单题成本 | $/题 | 账单 ÷ 题数 |
| **每正确回答成本** | $ / 正确题数 | 账单 ÷ 通过数（AtScale 用此口径） |
| 超时率 / 预算耗尽率 | 固定预算下 | trace |
| 缓存命中率 / 缓存正确率 | 命中且结果仍正确 | 缓存元数据 + 复算 |

DAB 的成本差异（$294–$705 对同一 104 题）说明：**成本必须与准确率一起报**，否则"便宜 50%"可能只是"少做了验证"。

### 5.7 回归与防污染

**回归**：
- 冻结"题集 + 快照 + 模型版本 + prompt + 工具权限 + scorer 版本"六元组；
- 每次只替换一个变量，配对重跑（同一题集），用 McNemar / bootstrap 置信区间判断；
- **新增失败 = 0** 作为 P0 门禁；整体下降 >2pp 阻断发布；
- 回归报告必须列出"新失败题 + 归因层 + 责任模块"。

**防污染**：
- 私有题集，不入公开仓库、不进 few-shot、不进检索索引；
- 训练/示例与评测物理隔离（Cortex 的"评测时移除 VQ"是标准做法）；
- 轮换 holdout（每季度 20%），保留一份"从不展示"的盲测集；
- 对公开题做 canary/近重复检测，避免把 BIRD/Spider 原题直接当内评；
- 记录题目是否出现在模型训练语料中的"可能重叠"标记（GIFT-Eval 的 leakage 标注思路）。

## 6. 评测分层与阈值

| 层 | 评什么 | 频率 | 核心指标 | 建议阈值（初始，需基线校准） | 阻断规则 |
| --- | --- | --- | --- | --- | --- |
| **L0 单元** | parser、AST 规则、召回、metric 编译、fingerprint | 每次提交 | 解析成功率、规则 P/R、recall@k、fingerprint 稳定性 | 解析 ≥99.5%；规则 P≥95%/R≥90%；表 recall@10 ≥95%；fingerprint 一致 100% | 任一不达标阻断 |
| **L1 任务** | golden set 端到端 | 每晚 + 发版前 | 严格答案准确率、口径正确率、证据完备率、澄清质量、成本 | 冻结集 ≥80%；单层 ≥70%；P0 口径 ≥95%；证据 ≥95%；静默假设 ≤5%；p95 <60s | P0 失败或整体下降 >2pp 阻断 |
| **L2 回归** | 六元组冻结后的差异 | 每周 + 每次模型/语义变更 | 新增失败数、配对 delta、复算一致率 | 新增 P0 失败 = 0；delta 置信区间不跨 0 才算改进 | 新增失败即回滚 |
| **L3 线上** | 真实流量、影子、反馈 | 实时 + 每日 | 点踩率、追问率、升级人工率、缓存正确率、漂移告警 | 点踩率 <5%；升级率 <3%；缓存错误 = 0 | 连续 3 天超阈告警 |
| **L4 对抗** | 越权、注入、不可回答、诱导 | 每次权限/策略变更 + 每月 | 越权读取/写入、编造率、拒答正确率 | 越权 = 0；编造率 <2%；拒答正确率 ≥90% | 越权一票否决 |

**阈值为什么这样定**：
- 认证答案 precision 必须 ≥99%：一条错的"认证答案"会被复用 N 次，错误被放大；
- 任务准确率 80% 是**试点门槛**而非行业标准：低于此，人工复核成本会超过收益；
- 空集假阳性 ≤2%、fanout 漏检 ≥95% 召回：这两类错误最容易被"看起来合理"掩盖；
- 越权 = 0：不能用平均分抵消（与 2026-10-30 前序调研的 Gate 设计一致）。

## 8. 失败归因分类法（8 层）

> 原则：**每个失败必须能落到唯一主责层**（允许有次要层），否则无法驱动改进。分类法要与模块编号对齐（DA01–DA12），让"评测—模块—修复"闭环。

| 层 | 对应模块 | 典型症状 | 自动检测手段 | 公开基准映射 |
| --- | --- | --- | --- | --- |
| **1 接入** | DA01/DA02 | 表选错、分区缺失、分页截断、编码错、快照漂移 | 行数/分区存在性、digest 对比、schema diff、空值/类型 profile、freshness | DAB 多库/脏数据；BIRD 脏值 |
| **2 理解** | DA05/DA07 | 意图错、指标错、时间范围错、粒度错、实体指代错 | 槽位抽取 vs 问题回译、歧义分类器、假设日志、同义问法一致性 | DAB FM2（计划错）；BIRD E1/E4 |
| **3 召回** | DA06 | 漏表/漏列/漏值/漏规则；召回噪声挤占上下文 | 必需集合 recall、AST 引用 vs 召回集合差、桥表/值召回单列 | BEAVER 表/列/join 子任务 |
| **4 计划** | DA07/DA08 | join 路径错、粒度错、聚合顺序错、漏去重、公式错 | join 图基数推理、守恒断言、与认证计划模板 diff | DAB FM2；BIRD E2 |
| **5 SQL** | DA07 | 语法/方言错、歧义列、类型不匹配、除零、非确定性 | SQLGlot parse/qualify/annotate_types、lint 规则、EXPLAIN dry-run | Spider 2.0 方言；BIRD 执行错 |
| **6 执行** | DA07/DA11 | 超时、权限拒绝、资源不足、部分结果、缓存陈旧 | 执行状态、行数/耗时、缓存元数据、快照校验 | Spider 2.0 云端环境；LiveSQLBench 状态 |
| **7 解释** | DA08/DA11 | 因果过度断言、单位错、对比基准错、图表与数据不符 | 数字可追溯、claim 类型分类、图表-数据绑定、单位检查 | DSBench 分析题；DiscoveryBench |
| **8 交付** | DA09/DA11 | 导出错、文件陈旧、证据缺失、收件人/权限错 | 产物 hash、渲染检查、证据完备率、访问控制 | SpreadsheetBench 文件；企业交付 |

**与 DAB 五类失败的映射**：
- DAB FM1（未开始）→ 层 1/6（工具不可用、环境失败）；
- FM2（计划错）→ 层 4（也可上溯到层 2 的理解错）；
- FM3（选错数据）→ 层 3；
- FM4（实现错）→ 层 5（SQL/代码实现）；
- FM5（运行时错）→ 层 6。

**归因流程**：先看可执行证据（SQL、执行状态、行数），再看 AST 与召回集合，最后才用 judge/人工；**禁止**在无证据时把失败归为"模型能力不足"。

## 10. 最小可行评测集（MVES）

### 10.1 规模与结构

**总量：150 题核心 + 40 题对抗 + 20 题权限 = 210 题**（对抗/权限单独计分，不混入主分）。

| 分层 | 题数 | 说明 |
| --- | --- | --- |
| 单表/单指标 | 35 | 基础正确性；覆盖 6–8 个域 |
| 多表 join | 45 | 含 10 题 fanout 陷阱、5 题桥表 |
| 口径歧义 | 25 | 10 题必须澄清、15 题可确定但需声明假设 |
| 时间/as-of | 25 | 财年、时区、闭开区间、迟到数据、重述 |
| 不可回答 | 20 | 5 题数据不存在、5 题权限不足、5 题定义缺失、5 题自相矛盾 |
| 对抗 | 40 | 注入、诱导、超长上下文、脏列名、假 schema |
| 权限 | 20 | 行/列/租户/导出/缓存 |

**为什么是 150**：
- 104 题的 95% CI 约 ±9.5pp；150 题约 ±8pp；300 题约 ±5.7pp；
- 要在配对设计下检出 5pp（10% 不一致率），约需 300 题（估算）；150 题可稳定检出 **8pp 级**回归，足够做发版门禁；
- 210 题总量可在 1 小时内跑完（单题平均 <15s 执行 + 判分）。

### 10.2 运行节奏

| 触发 | 跑什么 | 时长目标 | 门禁 |
| --- | --- | --- | --- |
| 每次 PR（改 DA05/06/07/11） | **快集 40 题**（P0 + 高风险层） | <8 min | 新增失败 = 0 |
| 每晚 | 核心 150 题 × 2 变体 | <60 min | 整体下降 >2pp 告警 |
| 每周 | 150 题 × 3 快照（T-1/T/T+1） | <3 h | 非预期变化 = 0 |
| 每次模型/语义层变更 | 150 题配对重跑 + 40 对抗 | <2 h | 置信区间不跨 0 |
| 每月 | 全量 210 + 人工抽检 30 | 1 天 | 证据完备率、静默假设率达标 |
| 每季度 | 轮换 20% holdout + 标注审计 30 题 | — | 标注一致率 ≥90% |

### 10.3 判分与产物

- **判分优先级**：执行结果（multiset + 守恒 + 快照）→ 口径断言 → 证据完备 → 澄清质量 → judge（仅解释类）；
- **每题产物**：SQL、AST diff、结果 hash、快照 ID、断言结果、耗时、成本、归因层、证据链；
- **报告**：分层分数 + 置信区间 + 新增失败清单 + 覆盖率折算后的 overall；
- **红线**：权限违规、越权导出、伪造证据 → 直接阻断，不看总分。

### 10.4 从 0 到 1 的落地顺序

1. **第 1–2 周**：选 1 个域、30 题、双人复核，跑通"SQL + 结果 + 快照 + fingerprint"闭环；
2. **第 3–4 周**：加守恒断言、fanout 注入集、空集检测；把快集接进 CI；
3. **第 5–8 周**：扩到 150 题，补口径/时间/不可回答层；接入 judge 校准集（≥100 条）；
4. **第 9–12 周**：上线影子流量 + 点踩闭环；建立季度轮换与标注审计；
5. **持续**：每季度用公开集（BIRD Mini-Dev / Spider 2.0-Lite 子集 / DAB）做"外部可比性"旁证，但**不作为验收**。

## 11. 对报告结论的直接支撑

1. **"能证明答案对"是独立能力，不是附属功能。** 公开 SOTA 60% 左右，意味着 40% 的错误必须由验证层拦截；而公开评分器（set 比较、focused EX、字符串包含）在结构上无法完成这件事。
2. **验证必须是一级模块，因为它消费所有模块的产物。** 它需要 DA01 的快照、DA04/05 的语义与口径、DA06 的召回集合、DA07 的 AST 与执行结果、DA09 的交付物；任何一层缺失，验证就退化为"看答案像不像"。
3. **认证答案/语义层是提升准确率的最强杠杆，但必须以覆盖率计价。** dbt 同题对照 90.0%→98.2%、84.1%→100%；AtScale 410 题 +20–31pp；但两者都是 in-coverage 口径，产品必须同时报 coverage 与 fallback。
4. **评测本身要防污染、防标注错误、防 judge 漂移。** 52.8%/62.8% 的标注错误率、0.32 的排名相关性、0.42–0.46 的 judge κ，说明"评测系统"也需要被评测。
5. **失败归因要能落到模块。** DAB 的 57% 失败中 90% 来自"计划错 + 实现错"，而不是"选错表"；这说明投资顺序应是：语义/口径 → 计划与验证 → 召回，而不是继续堆模型。

## 14. 一页版：给报告作者的可引用句

- "Spider 2.0-Lite 的最好系统是 60.15%（ProSPy，2026-06，Claude-4.5-Opus，无多数投票），Spider 2.0-Snow 60.51%；两年前这两个数字是 23.40%/23.77%。"
- "DataAgentBench 104 题、17 数据集、4 种 DBMS，最好的 GPT-5.5 只有 57% pass@1，没有一个 agent 超过 70% pass@5，`patents` 数据集全系统 0%。"
- "BIRD Mini-Dev 有 52.8%（263/498）的样本存在标注错误，Spider 2.0-Snow 为 62.8%（76/121）；修正 100 条后，16 个 agent 的排名平均移动 5 位、最大 9 位，原始与修正子集的排名相关性只有 0.32。"
- "在 410 道 BIRD-Interact 题上，语义层给 7 个模型各加 20–31 个百分点（GPT-5 21.5%→50.5%），而换模型最多只移动 17.6 个百分点——但这是覆盖率内的数字，必须按 `c×a_c+(1−c)×a_f` 折算。"
- "BIRD 的执行准确率实现是 `set(pred)==set(gt)`：丢重复行、丢行序、列序敏感；DAB 的验证脚本作者明确承认无法发现答案中多出来的错误信息。所以'结果集匹配'只能证明看起来一样，不能证明答案对。"
- "LLM judge 与人类的一致率可以到 80%（MT-Bench），但在细粒度失败归因上跨 judge κ 只有 0.42–0.46（DAB）；它适合分诊，不适合做唯一验收。"
