## 0. 结论摘要（可直接引用的判断）

1. **语义资产不是"文档"，是"有 owner 的代码"**。dbt 的 `groups` 机制要求每个组必须有 `owner`（且示例中直接出现 `data_owner: Finance team`），CI 在每个 PR 上跑测试——语义维护因此天然是"PR + owner 审批"的工程流程，而不是"知识库编辑"流程。`[事实]`
2. **企业级 text-to-SQL 的瓶颈从建模转移到"元数据认证"**。LinkedIn 的做法是先做 dataset certification：由领域专家圈定关键表，补必填表描述与可选字段描述，再叠加 AI 生成的注释；覆盖对象是"数百张重要表"，而不是全量数百万张表。`[自报]`
3. **评测的最小可行规模远小于直觉**。LinkedIn 用 10 个产品域、130+ 道题；Uber 的金标题集来自真实日志问题并人工核对 intent/表/金标 SQL，单题记录 5 类信号。两家都不是"几千题"。`[自报]`
4. **回归节奏由两类时钟叠加**：机器时钟（每个 PR/每次模型或 prompt 变更跑 CI）与人的时钟（季度专家复核）。LinkedIn 明确"每 3 个月专家复核并补充可接受答案"。`[自报]`
5. **采用率的第一驱动是入口位置，不是模型能力**。LinkedIn 把 SQL Bot 嵌进既有 DARWIN IDE 后，采用率相对独立原型应用提升 5–10 倍；"Fix with AI"（报错即修）占其会话的 80%。`[自报]`
6. **计费口径已经分化**：按消息/查询（Snowflake Cortex Analyst、Databricks Genie、BigQuery）、按容量（Microsoft Fabric Copilot 绑定 F2+ 容量）、按 token（直连 API）。同一句自然语言问题在不同云上的成本可差一个数量级，采购时必须对齐"每成功回答成本"。`[事实]`
7. **中文场景不会改变模块清单，但会改变优先级顺序**：口径治理与维值/编码映射要前置到"语义层"之前，Excel 交付与"报表复核"要作为一等交付物，出境合规要作为部署架构的硬约束。`[推断]`

## 1. 角色—职责—交付物

### 1.1 六个角色（含证据强度）

| 角色 | 一句话定位 | 语义维护 | 验收 | bad case 处理 | 关键交付物 | 证据 |
|---|---|---|---|---|---|---|
| **Data Owner**（数据/域负责人） | 对"这张表/这个域的数据能不能被外部使用"负责 | 决定哪些表进入"认证清单"；批准字段级敏感标记 | 签署域级上线（表可用性、权限、口径边界） | 判定"是数据错还是语义错"，决定是否回滚 | 认证表清单、数据契约、域级 SLA | dbt groups `owner` / `data_owner`；LinkedIn"领域专家圈定关键表" `[事实]`/`[自报]` |
| **Analytics Engineer**（分析工程师） | 把业务口径写成可测试的模型与指标 | 主要建设者：语义模型、指标定义、测试、 exposures | 提交 PR + CI 通过 + 上游 owner 评审 | 修模型/加测试/加唯一性约束；复现并归档 | dbt 模型、指标 YAML、测试、CI 报告 | dbt CI "每个 PR 触发，只跑变更模型" `[事实]` |
| **Data Steward**（数据管家） | 元数据质量与"可发现性"的守门人 | 补描述、同义词、Top-K 维值、废弃标记 | 元数据完整度验收（描述覆盖率） | 分诊：缺描述/缺同义词/维值缺失 → 派单 | 元数据字典、术语表、废弃清单 | LinkedIn 用 DataHub 的 deprecated 标记自动下线；"描述缺失是主要障碍" `[自报]` |
| **Metric Owner**（指标 owner） | 单个指标的"唯一签字人" | 定义分子分母、过滤、时间窗、版本号 | 指标认证（certified）与变更评审 | 判定"口径变更 vs 口径误解"，发布变更通告 | 指标卡（定义+示例+反例+owner+版本） | dbt"集中定义指标以保证治理与一致性"；认证/废弃属推断的行业做法 `[事实]`+`[推断]` |
| **AI 产品经理** | 决定"哪些问题值得让 Agent 答" | 不写定义，但拥有"问题域边界"与优先级 | 组织 UAT、定义验收阈值（如表格召回率） | 归类 bad case 为"产品缺口/语义缺口/模型缺口" | 问题域清单、验收标准、路线图 | Uber"要在初期就锁定正确 persona"（自述经验）`[自报]` |
| **Agent/平台工程师** | 检索、编排、校验、可观测性 | 提供语义资产的消费接口（不拥有内容） | 回归结果、延迟/成本达标 | 修检索与校验器；把 bad case 变成回归用例 | 检索管线、校验器、评测流水线 | Uber 的 intent/table/column-prune 三 agent；LinkedIn 的 validators + self-correction `[自报]` |

**关键分工原则（推断，有证据支撑）**：
- **"定义权"与"实现权"分离**：Metric Owner 签字、Analytics Engineer 实现、CI 守护。dbt 的 group owner + PR CI 是这一分离的现成机制。
- **"认证"是 Data Owner 的动作，"描述"是 Steward 的动作**。LinkedIn 把两者拆开：专家圈表（owner 权），专家写描述（steward 活），AI 补注释（工具降本）。
- **bad case 的三分法**必须有明确归属，否则会全部堆给平台团队：语义缺口→Metric Owner/AE；元数据缺口→Steward；产品/交互缺口→AI PM。Uber 的做法是把 bad case 拆成 intent / table / column / SQL 四层分别记分，天然对应四个 owner。`[推断]`

### 1.2 责任边界容易踩的三个坑（反模式，见 §8 详述）

1. **把 Steward 当"文档写手"**：只补描述、不参与废弃决策，结果是"描述写完了，表已经换了"（LinkedIn 明确表会被替换、source of truth 会迁移）。`[自报]`
2. **把 AI PM 当"需求转述者"**：不拥有问题域边界，导致 Agent 被要求回答"全公司所有问题"，评测集无法收敛（Uber 明说无法覆盖全部业务问题，只能覆盖"当前使用形态"）。`[自报]`
3. **让平台团队兼任 Metric Owner**：平台团队无业务签字权，指标一变就要返工，且无法拒绝不合理需求。

## 2. 语义/指标运营：流程、RACI 与节奏

### 2.1 六阶段流程（提名 → 采集 → 生成 → 审核 → 发布 → 废弃）

| 阶段 | 具体动作 | 提名权 | 审批（A） | 交付物 | 建议节奏 | 证据 |
|---|---|---|---|---|---|---|
| **① 提名** | 从问题日志/高频查询/考核报表中提取候选指标与候选表 | 任何人可提名；AI PM 汇总排序 | Data Owner（域级） | 候选清单（含预期使用方、频率、是否进考核） | 双周收集，月度定档 | Uber 金标题集"来自真实日志问题"；LinkedIn 用访问热度把百万表收敛到数千 `[自报]` |
| **② 采集** | 找定义、找口径分歧、找历史报表、找 Top-K 维值 | Steward 主导 | Steward 组长 | 口径卡初稿（含"现存 N 种算法"对照） | 单指标 ≤ 3 个工作日 | 推断（无公开流程文档）|
| **③ 生成** | 写 YAML/模型/指标定义 + 测试 + 示例问题 | Analytics Engineer | AE lead（技术） | PR（模型+指标+测试+示例） | 跟随双周迭代 | dbt MetricFlow"集中定义、避免重复编码" `[事实]` |
| **④ 审核** | 业务口径评审（"口径会"）+ 技术评审（CI） | — | **Metric Owner 签字** + AE lead | 评审记录、变更说明、影响面清单 | 周会 30–60 min 批量审 | dbt CI 每 PR 跑测试；群组 owner 审批 `[事实]` |
| **⑤ 发布** | 标记 certified、登记到语义库、同步给 BI/Agent、公告 | — | Data Owner（对外可见性） | 认证指标卡 + 发布通告 + 消费方清单 | 每月一次集中发布窗口 | 推断；LinkedIn 用"certified"标签在 UI 展示 `[自报]` |
| **⑥ 废弃** | 标 deprecated、给替代品、设 sunset 日期、通知消费方 | 任何人 | 原 Metric Owner | 废弃公告 + 迁移指引 | 季度清理 | LinkedIn/DataHub deprecated 信号自动下线；dbt 侧用 exposures 找消费方 `[自报]`/`[事实]` |

**RACI 矩阵（按角色 × 阶段，R=执行 A=签字 C=咨询 I=知会）**

| 阶段 | Data Owner | Analytics Eng | Data Steward | Metric Owner | AI PM | 平台工程师 |
|---|---|---|---|---|---|---|
| 提名 | A（域级） | C | C | C | **R**（汇总排序） | I |
| 采集 | C | C | **R/A** | C | I | I |
| 生成 | I | **R/A** | C | C | I | C |
| 审核 | C | R | C | **A** | C | I |
| 发布 | **A** | R | C | R | I | C |
| 废弃 | C | R | C | **A** | I | C |

> 注：RACI 为**建议设计**（`[推断]`），不是任何被调研企业的公开制度。可核对的锚点只有两处：dbt 要求 group 有 owner 且 PR 走 CI；LinkedIn 由领域专家承担表级认证与描述。

### 2.2 "多少指标值得认证"——给一个可辩护的区间

公开材料里**没有任何一家给出"认证指标数量/总指标数量"的比例**（`[未取得]`）。但三条可比数字可以约束量级：

- LinkedIn：全库"数百万张表"，按访问热度收敛到"数千张"，最终只对**数百张**做认证描述。→ 认证率约为"热门表的 10% 量级"。`[自报]`
- Uber：首版只放 **7 张一级表 + 20 条 SQL 样例**，后续扩到 Mobility + 11 个系统工作区。→ 起步是"十几个域、几十张表"。`[自报]`
- Pinterest：blog 原文未取得（Medium 抓取被 TLS 拦截），仅取得镜像摘要，**不给数字**。`[未取得]`

**建议判据（推断，可直接写进报告）**：一个指标值得"认证"（即投入 owner 时间 + 进 Agent 召回白名单），当且仅当满足以下 ≥2 条：
1. 月度被 ≥3 个部门消费；
2. 进入考核/对外披露/合同结算；
3. 在问题日志中出现频次进入前 20%；
4. 存在 ≥2 种互相冲突的现行算法（即"口径歧义"已经被观察到）；
5. 是 Agent 高频召回对象（可从检索日志统计）。

按此判据，一个万人体量的企业，**首批认证 80–200 个指标 / 30–80 张核心表**是可执行区间；把全量指标（常见数千至数万）都认证，投入产出不成立。`[推断]`

### 2.3 认证成本与维护成本：能公开核对的部分

| 成本项 | 可核对证据 | 结论 |
|---|---|---|
| 单指标认证人力 | 无公开数字 `[未取得]` | 只能用"人时"自建口径：采集 0.5–1 人日 + 评审 0.2 人日 + 实现 0.5–1 人日 + 测试 0.5 人日 ≈ **1.5–3 人日/指标**（推断，按 dbt 侧工作拆解） |
| 维护（口径变更） | dbt CI 每次 PR 全量回归，只跑变更节点 | 变更成本主要在"影响面确认"（exposures 查询），不在写 SQL `[事实]` |
| 元数据维护 | LinkedIn：描述缺失是检索主要障碍，需 AI 辅助生成注释 | 描述类工作可用 LLM 降本，但**必填项仍需人签字** `[自报]` |
| 工具成本 | dbt / 语义层 / 目录工具均按席位或按模型数计费 | 未取得可核对价目 `[未取得]` |

## 3. 评测运营的最小可行流程（MVP）

### 3.1 流程表

| 环节 | 谁做 | 规模/频率（公开锚点） | 产出 | 证据 |
|---|---|---|---|---|
| **出题** | 领域专家（不是平台团队）按产品域出题 | LinkedIn：10 个产品域、**130+ 题**，每题含问题 + 金标答案 | 题集 v0 | `[自报]` |
| **标注** | 专家给金标 SQL + **多个可接受答案** | 约 **60%** 的题存在多解；不加多解会低估召回 10–15% | 金标 + 备选答案集 | `[自报]` |
| **评分维度** | 机器可算的先行：表/字段召回、幻觉率、语法正确率、延迟；再加人评/LLM-judge 的总体分 | Uber：intent / table overlap / 成功执行 / 有结果 / 与金标相似度 5 类信号 | 每次运行的分项分 | `[自报]` |
| **回归触发** | 每个 PR / 每次 prompt、模型、检索参数变更 | dbt：PR 触发 CI，只跑变更模型 | CI 报告 | `[事实]` |
| **人工复核** | 专家季度复核，补"被判定为等价"的新答案 | LinkedIn：**每 3 个月**一次 | 题集 v1..vn | `[自报]` |
| **bad case 入集** | 从线上日志捞真实问题 → 人工确认金标 → 入回归集 | Uber：金标题集"来自 QueryGPT 日志的真实问题，人工核验 intent/schema/金标 SQL"，并随产品方向演进 | 题集增量 | `[自报]` |
| **噪声容忍** | 设定非确定性容忍带，不因小波动改决策 | Uber：**约 5%** 的运行间波动不作为决策依据，看长周期错误模式 | 趋势看板 | `[自报]` |

### 3.2 最小可行配置（推断，给落地用）

- **题量**：**80–150 题**即可上线第一版（LinkedIn 130+ 的同类量级），按"产品域 × 问题类型"分层，每层 ≥8 题；不要追求覆盖全库。
- **人**：每域 1 名出题专家（兼职），1 名评测 owner（全职 0.3–0.5），1 名平台工程师维护流水线。
- **频率**：CI 每 PR（自动）；人工抽检**每周 10–20 条线上 bad case**；全量人评**每月 1 次**；题集结构复核**每季度 1 次**。
- **门槛（建议写进验收）**：表召回 ≥0.9、字段召回 ≥0.85、幻觉率 ≤2%、P95 延迟 ≤15s、人工"Passes 及以上" ≥90%（LinkedIn 自报 95% pass，可作对标）。`[推断]`+`[自报]`
- **bad case 分流字段**：`问题类型 / 失败层（intent·表·字段·SQL·数据）/ 归属 owner / 是否入集 / 修复版本`。Uber 的分层记分是这一字段设计的直接依据。

## 4. 采用与推广：从 pilot 到规模化的门槛

### 4.1 可核对数字与口径

| 指标 | 数字 | 口径（重要） | 证据 |
|---|---|---|---|
| Uber QueryGPT | 受限发布阶段约 **300 DAU**；**78%** 表示减少了写查询时间 | "limited release to some teams in Operations and Support"；分母是**使用者自评**，不是全体目标用户 | `[自报]` |
| Uber 基线 | 平台每月约 **120 万**交互式查询；Operations 占 **36%**；单查询约 10 分钟 → 约 3 分钟 | 时长来自保守估计，非计时实验 | `[自报]` |
| LinkedIn SQL Bot | 相对独立原型应用，嵌入 DARWIN 后采用率 **5–10×**；"Fix with AI" 占 **80%** 会话；**95%** 评"Passes 及以上"，**40%** 评"Very Good/Excellent"；使用者"数百人" | 采用率是**相对倍数**，无绝对渗透率分母；满意度为问卷自评 | `[自报]` |

**没有公开的"权限开通比例"门槛数字**（`[未取得]`）。LinkedIn 只描述了机制：校验用户是否属于有权限的组，并自动给出使用组凭证的代码，以减少"跑到一半被拒"的挫败。`[自报]`

### 4.2 规模化门槛（推断，可按此设 gate）

| Gate | 判据 | 依据 |
|---|---|---|
| G0 场景选择 | 单一 persona + 单一域，日活 ≥20，周留存 ≥40% | Uber"初期锁定正确 persona" `[自报]` |
| G1 入口 | 已嵌入既有工作台（不是独立站点），入口 ≥2 处（侧栏 + 报错即修） | LinkedIn 5–10× 差异 `[自报]` |
| G2 权限 | 行/列权限可继承组织权限，越权拒绝率 <1%，开通走自助而非工单 | LinkedIn 组凭证自动注入 `[自报]` |
| G3 信任 | 评审通过率 ≥90%，且"答案可追溯"（展示所用表、口径、SQL） | LinkedIn UI 展示 certified/popular 标签与校验结果 `[自报]` |
| G4 成本 | 每成功回答成本 < 人工答疑成本的 1/3 | 推断（Uber 10min→3min 的替代口径） |
| G5 组织 | 每域有 1 名 owner + 1 名 champion 承接语义维护 | LinkedIn"识别 champion 主导自助式 context curation" `[自报]` |

## 5. 成本结构与定价模式

### 5.1 成本构成（按模块）

| 成本项 | 驱动因子 | 量级/证据 | 标签 |
|---|---|---|---|
| LLM token | 每次调用的上下文长度（schema + 样例 + 历史） | Uber 单张大表 schema 可达 **40–60K token**，3 张即撑爆 32K 窗口 → 催生 column-prune agent，直接降 token 与延迟 | `[自报]` |
| 查询/消息计费 | 按消息数（与 token 无关） | Snowflake Cortex Analyst：按消息数计费，**仅 HTTP 200 成功响应计数**；token 数只在经 Cortex Agents 调用时影响成本 | `[事实]` |
| 仓库算力 | 执行生成的 SQL | Cortex Analyst 明确"AI 费用之外另计仓库成本" | `[事实]` |
| 容量/CU | 平台容量档位 | Microsoft Fabric Copilot：随 F2+ 容量启用，消耗容量，过量会限流；Azure OpenAI 仅部署在 US/EU，区域外默认禁用需管理员开启 | `[事实]` |
| 存储 | 语义资产、题集、日志、trace | 量级远小于 token；BigQuery 同页给出活跃/长期存储两档价目（长期档约半价） | `[事实]` |
| 人力 | 认证/评审/评测/答疑 | 单指标 1.5–3 人日；评测 owner 0.3–0.5 FTE | `[推断]` |

### 5.3 私有化 vs SaaS（推断，无公开价目）

| 维度 | SaaS | 私有化/专有云 |
|---|---|---|
| 主要成本 | token/消息费 + 容量 | GPU/算力折旧 + 运维人力 + 模型许可 |
| 边际成本 | 近零、随用量 | 台阶式（扩容要买卡） |
| 语义资产归属 | 常在厂商侧，导出受限 | 完全自有，便于审计 |
| 出境合规 | 受厂商区域限制（如 Fabric Copilot 仅 US/EU 处理） | 天然境内闭环，是强监管行业的默认选项 |
| 迭代速度 | 厂商季度更新 | 自控，但需自建评测 |
| 结论 | 中小企业/非敏感域优先 | 金融、医疗、政务、跨境数据默认 |

> 成本优化的三个高杠杆点（有据）：**剪枝上下文**（Uber column-prune）、**按需路由小模型**（推断）、**把成功问答缓存成样例**（LinkedIn 把 certified notebook 作为 example query 入检索）。`[自报]`

## 6. 中文企业场景 → 模块优先级影响清单

| # | 中文场景特征 | 对模块优先级的影响 | 证据/标签 |
|---|---|---|---|
| 1 | **口径歧义与"口径会"**：同一"销售额/活跃用户"在财务、业务、区域三套算法并存，评审靠开会拍板 | "语义层/指标定义"模块**前置**，且必须有"版本 + 变更通告 + 多算法对照"能力；"口径会"应产品化为"指标评审工作流" | 阿里云 Quick BI 将"统一口径"与"AI-ready 语义层"列为产品底座能力 `[自报]`；"口径会"本身未见公开研究 `[未取得]`→`[推断]` |
| 2 | **报表文化**：决策仍以固定报表/看板为主，"问数"是补充而非替代 | "报告/看板生成"与"定时推送"优先级高于"多轮自由对话"；Agent 需能**回填到既有报表** | 推断（Quick BI 强调"对话生成看板/报告"、主动巡检推送）`[自报]` |
| 3 | **Excel 交付**：最终交付物常是 xlsx，含合并单元格、手写备注、二次加工 | "结果导出/Excel 友好"是一等能力：多 sheet、保留格式、公式可追溯；不能只给图表 | 推断（中文企业普遍实践，公开量化证据未取得）`[推断]` |
| 4 | **维值编码**：组织中台用编码而非名称（如组织编码、物料码、渠道码），且编码有历史版本 | "维值/编码映射"必须独立成模块（不是语义层的附庸），需支持码表版本、一对多、失效码 | 推断；LinkedIn 侧对应"Top-K 维度值 + 字段分类"入知识图谱，可作参照 `[自报]` |
| 5 | **监管与数据出境**：重要数据识别、出境评估、自贸区负面清单 | "部署架构/权限审计"成为**硬约束前置项**：默认境内闭环、行列级权限、全链路留痕；SaaS 方案需先过合规 | 《促进和规范数据跨境流动规定》（2024-03-22）：重要数据出境须申报评估；非 CIIO 累计向境外提供 ≥100 万人个人信息（或 ≥1 万人敏感个人信息）须评估；自贸区可设负面清单 `[事实]` |
| 6 | **权限即组织**：数据权限按部门/条线授予，跨部门取数靠审批 | 检索阶段就要做"权限感知召回"（先过滤再检索），否则答案不可执行 | LinkedIn：按组织架构推断默认数据集、按组凭证授权 `[自报]`→`[推断]` |
| 7 | **审计与"谁说的"**：需要能回答"这个数字依据什么口径、谁签的字" | "血缘 + 认证标记 + SQL 解释"必须默认展示，且可导出为审计包 | LinkedIn UI 展示 certified 标签、所用表、校验结果 `[自报]` |
| 8 | **私有化偏好**：金融/央企倾向本地部署、信创适配 | 模型可替换（多模型路由）、离线评测、无外网依赖成为选型门槛 | Quick BI 提"权限信创可控" `[自报]`；其余为 `[推断]` |

**优先级结论（推断）**：中文场景下的模块顺序应调整为
`权限与合规 → 语义/指标（含口径版本与维值编码） → 检索与校验 → 结果交付（Excel/报表/推送） → 多轮对话与深度分析`，
而英文公开案例（Uber/LinkedIn）的顺序更接近 `检索与校验 → 语义 → 交互`。差异的根源是：**中文企业的"答案"要能被复核、被审计、被贴进报表**，而不仅是"当场可用"。
