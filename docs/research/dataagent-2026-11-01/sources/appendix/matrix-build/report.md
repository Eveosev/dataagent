# DataAgent 模块化能力拆分调研报告

> **一句话结论：** 狭义 DataAgent 的模块化不是“把 12 个模块都建一遍”，而是用少量自研核心能力（9 项）串起一条可验证闭环，其余能力通过集成、薄封装与 AgentOS 复用；广义 General DataAgent 也不是“功能变多”，而是三次相变——**任务状态变资产、只读变写入、一次调用变持续运行**——每次相变都要求横向契约升级。
>
> 本报告基于[当前 DataAgent Brainstorm 文档](https://modelbest.feishu.cn/docx/TlN4dygs9oJR3Qx1FaictiPEn3c)（document revision 272）、本仓库此前三轮 DataAgent 调研，以及本轮六个方向的补充调研。它回答三个问题：狭义阶段哪些能力亟需建设、广义阶段哪些能力是“扩展”、哪些是“补充”。

## 0. 摘要

### 0.1 三个问题的直接回答

| 问题 | 回答 | 关键数字 |
| --- | --- | --- |
| 狭义 DataAgent 哪些能力亟需建设？ | 30 项 P0，分三道闸门：**闭环** 27 项、**信任** 1 项、**规模** 2 项；其中真正需要自研的只有 16 项，**核心自研（护城河）9 项**。第一批只做 21 项，即可打通单业务域的可信问数闭环。 | 30 P0 / 21 首批 / 9 核心自研 |
| 广义 General DataAgent 哪些能力需要**扩展**？ | 11 个既有模块的边界变大，共 61 项二级能力的形态或阈值发生变化。最关键是四类：接入从“读一次”到“持续同步”、语义从“复用”到“生产与运维”、验证从“单次校验”到“质量门禁”、交付从“一次性产物”到“持续刷新与订阅”。 | 61 项扩展 / 11 个模块 |
| 广义需要**补充**哪些能力？ | 四类：① 两个横向契约模块（DA13 运行态与成本、DA14 资产图与血缘）；② 两个纵向模块（DA10 预测/仿真/优化、DA15 建模/转换/调度）；③ 30 项狭义不存在的二级能力（持续接入、修复写回、实体解析、语义发布、漂移监测、影响面等）；④ 一个共同的接口缺口：可审阅的变更计划（plan/diff/dry-run）。 | 4 个新模块 + 30 项新能力 |

### 0.2 十条判断

1. **模块不是越多越好。** 15 个一级模块里，只有 8 个（DA01/DA02/DA05/DA06/DA07/DA09/DA11/DA12 的核心项）进入首个闭环；DA03/DA04/DA08/DA10 在狭义阶段可以“轻量存在”甚至不做。
2. **“必须有”不等于“必须自研”。** 30 项 P0 中 14 项可集成、薄封装或由 AgentOS 提供；把可复用件重写一遍，是这类项目最常见的浪费。
3. **真正的护城河只有 9 项**：语义编译、多入口检索、反向定位、证据契约、候选绑定、语义优先策略、查询验证、口径验证、黄金集回归。它们决定“答案对不对、能不能被审计”。
4. **语义层是最高杠杆，但不是“先建全量指标”。** 20 个指标 × 3 个维度 × 2 个时间角色通常覆盖 80% 的高频问题；剩下的长尾靠“任务级临时定义 + 来源标注”兜住。
5. **固定五段式检索（理解→表→规则→列→值）是错的。** 第一步选错表就不可恢复。正确做法是多入口进入 + 维护候选与缺口 + 按证据决定下一步 + 可回退。
6. **验证必须是独立模块。** 模型自评、用户点赞、SQL 执行成功都不能当验收；验证项要与失败模式一一对应，并输出可审计的“证据包”。
7. **广义的门槛不是功能数量，而是三次相变。** 任务状态→资产、只读→写入、一次调用→持续运行；每次相变都会新增横向契约（身份/版本/审批/幂等/调度/成本），这不是“再加一个模块”能解决的。
8. **资产化的核心是发布权。** 谁能把一次回答提升为企业事实？没有 `proposal → review → release → deprecate` 的状态机，反馈越多，污染越快。
9. **评测是最容易被推迟、也最不该推迟的模块。** 没有一套百题级黄金集，任何一次语义、检索或模型改动都无法判断是变好还是变坏。
10. **模块化有四条硬判据：单一事实源、可替换、可独立评测、故障可隔离。** 不满足这四条的，是功能，不是模块。

### 0.3 能力地图（一页纸）

```text
狭义闭环   DA01 接入 ─► DA02 探查 ─► DA05 语义 ─► DA06 检索
           ─► DA07 问数 ─► DA11 验证 ─► DA09 交付

```

## 1. 研究问题、范围与方法

### 1.1 三个问题

本轮不做产品选型，也不做实施排期，只回答三个决策问题：

1. **狭义**：如果只做“问题 → 答案”，哪些能力是缺失即不可用的？哪些可以集成、哪些必须自研？
2. **广义扩展**：同一批模块在“持续建设并运行数据工作”时，哪些边界会变大？变大之后，哪些契约必须先升级？
3. **广义补充**：哪些能力在狭义阶段根本不存在，必须新增模块或新增能力族？

### 1.2 概念基线

Brainstorm 文档给出的定义是：DataAgent 是以数据及其语义为主要工作对象，完成理解、计算、分析和结果交付，并可沉淀、维护可复用数据资产的智能体；狭义产品聚焦“问题到答案”，广义体系则按需覆盖数据准备、语义建设、深度分析和持续迭代运行。

文档用四行对照刻画了两者的差异，本报告完全沿用这一基线：

| 维度 | 狭义 DataAgent | 广义 General DataAgent |
| --- | --- | --- |
| 目标 | 基于当前输入回答问题、完成分析 | 建立、维护并持续运行一段时间内的数据工作 |
| 数据 | 给定数据库：任务内数据探查 | 无数据库：整合来源、处理数据、检测质量与身份对齐、维护关系，同时构建数据库 |
| 语义 | 给定语义库：召回正确语义资产，必要时局部解释 | 构造、验证、发布、维护可复用语义，解决冲突与变化 |
| 交付物 | 答案、SQL、图表、报告 | 数据库、语义层资产、分析流程、预测方法/模型等资产 |

**本报告的一个基本判断是：两者不是两个产品，而是同一条资产链上的两个阶段。** 狭义阶段的每一次高质量回答，都是广义阶段的资产原料；广义阶段的每一份资产，又反过来降低狭义阶段的边际成本。模块化设计必须让这条链“可回流”，而不是让两个阶段各建一套。

### 1.3 方法

本报告采用“先定判据、再拆能力、最后定优先级”的顺序，避免直接从功能清单出发：

1. **定义模块判据**（§3）：单一事实源、可替换、可独立评测、故障可隔离。
2. **拆一级模块**（§4）：按“事实所有权 + 变更频率 + 故障域”划分，而不是按页面、角色或团队。
3. **拆二级能力**（§5）：每项能力给出输入/输出、不变量、失败语义、验收口径。
4. **定优先级**（§6）：三道闸门（闭环/信任/规模）+ 五维评分（阻断度、复用度、广义依赖、成本、稀缺性）。
5. **判广义形态**（§7）：逐模块判定“扩展 / 新增 / 不变”，并提炼三次相变。

### 1.4 证据分级与边界

| 等级 | 含义 | 本报告中的用法 |
| --- | --- | --- |
| A 一手文档 | 飞书 Brainstorm 原文、官方产品文档、开源仓库固定提交 | 定义、接口、限制条件 |
| B 工程案例 | 具名团队公开的部署与流程描述 | 采用方式、组织前提、失败形态 |
| C 研究归纳 | 本仓库前三轮调研与本轮补充调研的综合 | 模块划分、优先级、路线图 |
| D 建议 | 本报告提出的阈值、批次、验收口径 | 需在真实业务中校准，不是既成事实 |

需要明确的边界：

- 本轮**没有**做产品租户对照测试、没有跑公开 benchmark、没有接入真实企业数据；所有“准确率/成本/时延”阈值都是**建议门槛**。
- 竞品能力以其官方文档为准，**不把宣传语当已验证能力**；产品文档中的“支持”不等于在客户数据上可用。
- 组织和运营建议（§8.3）来自公开案例的归纳，样本偏向英语数据社区，未做中文企业的代表性调查。
- 引用的外部来源见附录 D；其中标注“未复核”的条目，只作为方向参考，不作为结论依据。

### 1.5 与既有草案的关系

本仓库 2026-11-01 已有一版《DataAgent 模块能力草案》，给出 12 个一级模块、72 项二级能力。本报告**保留其编号体系与大部分能力描述**，做三件事：

1. **补三个模块**：两个横向契约模块（DA13 运行态/成本、DA14 资产图/血缘）与一个广义纵向模块（DA15 建模/转换/调度）。前两者横切所有模块，塞进任何纵向模块都会职责不清；后者回答“无数据库时数据库怎么建”，草案的 12 个模块里没有承接者。
2. **重排优先级**：草案是“能力清单”，本报告是“建设顺序”。清单回答“有什么”，顺序回答“先做什么、为什么”。
3. **补广义判定**：草案区分了狭义/广义，但没有逐项判定“扩展还是新增”。本报告给出 61 项扩展、30 项新增的明确归属。

### 1.6 本轮补充调研的四个修正

在六个方向的补充调研之后，本报告对草案做了四处修正。它们都来自证据，而不是偏好：

1. **草案缺一个模块：建模与转换。** 广义定义明确包含“整合来源数据、处理数据、构建数据库”，但 12 个模块里没有承接“ELT/DAG、物化、数据契约、回填、调度”的模块。DA01 只管把数据读进来，DA03 只管质量与修复，二者都不负责“把来源变成可查询数据集”。因此新增 **DA15 建模、转换与调度**。
2. **DA04 的实体解析是“模块表上算扩展、实现上算新建”。** 草案已列出“稳定身份与主数据对齐”，但 blocking、匹配阈值、合并/拆分、证据链、MDM 工作流在狭义产品里是零基础。按“扩展”估工作量会严重低估；本报告在 DA04.2 的供给列标为自研，并在 §7.6 单列风险。
3. **广义补充的共同缺口不是工具，而是“机器可审阅的变更计划”。** 接入、建模、质量、权限、语义、调度六类能力都不缺开源件，缺的是同一层：`plan / diff / dry-run / 回填区间 / 成本估算`。目前只有建模域做得较好（SQLMesh 的 plan 会给出变更分类与回填区间，dbt 的 contract 做构建前 preflight），其余类别基本停留在“生成配置、直接执行”。这决定“agent 生成 + 人审核”是接口还是话术。
4. **优先级依赖部署场景。** 若首发客户是中文大型企业，权限合规、维值编码、Excel/报表交付、出境合规会从“规模闸门”前移为“闭环闸门”；这不会改变模块划分，但会改变批 A 的组成（见 §7.7）。

**方法学限制：** 本轮 `web_search` 不可用，子 Agent 以直取官方文档为主，覆盖偏大厂工程博客与厂商文档，长尾中文来源不足；所有数字均标注样本与条件，未核实项在附录 D 单列。

## 2. 框架：狭义与广义之间是三次相变

### 2.1 狭义闭环

狭义 DataAgent 的最小闭环是七步：

```text
接入 → 理解/澄清 → 检索/绑定 → 编译/执行 → 验证 → 交付 → 轨迹
```

每一步都对应一个“必须成立”的条件：

| 步骤 | 必须成立的条件 | 缺失时的典型表现 |
| --- | --- | --- |
| 接入 | 读全、可追溯、有 as-of | 答案基于不完整数据，且无法发现 |
| 理解/澄清 | 关键歧义被识别，且只澄清高影响项 | 答非所问；或澄清过多导致用户放弃 |
| 检索/绑定 | 值/列/指标/规则能互相约束 | 找到相似表就开算，join 错误 |
| 编译/执行 | 语义优先、硬约束、可解释 | SQL 能跑，但口径错、越权、成本失控 |
| 验证 | 与失败模式一一对应 | 数字错了但看起来合理 |
| 交付 | 可检查、可复算、可分享 | 用户回到 Excel 手工核对 |
| 轨迹 | 可归因、可回归 | 同样的错反复出现，无法定位 |

### 2.2 广义闭环

广义闭环在狭义闭环外增加四个环：

```text
来源登记 → 持续接入 → 质量与实体 → 语义生产 → 发布/版本
     ↑                                            │
     └──── 漂移监测 ← 运行态 ← 资产复用 ← 影响面 ←┘
```

差别不在“多几个步骤”，而在**状态的生命周期**：狭义的状态随任务结束而失效；广义的状态必须跨任务、跨版本、跨环境存活，并且能被审阅、回滚和追责。

### 2.3 三次相变

| 相变 | 从 | 到 | 触发条件 | 新增的横向契约 | 主要受影响模块 |
| --- | --- | --- | --- | --- | --- |
| **资产化** | 任务内临时状态 | 跨任务可复用资产 | 同一问题被重复问、需要审阅、需要对外交付 | 身份、版本、owner、发布、回滚、影响面 | DA05 DA06 DA12 DA14 |
| **写入** | 只读分析 | 写数据、写语义、写回业务 | 需要修复数据、落地决策、回写工单/预算 | 幂等、事务边界、审批、补偿、审计 | DA03 DA05 DA11 DA13 DA15 |
| **运行态** | 一次调用 | 持续运行 | 需要 SLA、定时刷新、异常监测、多租户 | 调度、SLO、配额、漂移、降级、成本归因 | DA12 DA13 DA14 |

**这三次相变是“广义”的真正门槛。** 一个系统可以支持 20 个数据源、30 种图表、10 个 Agent 角色，但只要它仍然“任务结束状态即失效、只读、靠人触发”，它就仍然是狭义 DataAgent。反过来，一个只覆盖 3 个数据源、5 种图表的系统，如果具备资产版本、写操作治理和持续运行能力，它已经进入广义。

### 2.4 由此推出的模块化要求

三次相变对模块划分提出四条要求：

1. **事实所有权必须显式。** 语义定义归 DA05，证据归 DA06，验证结论归 DA11，权限判定归 DA11/DA13，资产身份归 DA14。任何“两个模块都能改同一份事实”的设计，都会在相变时崩掉。
2. **横向契约要独立成模块。** 运行态与资产图不属于任何一条纵向流水线，必须单独定义接口，否则每个纵向模块都会长出一套自己的版本/成本/血缘逻辑。
3. **写操作必须收敛到一个入口。** 无论是修复数据、发布语义还是写回业务系统，都应经过同一套“提案→审批→执行→回执→补偿”的通道，而不是各模块自己写库。
4. **评测必须能跨版本重放。** 相变之后，“同一问题在不同语义版本/数据快照/权限下是否仍然正确”成为常规问题；没有可重放的评测，资产化就是不可控的。

## 3. 模块化方法：什么才算一个模块

### 3.1 四条判据

| 判据 | 含义 | 反例 |
| --- | --- | --- |
| 单一事实源 | 每类事实只有一个模块拥有写权，其他模块只读 | “问数模块”和“分析模块”各自维护一份指标定义 |
| 可替换 | 换实现不改变上下游契约 | 换一个语义引擎就要改编排层和 UI |
| 可独立评测 | 有专属验收集与指标，能单独判断好坏 | 只能通过端到端“感觉”判断检索好坏 |
| 故障可隔离 | 失败时降级而非雪崩，且失败可归因 | 检索超时导致整个任务无响应，且无法定位 |

不满足这四条的，本质上是一个**功能**，应该放在某个模块内部，而不是单独成模块。

### 3.2 四层供给

同一个“能力”可以有四种供给方式，混为一谈会导致重复建设：

| 层次 | 内容 | 谁来做 | 例子 |
| --- | --- | --- | --- |
| 领域能力 | DataAgent 特有的语义、证据、验证、资产 | DataAgent 团队自研 | 语义编译、查询验证、黄金集 |
| 领域契约 | 输入输出规范、不变量、失败语义 | DataAgent 团队定义，实现可外包 | 证据包格式、能力单元 manifest |
| 通用设施 | 运行时、连接、沙盒、审批、追踪、发布 | AgentOS / 平台团队 | 任务生命周期、身份、审计、artifact |
| 应用组合 | 面向场景的 preset/app | 产品/解决方案团队 | 企业问数、文件分析、运营调查 |

**判断规则：** 如果一项能力的失败模式是“数据/语义/证据错了”，它属于领域能力；如果是“跑不起来/权限不对/追不了踪”，它属于通用设施。

### 3.3 能力单元 manifest（可插拔契约）

“Pluggable”要落到工程上，每个能力单元都应自带一份 manifest。建议字段：

| 字段 | 作用 | 为什么必需 |
| --- | --- | --- |
| `id` / `version` | 唯一标识与语义化版本 | 支持灰度、回滚、兼容矩阵 |
| `inputs` / `outputs` | 强类型 schema | 上下游可替换的前提 |
| `owns` | 声明拥有的事实 | 防止两个模块同时写同一份事实 |
| `requires` | 依赖的能力与数据 | 编排时做拓扑排序与降级 |
| `scope` | 数据范围与租户边界 | 权限与隔离的最小单位 |
| `budget` | token / 扫描量 / 时延上限 | 成本与超时的硬约束 |
| `sla` | 质量与可用性目标 | 独立评测与告警的依据 |
| `evalset` | 专属验收集 id | 没有验收集的能力不允许上线 |
| `fallback` | 失败时的降级路径 | 故障隔离 |
| `telemetry` | 必报的 trace 字段 | 可归因、可复盘 |

模板见附录 B。这套字段不是为了“标准化而标准化”，而是为了让**替换、灰度、回归、追责**四件事同时成立。

官方产品的硬性配额说明这些字段不是理论：Fabric data agent 限制 25 行 × 25 列、仅英语、严格只读、最多 5 个源；BigQuery Conversational Analytics API 限制结果 5,000 行（Looker）/1,000 行（数据库源）、扫描 500 GB、输出 8,192 token、失败最多重试 3 次；Databricks Genie 限制 100 条 instruction、200 条 knowledge snippet、200,000 个会话；Snowflake 托管 MCP 限制 50 个工具、响应 250 KB 截断、`read_only` 默认 true。**这些数字本质上就是 `budget`、`scope`、`fallback` 三个字段的具体取值**；把它们写进 manifest，比写在产品文档里更能约束实现。

### 3.4 五个反模式

1. **按 Agent 角色拆模块**（问数 Agent / 分析 Agent / 报告 Agent）：能力重复、事实源分裂，最后变成三个半成品。
2. **按 UI 页面拆模块**：后端无法复用，权限容易在页面层被绕过。
3. **按团队拆模块**：组织一调整，模块就要重组，架构随组织漂移。
4. **按模型拆模块**（GPT 模块 / Claude 模块）：模型无关性丢失，换模型等于重写。
5. **按数据源拆模块**（MySQL 模块 / Excel 模块）：N 个源 × M 个能力，组合爆炸；正确做法是“源适配器 + 统一数据句柄”。

### 3.5 一级/二级的划分规则

- **一级模块**回答“谁拥有哪类事实、谁对哪类失败负责”，数量应控制在 10–15 个，便于形成 owner 与验收边界。
- **二级能力**回答“这个模块具体能做哪些事”，是采购/自研/排期的单位，应可独立评测。
- 一级模块不等于部署单元，也不等于代码仓库，更不等于 Agent 数量；一个模块可以由多个服务实现，一个服务也可以承载多个模块的只读能力。

关键路径上的依赖关系有三条值得注意：

1. **DA05 与 DA06 互为前提。** 语义层提供指标/维度/时间的稳定 ID，检索才能从“指标”入口召回；检索提供值/列/规则证据，语义编译才能确认绑定。二者必须同步设计，不能先做完一个再做另一个。

**判断原则：** DataAgent 不自建运行时、身份、审批、沙盒、长任务、artifact 与分发；这些由 AgentOS 提供。DataAgent 自建的是**领域事实与领域契约**：语义、证据、验证、资产身份。两边共同定义的是接口：数据句柄、证据包、权限声明、成本上报、能力 manifest。

从 2026 年 11 月的官方接口文档看，头部产品有两条清晰分野，正好对应本报告的两个设计选择：

| 分野 | 路线 A：语义是可 diff 的对象 | 路线 B：语义是上下文包 |
| --- | --- | --- |
| 代表 | Snowflake Semantic Views、dbt `semantic_model`、Cube、Wren MDL、LookML、ThoughtSpot TML | BigQuery Conversational Analytics API（description/synonyms/tags/sample values + `system_instruction` + `example_queries`）、Fabric data agent、Power BI Copilot |
| 确定性放在哪 | 平台编译 SQL，模型只负责“选字段/选过滤” | 模型生成 SQL 文本，靠示例、认证查询与评测收敛 |
| 可移植性 | 高（对象可 diff、可迁移，Cube/dbt/Wren 可换引擎与模型） | 低（语义与引擎/平台绑定） |
| 验收方式 | 验“字段/过滤/口径选对”＋编译计划 | 验“结果对”＋回归集＋VQ 命中 |

**本报告选择“路线 A 为骨架、路线 B 为补充”**：核心指标与维度用可编译、可解释的语义对象承载；长尾问题用上下文包（说明、示例、值）兜底，但必须带来源与失效条件。原因不是审美，而是路线 B 的口径不可回归：同一个问题换模型、换时间就可能给出不同定义，而企业无法接受“每次都要重新确认口径”。

## 5. 二级能力矩阵

### 5.0 读法

- **狭义列**：`P0` 缺失即无法交付可信答案；`P1` 显著影响成功率/效率/规模化；`P2` 广义阶段再做。
- **广义列**：`扩展` 同一能力在广义下边界变大；`新增` 狭义不存在；`不变` 形态基本不变。
- **供给列**：`自研`（含核心自研★）、`薄封装`（开源/引擎之上加契约）、`集成`（直接用成熟件）、`平台`（AgentOS/运行时提供）。
- **验收口径**：建议门槛，需按业务校准；不是既成事实。

### DA01｜接入与任务数据空间

**职责边界：**数据怎样安全、稳定、可追溯地进入任务。狭义形态：读一次：文件 + 单库，任务内有效；广义形态：持续同步：多源、CDC、多租户、schema 演进。

**接口契约**

```text
拥有的事实  来源登记、读取契约、快照/游标、任务数据空间
输入        源标识、凭据引用、调用身份、目的、范围、as-of
输出        可寻址数据句柄 + schema + 覆盖范围 + 失败/漂移记录
关键不变量  任何结果都能回答“哪个源、哪个时点、哪次读取、读到了多少”
失败语义    部分读取、截断、分页丢失必须显式标注，不得静默补全
责任角色    数据平台 / 连接器 owner
```

| 编号 | 二级能力 | 是什么 | 狭义 | 广义 | 供给 | 验收口径 |
| --- | --- | --- | --- | --- | --- | --- |
| DA01.1 | 连接器与来源登记 | DB/API/文件/MCP；凭据引用、能力声明、限流、许可 | P0 | 扩展 | 集成 | 接入验收清单 100% 通过 |
| DA01.2 | 结构解析与规范化 | sheet/表头/嵌套/分页/类型/公式双轨 | P0 | 扩展 | 薄封装 | 抽样 200 行解析准确率 ≥98% |
| DA01.3 | 快照、as-of 与可重放 | digest、分区、游标、删除、迟到数据 | P0 | 扩展 | 薄封装 | 任一答案可定位 snapshot_id |
| DA01.4 | 任务数据空间 | 隔离的临时表/中间结果/生命周期/配额 | P0 | 扩展 | 平台 | 跨任务隔离测试 0 泄漏 |
| DA01.5 | 读取契约与降级 | 分页/采样/截断/失败/限流/重试 | P1 | 扩展 | 自研 | 失败与截断显式率 100% |
| DA01.6 | 数据边界与授权传递 | 读取/采样/索引/缓存/导出/模型上下文 | P0 | 扩展 | 平台 | 越权拦截 100%，误拦 ≤2% |

**关键判断**

- 接入的真实难点不是“连得上”，而是“读全了”。分页丢失、软删除、迟到数据、无快照源，最终都会在验证阶段以“答案错”的形式出现，但根因在 DA01。
- 狭义只需“一次性只读 + 快照”，不要过早做 CDC 与流式；但 `snapshot_id` 必须从第一天就有，否则证据包、回归和重算都无从谈起。
- 连接器数量不是能力指标。“源能力声明 + 覆盖范围报告”才是；能说清“这次读到了什么、没读到什么”比多接十个源更重要。

### DA02｜探查与画像

**职责边界：**当前有哪些数据、粒度、质量和关系。狭义形态：任务内按需探查，够用即停；广义形态：持续画像、质量基线、契约与异常监测。

**接口契约**

```text
拥有的事实  profile 事实：结构、取值、时间、粒度、关系候选
输入        数据句柄、允许采样范围、预算、质量规则
输出        表/字段画像、时间与粒度假设、join 候选、覆盖报告
关键不变量  候选不等于事实；每个候选必须带来源、采样范围与置信说明
失败语义    探查不足要报“未覆盖区”，不得用默认值补齐
责任角色    数据探查 / 语义工程
```

| 编号 | 二级能力 | 是什么 | 狭义 | 广义 | 供给 | 验收口径 |
| --- | --- | --- | --- | --- | --- | --- |
| DA02.1 | 结构画像 | 表/列/类型/空列/重复列/嵌套层级 | P0 | 不变 | 集成 | 表列覆盖率 100%，类型准确率 ≥95% |
| DA02.2 | 取值与分布画像 | 空值、基数、频率、枚举、代表样本 | P0 | 扩展 | 薄封装 | 枚举召回 ≥90%，空值率误差 ≤0.5pp |
| DA02.3 | 时间与粒度识别 | 事件/业务/更新/时区/周期/grain | P0 | 扩展 | 自研 | 时间角色识别准确率 ≥90% |
| DA02.4 | 质量与异常初筛 | 缺失/重复/类型冲突/突变/跨源不一致 | P1 | 扩展 | 集成 | 检出率 ≥80%，误报 ≤15% |
| DA02.5 | 关系与 join 候选 | PK/FK、名称/类型/覆盖、历史 SQL、基数 | P0 | 扩展 | 自研 | 候选 recall@5 ≥90%（含桥表） |
| DA02.6 | 探查计划与覆盖报告 | 预算内下一步、未覆盖区、索引缺口 | P1 | 扩展 | 自研 | 覆盖报告 100% 标注未覆盖区 |

**关键判断**

- 探查是“为决策取证”，不是“生成数据字典”。每个画像项都应能回答一个具体问题：能不能切、能不能 join、时间对不对、分母是谁。
- 采样结论不能当全量事实。画像必须携带采样范围与置信说明，否则会稳定地产生“看起来对”的错误。
- join 候选的价值在“排序 + 反例”，不在“自动确认”。值重合、命名相似、历史有人 join 过，都只是候选证据。

### DA03｜数据质量与修复

**职责边界：**数据是否可信，问题怎样修复和复核。狭义形态：关键结果校验为主，不做全库治理；广义形态：质量契约、基线、修复写回、事故影响分析。

**接口契约**

```text
拥有的事实  质量断言、修复提案、复核记录、质量基线
输入        数据句柄、断言集、业务对账规则、影响面查询
输出        质量报告、异常定位、修复候选、修复前后对比
关键不变量  修复建议与写回执行分离；原始输入不可被覆盖
失败语义    断言通过不等于业务口径正确，不得据此认证资产
责任角色    数据质量 / 数据治理
```

| --- | --- | --- | --- | --- | --- | --- |
| DA03.1 | 结构与取值契约 | 列存在/类型/唯一/非空/范围/枚举/格式 | P1 | 扩展 | 集成 | 断言可执行率 100%，接入 CI |
| DA03.2 | 跨表对账与一致性 | 总分/余额/计数/FK 覆盖/时间连续 | P1 | 扩展 | 自研 | 差异定位到记录级 ≥90% |
| DA03.3 | 异常与缺失定位 | 记录/分区/模式；业务变化 vs 数据错误 | P2 | 扩展 | 自研 | 人工一致率 ≥80% |
| DA03.4 | 修复方案生成 | 去重/标准化/类型/补齐/值映射候选 | P2 | 扩展 | 自研 | 方案采纳率 ≥50% |
| DA03.5 | 修复执行与复核 | 隔离空间执行、前后对比、可回滚 | P2 | 新增 | 自研 | 修复前后对比可复现 100% |
| DA03.6 | 质量事故影响分析 | 沿血缘定位受影响指标/报表/任务 | P2 | 新增 | 自研 | 影响面召回 ≥90% |

**关键判断**

- 狭义不做质量治理，但必须做“答案级校验”。总分对账、重复计数、空值分母这三类问题，占了错误答案的多数。
- 修复写回是广义能力，也是系统第一次做“写操作”。在此之前必须先有幂等、回滚与审批（DA11/DA13），否则一次误修复会污染源数据。
- 质量事故影响分析依赖血缘（DA14），不要在这一层自建图。没有列级血缘时，影响面只能给到表级并显式标注不确定性。

### DA04｜实体、身份与 Ontology

**职责边界：**数据中的对象是什么，怎样对齐和关联。狭义形态：局部对象理解：客户/订单/设备等 Top 对象；广义形态：企业实体解析、主数据、对象图谱与冲突治理。

**接口契约**

```text
拥有的事实  实体类型、身份与合并证据、关系与约束、粒度与状态
输入        schema、文档、指标、代码、历史查询、样本值
输出        实体类型与实例、身份映射、关系图、粒度声明
关键不变量  合并必须可拆；每次合并/拆分保留证据与生效范围
失败语义    同名不等于同实体，值重合不等于合法关系
责任角色    数据建模 / MDM
```

| --- | --- | --- | --- | --- | --- | --- |
| DA04.1 | 概念与实体类型提取 | 从 schema/文档/指标/代码/问题形成对象类型 | P1 | 扩展 | 自研 | Top 业务对象覆盖率 100% |
| DA04.2 | 稳定身份与主数据对齐 | 主键/自然键/别名/跨系统编码/合并拆分 | P2 | 扩展 | 自研 | 高置信匹配 precision ≥95% |
| DA04.3 | 粒度与状态模型 | 行/事件/版本/有效期/状态变化 | P1 | 扩展 | 自研 | 认证数据集粒度声明 100% |
| DA04.4 | 对象关系与约束 | 1:1/1:N/N:N、桥表、租户、时态、合法路径 | P1 | 扩展 | 自研 | 关系约束可执行校验 ≥80% |
| DA04.5 | Ontology 映射与实例化 | 对象/属性/关系映射到表/列/区域/API | P2 | 扩展 | 自研 | 映射可编译率 100% |

**关键判断**

- 狭义只做 Top 对象（客户、订单、商品、设备、合同），不做全企业 ontology。对象模型的第一价值是“统一 ID”，不是“知识图谱”。
- 实体匹配的阈值应按用途分级：筛选客户可以宽，合并主数据必须严。一个阈值同时服务两种场景，必然在一边出错。
- 关系声明必须可执行（基数、租户键、时态约束能被校验），否则它只是文档，不能支撑 join 合法性判断。

## 6. 狭义：哪些能力亟需建设

### 6.1 判定标准

优先级不是“重要/不重要”的主观排序，而是三道闸门 + 五维评分的组合：

| 闸门 | 判据 | 不满足的后果 |
| --- | --- | --- |
| **闭环** | 缺失则七步闭环走不通 | 产品无法交付第一个可信答案 |
| **信任** | 缺失则答案可能错、无法审计、无法复现 | 用户不敢用，或用了要人工复核 |
| **规模** | 缺失则无法多租户、多场景、低成本运行 | 只能做单点试点，无法推广 |

五维评分用于同闸门内排序：阻断度（0–3）、复用度（0–3）、广义依赖（0–3）、建设成本（1–3）、供给稀缺性（0–3）。本报告不逐项展示分数，只给结论与理由；评分方法可在评审时复算。

**关键区分：** “必须有”是闸门判断，“必须自研”是供给判断。二者混用，会把 30 项 P0 全部当成自研任务，直接压垮团队。

**三个外部事实（决定优先级的外部证据）：**

1. **公开最强水平约为 60%，不是 90%+。** Spider 2.0-Lite 60.15%、Snow 60.51%（ProSPy，2026-06，Claude-4.5-Opus，未用多数投票）；2024 年原论文同基准为 Lite 23.40%、Snow 23.77%。DataAgentBench（104 题、17 个数据集、4 种 DBMS）上，GPT-5.5 为 57% pass@1，没有 agent 超过 70% pass@5。**结论：目标应是“可验证的 60–70% + 人工兜底”，不是“追求 90% 自治”。**
2. **语义层带来的提升大于换模型。** AtScale 在 410 道 BIRD-Interact 上对比 7 个模型：无语义层 21.5–36.1%，有语义层 44.6–62.2%（+20～31pp）；换模型最多只移动 17.6pp。dbt 的同题对照（11 题 × 20 次，15 张表）为 90.0%→98.2%（Sonnet 4.6）与 84.1%→100%（GPT-5.3-codex）。**结论：语义层是最高杠杆，但必须按覆盖率折算 `c×a_c+(1−c)×a_f`，不能只报覆盖内准确率。**
3. **公开榜单不能作为验收真值。** BIRD Mini-Dev 有 52.8%（263/498）样本标注错误，Spider 2.0-Snow 有 62.8%（76/121）；修正 100 条 Dev 子集后，16 个 agent 的执行准确率相对变化 −7%～+31%，排名平均移动 5 位、最大 ±9 位，原/修正子集排名相关仅 0.32。**结论：必须自建黄金集，公开 benchmark 只作方向参考。**

### 6.3 护城河九件套

30 项 P0 里，只有 9 项属于“别人替不了、且直接决定答案可信度”的核心自研：

| # | 编号 | 能力 | 为什么别人替不了 |
| --- | --- | --- | --- |
| 1 | DA05.5 | 语义编译与解释 | 语义→计划→SQL 的编译契约，决定口径能否被复用与解释 |
| 2 | DA06.1 | 多入口问题理解 | 没有固定入口假设，新问题才能从最强线索进入，而不是被第一步选表锁死 |
| 3 | DA06.3 | 反向定位与渐进导航 | 反向定位（值→列→实体），是把业务语言映射到 schema 的关键 |
| 4 | DA06.5 | 证据与权限感知召回 | 召回必须携带来源/版本/权限/新鲜度，否则答案无法审计、无法授权 |
| 5 | DA07.2 | 候选绑定与查询计划 | 把业务词绑定到稳定对象 ID 并保留多候选，决定“问的是不是这件事” |
| 6 | DA07.3 | 语义查询优先与 fallback | 语义优先/受控兜底策略，决定准确率与可解释性的上限 |
| 7 | DA11.1 | 数据与查询验证 | 查询级验证（空集/膨胀/守恒/时间/单位），是正确性的最后一道闸 |
| 8 | DA11.2 | 语义与口径验证 | 口径验证（定义/版本/例外/as-of），是企业敢用的前提 |
| 9 | DA12.4 | 离线回放与回归题集 | 黄金集与回归，是唯一能证明“变好了”的机制 |

这 9 项之外，还有 3 项“准核心”（DA05.1 指标定义、DA11.6 证据包、DA12.1 轨迹），它们的重要性接近核心，但部分工作可以由平台或模板承担。

**语义控制面的七个接口（DA05.5 的最小设计）：**

| 接口 | 输入 | 输出 | 不变量 |
| --- | --- | --- | --- |
| `draft` | 指标/维度/关系草稿 | 草稿版本 + 乐观锁 | 不改动已发布 release |
| `validate` | 草稿或变更集 | 分级检查结果 + 证据 | 结构/键/grain/join/时间/币种缺一不可 |
| `compile` | 指标请求 + release + 身份 | 逻辑计划 + 物理 SQL + 所需授权 | 同版本同参数→同计划 |
| `explain` | 编译结果 | 指标展开、join 路径、grain、假设、风险 | 必须能解释“为什么这样算” |
| `publish` | 通过验证的草稿 | 不可变 release + 指针切换 | 发布需 owner 批准 |
| `deprecate` | 旧 release | 软废弃 + 替换建议 + 宽限期 | 不删除历史，只停用 |
| `diff` | 两个 release | 结构/语义/影响/行为四类差异 + breaking 标记 | breaking 必须触发回归 |

**指标语义 CI 的四层：** ① 结构/键/grain/join/时间/币种检查；② 目标方言 EXPLAIN；③ 黄金集结果差分；④ owner 批准与影响面分析。跨厂商的完整“口径 CI”目前不存在，必须自建；dbt 的 `dbt sl validate --select state:modified+` 是最成熟的编译级 CI，Snowflake 用 verified queries 做 accuracy/regression/latency 评测并防 VQ 泄漏，是最接近“语义 CI”的产品化证据，但它只证明“答对了既有题”，不证明口径正确。

**VQ 必须绑定失效条件：** 每条认证查询至少要记录 `semantic_release`、schema hash、data as-of、权限/租户、验证人、有效期与失效条件（Snowflake 的 `name/question/verified_at/verified_by/sql` 可作为最小字段集）。否则口径一变，旧 VQ 就会变成“高置信度的错误答案”。

一个容易被忽略的工程细节：**受控路径必须可观测，否则无法回归。** 目前只有 Snowflake（响应体含 `confidence.verified_query_used`）与 BigQuery CA API（含 `matched_query`）把“是否命中认证查询”写进响应；Looker 的 verified query 只是一组“问题 + Explore URL”，Cube 明确 agent 可以改写或忽略 certified query。DA06.7 应把“命中/改写/未命中”作为必报字段，否则 VQ 的收益无法度量。

**判断理由：** 语义编译、检索、绑定、验证、评测这五类能力，决定的是“同样的模型、同样的数据，为什么你答得对而别人答不对”。它们无法通过采购获得，也无法通过 prompt 工程替代；其余能力（连接器、SQL 引擎、图表库、索引、沙箱、追踪）都有成熟替代品，自研的边际收益很低。

### 6.4 最小可信闭环（MVP）

MVP 不是“功能最少”，而是“能被业务真正用起来的最小闭环”。建议范围：

| 维度 | MVP 范围 | 明确不做 |
| --- | --- | --- |
| 业务域 | 1 个域、2–3 个高频问题族 | 跨域、开放式探索 |
| 数据源 | 1 个数据库 + 1 类文件 | 多源 CDC、API 生态 |
| 语义 | 20 个指标、3 个维度、2 个时间角色 | 全量指标、ontology |
| 问题类型 | 单轮问数、对比、下钻、简单追问 | 归因、预测、优化 |
| 交付 | 表 + 图 + SQL + 证据包 | 报告模板、看板、嵌入 |
| 验证 | 空集/膨胀/守恒/时间/单位/口径 6 类 | 统计与因果验证 |
| 评测 | 120–150 题黄金集（含多解），PR 快集 40 题 | 大规模自动出题 |
| 运行 | 单租户、同步调用、成本记录 | 多租户、SLA、配额 |
| 歧义处理 | 只处理无歧义问题；歧义走澄清模板或拒答 | 自动多轮澄清（批 B） |

**90 天节奏（建议）：**

| 周 | 目标 | 出口物 |
| --- | --- | --- |
| W1–2 | 定契约与基线 | 模块 manifest、数据接入清单、80–120 题黄金集 v0、20 个指标定义 |
| W3–5 | 打通检索与绑定 | 多入口索引、值/列/指标召回、候选绑定与计划 |
| W6–7 | 打通编译与执行 | 语义编译、受控 SQL、只读/预算/超时硬约束 |
| W8–9 | 打通验证与交付 | 6 类验证规则、证据包、表/图交付 |
| W10–11 | 轨迹与回归 | 结构化轨迹、回归流水线、错误归因 v0 |
| W12 | 试点复盘 | 2 个团队、30 天真实使用数据、扩/停决策 |

**MVP 出口门槛（建议，需按业务校准）：**

- 答案采纳率 ≥ 60%，一次通过率 ≥ 55%
- 口径一致率 ≥ 95%（同一问题在不同入口/不同时间答案一致）
- 证据完备率 100%（每个答案都有定义、时间、数据版本、SQL、限制）
- P95 端到端 ≤ 30 秒；单题成本 ≤ 1.5 元
- 黄金集回归通过率 ≥ 80%，且连续两周不回退

### 6.5 三个“现在不要做”

1. **不要做全量 ontology。** 狭义阶段只需要 Top 对象（客户/订单/商品/设备）的稳定 ID 与关系约束；全量建模的投入产出比在数据资产尚未积累时极低。
2. **不要做自由 NL2SQL 为主路径。** 自由生成会把语义层架空，且无法保证口径一致；正确顺序是“受控语义查询优先，NL2SQL 有界兜底”。
3. **不要做预测/仿真/优化。** 它们的真值（未来误差、情景校准、约束满足）与问数完全不同，会显著拉长交付周期，并稀释验证体系。客户强需求时，先做“受控函数 + 人审”。

### 6.6 常见误判

| 误判 | 表现 | 纠正 |
| --- | --- | --- |
| 把“支持更多数据源”当能力 | 连接器数量成为 KPI | 看“接入覆盖率 + 首次可信答案耗时” |
| 把“SQL 执行成功率”当准确率 | 简单题拉高指标 | 用黄金集 + 答案级验收 |
| 把“Agent 数量”当智能化 | 多 Agent 互相调用 | 单 Agent + 强工具契约优先 |
| 把“语义层”当一次性项目 | 建完即弃，无 owner | 语义是资产，需要版本、健康度、废弃流程 |
| 把“用户点赞”当正确 | 点赞率高但复问率高 | 采纳率 + 申诉率 + 抽检正确率 |

## 7. 广义：哪些需要扩展、哪些需要补充

### 7.1 判定方法

对每个二级能力问三个问题：

1. **它的事实是否从“任务内”变成“跨任务”？** 是 → 资产化相变，需要身份/版本/发布。
2. **它是否从“读”变成“写”？** 是 → 写入相变，需要幂等/审批/补偿。
3. **它是否从“人触发”变成“系统持续运行”？** 是 → 运行态相变，需要调度/SLO/漂移/成本。

三个都否 → 判定为“不变”；任一为是 → “扩展”；狭义根本不存在 → “新增”。

| DA10 | 不做 | 预测/仿真/优化产品化 | **补充** | 全部 6 项 |
| DA11 | 自动校验 | 质量门禁、审批、审计、责任链 | **扩展** | 风险分级、审计留存、合规 |
| DA12 | 轨迹+黄金集 | 归因、提案、漂移、发布回滚 | **扩展+补充** | 提案流水线、漂移监测 |
| DA13 | 轻量运行 | SLO、配额、隔离、容量、降级 | **补充** | 全部 6 项 |
| DA14 | 轻量血缘 | 列级血缘、影响面、目录、跨环境 | **补充** | 全部 6 项 |
| DA15 | 不做（狭义假设已有库） | ELT/DAG、物化、契约、回填、调度 | **补充** | 全部 6 项 |

判定为“扩展+补充”的模块，表示同一模块内**既有形态变化、也有狭义不存在的新能力**（例如 DA03 的修复写回、DA05 的语义发布）。

**统计：** 92 项二级能力中，61 项属于“扩展”（同一模块边界变大），30 项属于“新增”，1 项基本不变（DA02.1 结构画像）。也就是说，**广义 ≈ 2/3 的边界扩大 + 1/3 的新能力**，而不是“再造一套系统”。

### 7.3 补充清单

补充分四类：

**第一类：横向契约模块（2 个）**

- **DA13 运行态、成本与可观测**：狭义只需要超时/取消/成本记录；广义需要 SLO、配额、隔离、容量、降级、成本归因。它横切所有模块，不能塞进任何一条纵向流水线。
- **DA14 资产图与血缘**：狭义只需要“答案→表/列”；广义需要列级血缘、影响面、目录、生命周期、跨环境一致性。它决定“变更时谁会坏”。

**第二类：纵向业务模块（2 个）**

- **DA10 预测、仿真与优化**：真值分别是未来误差、情景校准、约束/目标满足，与问数不同。6 项能力全部为“新增”。
- **DA15 建模、转换与调度**：狭义假设“已有库”，所以不做；广义要“构建数据库”，必须有 ELT/DAG、物化、数据契约、回填、调度与发布回滚。6 项能力全部为“新增”。

**第三类：狭义不存在的二级能力（30 项）**

按主题归纳：

| 主题 | 新增能力 | 为什么狭义不需要 |
| --- | --- | --- |
| 持续接入 | 连接器治理、时点一致、配额与许可 | 狭义只读一次 |
| 建模与转换 | ELT/DAG、物化、契约演进、回填幂等、调度 | 狭义不建库 |
| 质量治理 | 修复写回、回滚、质量事故影响面 | 狭义只校验答案，不改数据 |
| 实体与主数据 | 身份对齐、合并拆分、关系约束 | 狭义只需 Top 对象的局部理解 |
| 语义生产 | 发布状态机、指标健康、语义影响面 | 狭义复用已有语义 |
| 运行态 | SLO、配额、隔离、降级、容量 | 狭义靠人触发 |
| 资产运营 | 目录、认证、废弃、跨环境一致性 | 狭义产物即用即弃 |
| 持续评测 | 漂移监测、提案流水线 | 狭义只有会话级反馈 |
| 预测与优化 | 回测、情景、约束、多目标、校准 | 狭义不做预测 |

> 30 项“新增”里有 18 项来自 DA13/DA14/DA15 三个新模块，其余 12 项散落在既有模块内部（如 DA03.5 修复执行、DA05.6 语义发布、DA12.5 漂移监测）。这也是为什么“广义 = 模块表变大”是一种误读：**新模块贡献了大部分新增能力，既有模块主要是边界扩大。**

### 7.4 三个断层与横向契约升级

**断层一：资产化。** 狭义产物是“答案”，广义产物是“资产”。资产需要六件套：稳定身份、版本、owner、质量标记、血缘、发布/废弃状态。缺任何一件，资产就会退化成“文件堆积”。

- 需要新增的契约：`asset_id`、`release`、`deprecate`、`impact`。
- 度量：资产复用率、认证率、失效率、平均维护工时。

**断层二：写入。** 从 `SELECT` 到 `INSERT/UPDATE`、写回语义、写回业务系统。写操作的危险不在于“写错”，而在于“不知道写错了、不知道影响了谁、不知道怎么退”。

- 需要新增的契约：幂等键、事务边界、审批单、补偿动作、审计日志。
- 度量：写操作事故率、回滚成功率、审批覆盖率。

**断层三：运行态。** 从“用户发起”到“系统自主运行”。运行态的核心不是调度器，而是“知道自己在什么状态下、成本多少、什么时候该停”。

- 需要新增的契约：任务状态机、SLO、配额、漂移检测、降级路径、成本归因。
- 度量：无人值守时长、漂移检出时延、单资产运行成本、降级恢复时间。

**三个断层共同的结论：** 广义不是“12 个模块都变大”，而是“每个断层都要求所有相关模块接受同一套横向契约”。因此 DA13/DA14 必须在广义阶段独立成模块，而不是继续寄生在 DA11/DA12 内部。

**第四个契约：变更计划。** 三个断层表面上各需要一套契约，实际上共享同一个前置物：**机器可审阅的变更计划（plan / diff / dry-run）**。任何“写”动作——接入新源、改 schema、改语义、改权限、回填、发布——都应先生成一份结构化计划，再进入审批与执行。

| 计划字段 | 内容 | 消费者 |
| --- | --- | --- |
| `change_id` / `target` | 改什么、改哪个资产/版本 | 审计、回滚 |
| `kind` / `breaking` | 变更类型、是否破坏性 | 审批、下游告警 |
| `affected_assets` | 受影响的指标/报表/任务（含未覆盖清单） | 影响面、回归 |
| `backfill_range` / `cost` | 回填区间与成本估算 | 调度、预算 |
| `rollback_plan` | 回滚路径与前置条件 | 运维、事故处理 |

当前只有建模域做得较完整（SQLMesh 的 `plan` 会区分 breaking / non-breaking 并给出回填区间，dbt 的 contract 在构建前做 preflight）；接入、质量、权限、语义发布、调度大多仍是“生成配置后直接执行”。**这是广义阶段最值得补齐的接口，也是“agent 生成 + 人审核”能否落地为流程的分水岭。**

官方文档给出了同样的边界判断。Snowflake 托管 MCP 的文档明确写道：**“把裸 SQL 执行与 agent 暴露在同一入口，会绕过语义视图、verified queries 与编排”**。这句话可以当作模块划分的官方注脚：受控查询与自由执行不是两个工具，而是两条必须分开治理的路径。

### 7.5 交付形态会反向定义能力拆分

同一套能力，在不同入口下的要求不同；如果先定架构再选入口，通常会在时延、权限或可复算上返工。

| 交付形态 | 硬约束 | 对拆分的反向要求 |
| --- | --- | --- |
| 嵌入式 BI | 低时延、权限透传 | 不能每次走完整 Agent 循环；需要预编译/缓存与语义查询直连 |
| Slack / Teams | 异步、消息卡片、线程上下文 | 澄清与追问要能跨消息保持状态；结果要可折叠 |
| Excel | 保格式、公式可重算、未涉及区域不被破坏 | 交付层必须产出“可复算产物 + 变换记录”，不能只给截图 |
| Google Sheets | 自定义函数不能申请个人授权、需传入引用区域才重算 | 先生成可复算产物，再做显式刷新；不能依赖用户级凭据 |
| API / Headless | 契约稳定、幂等、批量、配额 | 能力单元要有稳定 schema 与错误码，不能暴露内部编排 |
| 报告 / 幻灯片 | 事实可溯源、可刷新 | 每个数字要绑定结果引用与数据版本 |
| Chat / MCP Apps | 工具描述即路由契约 | 能力单元的 `description` 要能独立表达适用场景与边界 |

### 7.6 四类“伪扩展”

1. **数据源数量**：从 3 个源到 30 个源，是 DA01 的线性扩展，不产生新能力；除非同时具备 schema 演进、时点一致、配额治理。
2. **图表类型**：从 5 种到 20 种，是 DA09 的配置扩展；不解决“可复算/可分享/可刷新”。
3. **Agent 角色**：从 1 个到 10 个，是编排复杂度；不解决事实源分裂，反而加剧。
4. **模型接入**：从 1 个到 N 个，是模型无关性；不产生资产。

判断标准很简单：**是否引入了新的失败模式与新的验收标准**。没有，就是伪扩展。

### 7.7 广义阶段的组织前提与场景化优先级

广义不是纯技术问题。三类角色必须到位，否则模块建了也跑不起来：

| 角色 | 职责 | 缺位的后果 |
| --- | --- | --- |
| 语义 owner（指标 owner） | 定义、审核、废弃、口径冲突裁决 | 指标越建越多，口径越用越乱 |
| 评测运营 | 出题、标注、回归、bad case 归因 | 没有客观信号，改进靠感觉 |
| 数据 steward | 源登记、质量规则、权限与合规 | 数据不可信、越权、审计不过 |

技术团队负责“让能力可运行”，这三类角色负责“让能力可信”。把两者混为一谈，是 DataAgent 项目最常见的组织失败。

公开工程案例给出了三条可操作的经验（均为具名团队自述，不能外推为行业统计）：

- **认证范围应是“数百张重要表”，不是全库。** LinkedIn 在全库数百万张表中，先按访问热度收敛到数千张，再由领域专家圈定数百张认证表；定义权（圈表）与描述权（steward）分开。国内万人体量企业的首批规模可参考 80–200 个指标、30–80 张核心表（推断值，需按业务校准）。
- **评测要双时钟。** 机器在每个 PR 上跑快集（40 题以内、分钟级），人按月抽检、按季复核；不要因为约 5% 的运行间波动就改决策。
- **入口决定采用率。** LinkedIn 把能力嵌入既有 IDE 后，采用率相对独立原型高 5–10 倍；“Fix with AI”占 80% 会话。这说明“独立站点 + 聊天框”不是默认最优入口。

**若首发客户是中文大型企业，模块顺序需要调整**（不改变模块划分，只改变批 A 的组成）：

| 场景特征 | 需要前移的能力 | 原因 |
| --- | --- | --- |
| 口径会 / 多口径并存 | DA05.6 语义发布、DA11.2 口径验证 | 口径必须版本化、可对照、可通告 |
| 报表文化 / 定时推送 | DA09.4 报告、DA09.6 订阅与刷新 | 用户要的是“能贴进报表的结论”，不是聊天 |
| Excel 为主要交付 | DA09.1 表格清洗、DA09.5 可复跑产物 | 保格式、可重算、可追溯是一等需求 |
| 维值编码复杂 | DA02.2 值画像、DA06.2 值索引、码表映射 | 编码映射需要独立版本与失效管理 |
| 数据出境 / 合规 | DA01.6 边界、DA11.4 权限与外发 | 合规是硬门槛，不能后置为“规模闸门” |

## 8. 建设路线图与验收门

### 8.1 四阶段

| 阶段 | 周期 | 目标 | 主要范围 | 出口标准（Gate） |
| --- | --- | --- | --- | --- |
| **P0 定义** | 0–2 周 | 定契约与基线 | manifest、数据接入清单、120 题黄金集、20 个指标 | 契约评审通过；黄金集可跑 |
| **P1 可信闭环** | 2–12 周 | 单域可回答且可验证 | 批 A 21 项 | 采纳率 ≥60%、口径一致 ≥95%、证据完备 100% |
| **P2 复用与信任** | 12–24 周 | 从“能答”到“敢用、可复用” | 批 B 12 项 + 批 C 8 项 + 语义生产 v0 | 专家介入率 ≤30%、资产复用率 ≥40%、回归不回退 |
| **P3 广义扩展** | 24–40 周 | 持续接入、质量、实体、建模、血缘、运行态 | DA03/DA04/DA15/DA13/DA14 的核心项 | 无人值守 ≥14 天、漂移检出 ≤24h、影响面召回 ≥90% |
| **P4 预测与行动** | 40–52 周 | 预测/仿真/优化 + 写回业务 | DA10 + 写操作治理 | 回测优于 baseline ≥10%、写操作 0 事故 |

### 8.2 每个阶段的“不可跳过”项

- **P1 不可跳过**：语义编译、多入口检索、证据包、黄金集。缺任何一项，后面的投入都会变成“在错误的基础上优化”。
- **P2 不可跳过**：口径验证、权限传递、成本可见性。缺任何一项，规模化时会以事故形式补课。
- **P3 不可跳过**：资产身份与血缘、数据契约与回填幂等。缺任何一项，广义阶段既无法回答“这个变更会影响谁”，也无法安全地改 schema。

### 8.3 资源与团队配置（建议）

| 角色 | 人数（P1） | 人数（P2–P3） | 主要职责 |
| --- | --- | --- | --- |
| 领域架构 / Tech Lead | 1 | 1 | 模块契约、优先级、跨团队对齐 |
| 语义工程 | 2 | 3 | 指标/维度/时间/规则、语义编译 |
| 检索与索引 | 1–2 | 2 | 多入口索引、证据契约、评测 |
| 后端 / 执行 | 1–2 | 3 | 接入、执行、验证、运行态 |
| 前端 / 交付 | 1 | 2 | 表/图/报告、审阅工作台 |
| 评测 / 数据运营 | 1 | 2 | 黄金集、归因、回归 |
| 领域专家（兼职） | 1 | 2 | 口径、反例、验收 |

P1 阶段建议 7–9 人；P2–P3 建议 12–15 人。**不建议**在第一阶段设置独立的“Agent 平台组”和“数据组”，两者必须共用一套契约。

### 8.4 决策点

## 9. 度量体系

### 9.1 北极星指标

**可信答案率（Trusted Answer Rate, TAR）** = 被用户采纳、且抽检正确的任务数 ÷ 总任务数。

它同时约束“对不对”和“有没有用”，避免团队用“SQL 执行成功率”或“对话量”自我安慰。

### 9.2 分层指标

| 层级 | 指标 | 定义 | 建议目标 | 采集方式 |
| --- | --- | --- | --- | --- |
| 体验 | 首次可信答案时长（TTFA） | 从提问到用户可用的首个可信答案 | ≤ 3 分钟 | 埋点 |
| 体验 | 澄清轮次 | 平均澄清次数 | ≤ 1.2 | 轨迹 |
| 体验 | P95 端到端时延 | 95 分位耗时 | ≤ 30 秒 | 追踪 |
| 正确 | 一次通过率 | 无需人工改写即通过验证 | ≥ 55% | 验证记录 |
| 正确 | 口径一致率 | 同题跨入口/跨时间答案一致 | ≥ 95% | 回归 |
| 正确 | 证据完备率 | 含定义/时间/版本/SQL/限制的答案占比 | 100% | 证据包校验 |
| 正确 | 回归通过率 | 黄金集通过比例 | ≥ 80% 且不回退 | CI |
| 信任 | 采纳率 | 用户直接使用或转发的比例 | ≥ 60% | 产品埋点 |
| 信任 | 专家介入率 | 需要数据团队介入的任务占比 | ≤ 30% | 工单 |
| 信任 | 申诉/纠错率 | 用户标记错误的比例 | ≤ 5% | 反馈 |
| 成本 | 单题成本 | token + 扫描量 + 算力 | ≤ 1.5 元 | 计量 |
| 成本 | 缓存命中率 | 语义/结果缓存命中 | ≥ 25% | 计量 |
| 资产 | 认证指标数 | 已发布且有人负责的指标 | 按阶段目标 | 语义库 |
| 资产 | 资产复用率 | 被 ≥2 个场景引用的资产占比 | ≥ 40% | 资产图 |
| 正确 | 认证答案精确率 | 认证答案中真正正确的比例 | ≥ 99% | 抽检 |
| 正确 | 空集假阳性率 | 本应有结果却返回空集的比例 | ≤ 2% | 回归 |
| 正确 | join fanout 检出率 | 重复计数/膨胀被拦截的比例 | ≥ 95% | 回归 |
| 正确 | 越权拦截 | 越权查询/导出被拦截 | 100%（一票否决） | 对抗测试 |
| 正确 | judge 一致性 | LLM judge 与人工一致（κ / 差≤1分比例） | κ ≥ 0.6；≥ 75% | 抽检 |
| 资产 | 漂移检出时延 | 从变更到告警 | ≤ 24 小时 | 监测 |

### 9.3 反指标

以下指标**不能**作为主要 KPI，否则会诱导作弊：

- SQL 执行成功率（简单题拉高、失败被静默丢弃）
- 对话量 / 日活（可以靠营销与重复提问拉高）
- 点赞率（社交礼貌偏差）
- 公开 benchmark 分数（与真实业务分布不一致，且标注错误可让排名移动 5 位）
- LLM judge 分数（只能做分诊：跨 judge κ 约 0.42–0.46，与人工精确一致约 67%）
- “支持的数据源/图表/模型数量”（供给指标，不是效果指标）

### 9.4 成本与计费口径

成本不是财务问题，而是架构约束。当前主流产品有四类计费口径，直接对应四种成本控制点：

| 口径 | 代表 | 成本主因 | 对 DataAgent 的要求 |
| --- | --- | --- | --- |
| 按消息 / 调用 | Snowflake Cortex Analyst（仅 HTTP 200 计费，仓库算力另计） | 调用次数 | 缓存、去重、澄清前置，避免无效调用 |
| 按 DBU / 算力 | Databricks Genie（约 $0.07/DBU，计算另计） | 扫描量与并发 | 分区裁剪、结果上限、预算硬约束 |
| 按容量 / 席位 | Microsoft Fabric Copilot（绑定 F2+ 容量） | 常驻容量 | 多租户隔离、闲时降配 |
| 按 token | 直连模型 API | 上下文长度与轮次 | 上下文压缩、检索精度、重试上限 |

**一个反直觉的事实：** 单表 40–60K token 的 schema 上下文，往往比 SQL 执行更贵。因此“检索精度”不只是准确率问题，也是成本问题——少召回一张无关表，可能比优化一条 SQL 更省钱。

### 9.5 采集原则

1. **固定分母**：超时、漏答、工具失败都计入失败，不允许从分母里剔除。
2. **可重放**：每个指标都能绑定“语义版本 + 数据快照 + 权限 + 模型/工具版本”。
3. **可归因**：失败必须能落到 接入/理解/召回/计划/SQL/执行/解释/交付 某一层。
4. **可对抗**：定期做“对抗题”（歧义、缺失数据、越权、诱导），防止指标好看但能力退化。

## 10. 风险与反模式

### 10.1 十个反模式

| # | 反模式 | 表现 | 后果 | 对策 |
| --- | --- | --- | --- | --- |
| 1 | 按角色拆模块 | 问数/分析/报告三个 Agent 各建一套 | 能力重复、事实源分裂 | 按事实所有权拆 |
| 2 | 语义层一次性项目 | 建完即弃，无 owner | 口径漂移、无人维护 | 语义当资产，设 owner 与健康度 |
| 3 | 用点赞当验收 | 点赞高、复问率高 | 错误被固化 | 采纳率 + 抽检 + 回归 |
| 4 | 反馈自动入库 | 一次纠错进入全局知识；Databricks Genie 文档明说“行为不会仅因用户反馈而改变” | 污染扩散 | proposal → review → release |
| 5 | 先做预测后做验证 | 预测结果无法验收 | 承诺无法兑现 | 先闭环后预测 |
| 6 | 只做 schema 检索 | 值与规则缺失 | 找不到正确过滤条件 | 多入口 + 值索引 |
| 7 | 权限只在 SQL 层 | 采样/索引/缓存/导出泄露 | 合规事故 | 权限贯穿全链路 |
| 8 | 用 benchmark 代替内评 | 榜单高、业务差 | 方向误判 | 黄金集为主、benchmark 为辅 |
| 9 | 自研运行时 | 重造调度/沙箱/审批 | 维护成本高、能力弱 | 交给 AgentOS |
| 10 | 成本后置 | 上线后才发现不可持续 | 被迫降级或停服 | 第一天就埋成本 |

### 10.2 三个技术风险

- **语义漂移**：物理 schema、业务规则、口径变更后，旧语义仍然“编译成功”，但结果已错。典型失败：一笔订单 5 行明细让收入放大 5 倍（join fanout）；SCD 没有有效期，历史订单被全部重算；USD 与 CNY 直接相加；退款政策变更后旧 VQ 继续复用。对策：语义 release 绑定 schema fingerprint + 数据 as-of；变更触发影响面分析（DA14）与回归（DA12）。
- **权限穿透**：值索引、缓存、证据包、导出都是新的数据出口，容易绕过原有行列权限。对策：权限作为能力单元的 `scope` 字段，贯穿每一次读写；用“越权测试集”做回归。
- **成本失控**：多轮检索、重试、大结果集、长上下文会放大成本。对策：每个能力单元声明 `budget`，执行器强制；成本按租户/任务归因（DA13.2）。

### 10.3 三个组织风险

- **语义 owner 缺位**：指标没人负责，冲突无人裁决。对策：认证指标必须绑定 owner，废弃需 owner 确认。
- **评测无人运营**：题集不更新，回归流于形式。对策：设评测运营岗，固定节奏（周回归、月扩题）。
- **业务方预期错位**：把 DataAgent 当“万能问答”。对策：明确“可回答问题族”与“不可回答情形”，用证据包与限制说明管理预期。

## 11. 开放问题与下一步验证

### 11.1 需要决策的八个问题

| # | 问题 | 选项 | 建议 |
| --- | --- | --- | --- |
| 1 | 首个业务域怎么选 | 财务/销售/运营/供应链 | 选“问题高频、口径相对稳定、有 owner、数据可授权”的域 |
| 2 | 语义层自建还是复用 | 全自建/复用编译/混合 | 混合：复用编译与校验，自建口径发布与影响面 |
| 3 | 是否支持文件入口 | 只做库/库+文件 | 库+文件：文件是“无数据库”广义能力的入口，也是最快验证闭环的场景 |
| 4 | 是否做 ontology | 不做/轻量/全量 | 轻量：Top 对象 + 稳定 ID + 关系约束 |
| 5 | 多轮对话深度 | 单轮/有限多轮/自由多轮 | 有限多轮（继承对象与约束，不继承猜测） |
| 6 | 评测规模 | 80–150 / 300–500 题 | 120–150 起步（含多解），按域扩到 300+ |
| 7 | 私有化要求 | 必须/可选 | 架构上“可私有化”，部署按客户 |
| 8 | 是否对外输出能力 | 产品/API/嵌入式 | 先产品，API 与嵌入式在 P2 后评估 |

### 11.2 下一轮研究计划

1. **真实业务样本对照**：同一组 120 题，比较“已有语义”“动态上下文”“二者结合”三种配置的正确率、专家工时、成本与维护量。
2. **值索引规模实验**：在 10 万/100 万/1000 万值规模下测召回率、时延与权限过滤成本。
3. **语义编译对照**：dbt MetricFlow / Cube / 自建编译在复合键、SCD、多事实表上的通过率与失败类型。
4. **写操作治理演练**：一次“修复数据 + 写回业务系统”的端到端演练，验证幂等、审批、补偿、审计。
5. **成本基线**：单题 token/扫描量/时延的分布，建立成本模型与配额策略。

## 附录 B｜能力单元 manifest 模板

```yaml
id: da05.semantic.compile
version: 1.3.0
title: 语义编译与解释
owns: [semantic_release, compiled_plan]
inputs:
  metric_request: {schema: MetricRequest, required: true}
  semantic_release: {schema: ReleaseRef, required: true}
  principal: {schema: Principal, required: true}
outputs:
  logical_plan: {schema: LogicalPlan}
  sql: {schema: SqlText}
  explain: {schema: ExplainDoc}
requires: [da05.metric_definition, da05.dimension_scope, da14.asset_graph]
scope: {tenant: required, row_policy: inherit}
outputs_meta:
  result_type: table        # table | scalar | chart | report | plan
  determinism: deterministic # deterministic | stochastic
  evidence: required        # 是否必须产出证据包
budget: {tokens: 4000, usd: 0.05, wall_ms: 15000, bytes_scanned: 500000000, rows: 10000}
on_exhausted: partial_with_notice   # fail | partial_with_notice | degrade
sla: {success_rate: 0.99, p95_ms: 8000}
evalset: evals/da05-compile-v3
fallback: [da07.nl2sql_guarded]
telemetry: [release_id, metric_ids, compile_status, error_class, bytes_scanned, data_as_of]
```

**字段设计说明：** `owns` 防止事实源分裂；`scope` 把权限前移到能力单元；`budget` 用五维（token/金额/时延/扫描量/行数）把成本写成硬约束，`on_exhausted` 明确“预算耗尽时是失败、部分返回还是降级”；`result_type` 与 `determinism` 决定能否缓存、能否进 Sheets 公式、能否当证据；`evalset` 让“没有验收集不允许上线”可执行；`fallback` 让故障可隔离；`telemetry` 让失败可归因。

**落地方式：** 这份 manifest 不应成为第二套清单，而应作为 AgentOS `mint.toml` 的扩展段：复用其能力声明（文件/网络/执行/环境/模型/密钥/UI/记忆九类），新增 `data_scope`、`side_effect`、`egress` 与 `evidence` 四个领域字段。这样“可插拔”才能同时被运行时、评测与审计消费。
