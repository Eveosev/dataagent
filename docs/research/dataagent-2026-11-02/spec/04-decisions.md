## D1｜DA04 存储归属：补内核还是自建

### 背景
内核只提供 `StoreContract::append/read(session, from, limit)`，游标是**会话内**的。DA04 要的是三级作用域（个人/任务/企业）、跨会话检索、版本钉定与失效传播——三者都不是「会话内只增日志」能表达的。

### 作用
决定 DA04 是「一个适配层」还是「一个新的存储子系统」。也决定记忆能不能在不同会话、不同现场之间复用——这正是「越用越好」的前提。

### 影响面
- **DA04 全部 24 个原子**：作用域、版本、失效三条主线都挂在这个决定上
- **DA05.3**：记忆检索依赖跨会话索引，存储不定则检索索引也无处落
- **DA12.2.3**：记忆版本管理要求可回滚，只增日志无法回滚
- **DA17.2**：上下文钉定要引用「数据版本 + 语义版本」，若记忆也进钉定，则同一套版本机制
- 返工成本：高。改动会波及内核 iface（破坏性变更需重发 0.1.x→0.2.0）与四个 bundle

### 选项
| 选项 | 说明 | 代价 |
|-|-|-|
| A 补内核 | 在 iface 加 `Scope`、`MemoryEntry{version, scope, invalidated_by}`、`PinSet` | 动 iface，需版本升级与全仓同步 |
| B OS 上自建 | 能力层自建索引库，内核只存会话轨迹 | 不动 iface，但两套存储、两套权限 |
| C 分两步 | 先 B 跑通，把接口形状冻结；验证后再下沉 A | 前期快，后期有一次迁移 |

### 建议
**C**。先用 B 把 DA04.1/4.3/4.5 跑通并冻结 `Scope`/`PinSet` 的接口形状，等 DA17 钉定也稳定后，一次性把两者一起下沉内核（它们本来就要共用一套版本机制）。
**定之前可以往前走**：DA04.1 用现有 `StoreContract` 直接落地，不受影响；DA04.3/4.5 只写接口不落实现。

### 需要的输入
- 记忆是否需要跨现场共享（影响作用域模型）
- 内核是否接受一次破坏性版本升级

## D2｜DA15/DA16 契约与 iface 的映射

### 背景
内核已有 `EffectLevel{ReadOnly, Advance, SideEffect}`、`DelegationGrant{grant_id, scope, depth_remaining, expires_at_ms, parent_grant}`、`ReviewPosition{Input, Plan, ToolParams, FinalResult}`、`ApprovalRequest`（仅 4 字段：session、call、summary、timeout_ms）。
而我们的 DA15 契约有档位 A0/A1/A2 + 参数 schema + 前后置条件 + 影响面 + 可逆性 + 幂等/dry-run/补偿，DA16 的审批要证据包、批量、免审、双人复核。**两套概念并存，字段对不齐**。

### 作用
决定「动作面」到底以谁为准。若不定，实现时会出现：网关按 DA15 判档、内核按 EffectLevel 判权限，两边结论不一致 → 越权或误拦。

### 影响面
- **DA15 全部 14 个原子**、**DA16 全部 17 个原子**
- **DA07.7 网关**：它到底调谁
- **DA12.10 证据链**：审计字段跟哪套
- **DA11.8.2 过程合规性**：按哪套判「审批纪律」
- 返工成本：中高。错在早期只是改文档，错在实现后要改网关与全部契约

### 选项
| 选项 | 说明 |
|-|-|
| A DA15 为准，内核只当执行器 | 内核退化，但需要把 A0/A1/A2 塞进 EffectLevel 或旁路 |
| B 内核为准，DA15 只是渲染 | 契约表达力受限（`ApprovalRequest` 只有 4 字段，放不下证据包） |
| C DA15 是上层封装，映射到内核原语 | 档位 → EffectLevel + ReviewPosition；证据包 → 扩展 payload |

### 建议
**C**，并先做一张映射表（下面这张就是初稿）：

| DA15/DA16 概念 | 内核原语 | 缺什么 |
|-|-|-|
| A0 读 | `EffectLevel::ReadOnly` | 无 |
| A1 提议 | `EffectLevel::Advance` + `ReviewPosition::Plan` | 无 |
| A2 执行 | `EffectLevel::SideEffect` + `ReviewPosition::ToolParams` | 无 |
| 委托范围 | `DelegationGrant.scope/depth_remaining` | 无 |
| 审批请求 | `ApprovalRequest{session, call, summary, timeout_ms}` | **证据包、影响面、回滚方案放不下** |
| 双人复核 / 批量 / 免审 | 无对应 | 需扩展或落在 DA16 内部 |
| 幂等 / dry-run / 补偿 | 无对应 | 落在 DA15.3 + DA07 实现 |

结论：**档位与委托可以完全映射；审批内容放不进 `ApprovalRequest`**。要么扩字段（动 iface），要么把证据包放外部存储、`summary` 里只放引用。后者改动小，建议先用后者。

### 需要的输入
- 内核是否允许 `ApprovalRequest` 增字段
- 审批证据是否需要进入审计不可变链

## D3｜组装层归属与 payload schema

### 背景
此前评审提过「Preset 组装层没定义」。核对后事实是：内核**已有** `ExtensionContract`（`describe → on_assembly_intent → assembly_status → deactivate`）与 `ComponentContract{name, version, requires_api}`、`AssemblyIntent{session, act, payload: Vec<u8>}`。
**协议有了，缺的是 `payload` 的声明式结构**——也就是「选哪些模块、什么参数、什么版本、什么顺序」的那份清单。

### 作用
决定「模块化」能不能真的组装。没有清单格式，每个场景都要写代码拼装，模块化就退化成「一堆可复用函数」。

### 影响面
- **全部 18 个模块**：每个模块都要能声明自己的可装配点与参数
- **bundle 设计**（D4）：清单里引用的就是 bundle
- **DA17.2 钉定**：钉定对象就是清单里的版本集合
- **DA18 交付**：交付物之一就是可复现的装配清单
- 返工成本：中。定晚了，各模块会各自发明配置格式

### 选项
| 选项 | 说明 |
|-|-|
| A 用现有 TOML/JSON 约定（`mint.toml` 扩展） | 复用打包体系 |
| B 新定义 manifest schema | 表达力强，但要维护新格式 |
| C 直接用代码（Python 装配脚本） | 最快，但不可声明、不可审计 |

### 建议
**A**。清单 = `mint.toml` 的 `[assembly]` 段：模块列表 + 版本约束 + 参数 + 依赖顺序，序列化进 `AssemblyIntent.payload`。
**定之前可以往前走**：D4 的 bundle 按「一模块一包」先切，清单格式后补——因为包边界稳定后，清单只是引用它们。

## D4｜bundle 粒度与发布单元

### 背景
数据层我按「一模块一 bundle」写（connectors / profiler / ontology），但也可以「一层一包」或「按场景组包」（如「制度审核包」）。粒度决定复用与升级的代价。

### 作用
决定升级时「改一个模块要不要重发整层」。也决定客户现场装多少东西。

### 影响面
- 全部模块的目录结构与 `mint.toml`
- DA17.5 部署包构建（包的粒度 = 部署单元）
- DA12.2 版本管理（版本号粒度）
- 返工成本：中。切细了可以合并，切粗了拆分要改引用

### 建议
**一模块一 bundle**。理由：18 个模块的变更频率差异极大（DA01 连接器随客户环境变，DA16 审批策略几乎不变），捆在一起会让低频模块被高频模块拖着升级。版本号天然按模块递增。

## D5｜能力组接口 schema 何时定

### 背景
四份拆分文档给的是**原子能力的输入输出描述**（半形式化），不是可校验的 schema。上一版文档明确写了「本版不定义 schema」。

### 作用
决定契约是先设计再实现，还是先实现再抽取。也决定跨模块联调时靠什么对齐。

### 影响面
- 全部 136 个能力组
- 与 DA15 契约的关系（DA15.2.1 参数 schema 是动作侧，能力侧另有一套）
- 返工成本：若先写 schema 后实现，schema 会大量返工；若先实现，则联调期靠口头约定

### 建议
**先代码后回填**：每个能力组先落一个 dataclass/TypedDict 当事实标准，等 2–3 个模块跑通后，用脚本从代码生成 schema。理由：这套能力的输入输出形状现在还是猜的（比如 `Hit` 到底带不带 `why`），过早形式化会锁死错误抽象。

## D6｜实现语言与运行时形态

### 背景
数据层文档默认 Python（生态：pandas/openpyxl/OCR/SQL 驱动）。但内核是 Rust，网关与 guard 属于安全边界。

### 作用
决定「谁能碰写动作」。若能力层用 Python 且能直接调后端，DA07.7「唯一写通道」就只是约定而非强制。

### 影响面
- DA07 网关与 guard 的强度
- 部署形态（Python 运行时 vs 单二进制）
- DA17.5 离线包体积与依赖
- 返工成本：高。语言定了再换等于重写

### 建议
**Python 做能力（DA01–DA06、DA08–DA14、DA18），Rust 做网关与 guard（DA07.7/7.8、DA16 的委托校验）**。写动作只能由 Rust 侧发起，Python 侧拿不到写后端的凭据——这样「唯一写通道」是编译期与进程边界保证的，不是纪律。

## D7｜存储选型

### 背景
拆分文档里出现了四类存储：语义库（DA03）、血缘图（DA02.7/DA03.7）、证据链（DA12.10）、检索索引（DA05）。

### 作用
决定 DA05 检索质量上限、DA12 审计能否不可篡改、DA03 版本切换是否原子。

### 影响面
- DA03 全部、DA05 全部、DA12.10、DA02.7
- DA17.5 部署（客户环境能不能装图库/向量库）
- 返工成本：中。存储可替换，但索引与查询代码要重写

### 建议
**PostgreSQL 起步**：语义库用表 + JSONB，血缘用递归 CTE，证据链用只追加表 + 哈希链，检索先用 `pg_trgm` + 可选向量扩展（pgvector）。
理由：客户环境能装 PG 的概率远高于能装图库/独立向量库；且四类存储能用一套备份与权限体系。图查询真成瓶颈时再把血缘单独迁出。

## D8｜DA12 权限与内核 guard 的关系

### 背景
内核 `core/src/guard/` 已经是「单一门 + fail-closed + 审计不可关」。DA12.1 又定义了访问范围检查与脱敏。

### 作用
决定是「两道闸门」还是「一道闸门 + 策略源」。两道闸门会出现「内核放行、DA12 拒绝」的不一致。

### 影响面
- DA12.1 三个原子
- DA16 委托校验
- 全部取数路径
- 返工成本：低（早定），高（实现后再统一）

### 建议
**单闸门**：内核 guard 是唯一的执行点，DA12.1 只作为**策略源**（提供允许范围、敏感字段、脱敏规则），不自己做放行判断。脱敏作为取数后处理，挂在 DA01 读取返回处。

## D9｜执行沙箱与引擎自举的边界

### 背景
DA07.2.1 本地 Python 执行、DA07.2.2 远程沙盒、DA07.10 引擎自举与一致性验证、DA17.5 现场部署，四者都在回答「在哪跑、跑哪个版本」。

### 作用
决定「一致性验证」由谁负责——这是 FDE 场景里最容易出事的地方（客户环境装的版本和验证过的版本不是一个）。

### 影响面
- DA07.10 三个原子
- DA17.5 五个原子
- DA11.4.5 引擎一致性回归
- 返工成本：中

### 建议
**引擎获取与校验归 DA07.10，部署归 DA17.5**：DA17.5 只负责把「带校验和的离线包」装上去；DA07.10 每次启动校验版本与校验和，不一致就降级留证（DA07.10.3）。一致性回归（DA11.4.5）消费 DA07.10.2 的差异分类，不自己再跑一套。

## D10｜令才是否覆盖支柱一

### 背景
「制度提取与规则审核」以只读与判定为主。它天然覆盖支柱三（可验收），是否覆盖支柱一（契约下的写动作）取决于**审核结论要不要回写客户系统**。

### 作用
决定令才对外是「DataAgent 案例」还是「FDE 案例」。差别很大：写回意味着要建 DA03.11–13、DA15、DA16.2、DA07.7 一整条链。

### 影响面
- 交付口径与宣传口径
- 需要补建的模块数量（约 3 个模块 + 4 个能力组）
- 返工成本：低（现在只出报告），高（承诺了写回再退回）

### 建议
**先按「只出报告」交付**，把 DA10.3 报告链路做扎实；写回作为第二阶段，且必须先有 DA03.12 权属模型与 DA16.2 审批，否则等于给客户一个能改数据但没有审批的系统。

## D11｜五个偏宽能力组是否本版拆

### 背景
按原子能力判据复核，`DA06.4 计算计划修正`、`DA08.5 结果解释`、`DA12.3 反馈与更新建议`、`DA14.7 编队与接管`、`DA18.2 自助界面` 一个名字下装了多个动作。

### 作用
影响装配粒度：不拆则这五处只能整组选，拆了才能按需组合。

### 影响面
- 仅这五组，及其下游引用（DA11 评测、DA18 交付清单）
- 返工成本：低（只改文档与编号），但如果已经有人按旧编号做了实现，要改名

### 建议
**下一版拆，且用追加编号不重排**（如 DA06.4 拆成 06.4a/06.4b），避免打断已有引用。当前已定稿，不宜再动结构。

## D12｜编队归 OS 还是能力层

### 背景
DA14.7 定义了「角色与子目标划分 / 上下文派发 / 人工接管」。内核已有 `DelegationGrant`、`Lease`（租约、接管语义）、`BlockedOnItem`（等待项）。

### 作用
决定多 Agent 是「能力层编排出来的」还是「OS 原生支持的」。若 OS 已有租约与委派，能力层再造一套会出现双重归属。

### 影响面
- DA14.7 三个原子
- DA16.1 委托
- DA17.3 上下文派发
- 返工成本：中

### 建议
**编队的机制归 OS（委派、租约、阻塞项），能力层只做「角色与子目标划分」**。DA14.7.2 的上下文派发直接调 DA17.3，不另建通道。这样「谁在跑、谁有权跑」只有一处定义。
